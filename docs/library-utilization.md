# Library utilization catalog

A tabulation of which third-party Rust libraries and features this repository uses, and in which
files. `docs/library-utilization.jsonl` is the data; this page is the schema, the query recipes
and the plan for generating it by script. It offers potentially valuable context on library
capabilities and integration patterns already used in the codebase. Optional, focused lookups
can suggest established mechanisms worth considering, even when some entries lag the
implementation. The [library skills](../.claude/skills/README.md) and [pins](pins.md) provide
further API and version context.

Compiled by hand from reading the code on 2026-09-29, then regenerated by script (below): the
`library` records and each capability's items, files and status come from the manifests, a source
scan and rust-analyzer's resolution; the feature labels, purposes and wrappers are hand-written.
`verified` stamps are `YYYY-MM-DD@sha`. Rust only. No stage builds the workspace, so a mid-refactor
tree does not invalidate it; files drift as the cutover proceeds.

## Querying it

The file is large; query it, do not read it whole.

```
# libraries, pins, dependents
jq -r 'select(.kind=="library") | [.lib,.pin,.status,(.dependents|join(","))] | @tsv' docs/library-utilization.jsonl
# features of one library and the files using each
jq -r 'select(.kind=="capability" and .lib=="petgraph") | [.feature,(.files|map(.path)|join(" "))] | @tsv' docs/library-utilization.jsonl
# skill-covered libraries with no local precedent
jq -r 'select(.kind=="library" and .status=="not-used") | [.lib,.skill] | @tsv' docs/library-utilization.jsonl
# who uses what in one crate
jq -r 'select(.kind=="capability" and (.files[].path|test("crates/cpg-flow/"))) | [.lib,.feature] | @tsv' docs/library-utilization.jsonl
```

## Records

One JSON object per line, sorted by `lib`, library record first; `kind` discriminates.

**`library`**

| Field | Meaning |
|---|---|
| `lib`, `pin`, `features`, `default_features` | Crate as Cargo spells it (renamed keys such as `ruff_python_ast_ty` are their own records), workspace pin, enabled features, `false` when default features are off (absent otherwise) |
| `skill`, `skill_pin_delta` | Covering library skill (`null` = none) and where a covering skill indexes a version other than ours |
| `dependents` | Crates that declare it; `(dev)` and `(build)` mark the dependency kind |
| `used_in` | Files referencing it per workspace package, by role: `src` (production code, build scripts included), `test` (`tests/`, `examples/`, `#[cfg(test)]` items), `dormant` (uncompiled) |
| `crates` | On a `not-used` family record, the skill crates it stands for |
| `status` | From the source scan: `used` (any production file), `test-only`, `dormant-only`, `declared-unused` (declared, no reference); `not-used` (skill-covered, no direct dependency: no local precedent; the note says if it is locked transitively) |
| `wrappers` | The local abstraction other code goes through, `{path, symbol}` |
| `note`, `verified` | One-line caveat; `YYYY-MM-DD@sha`, restamped only when a generated field changes |

**`capability`**: one per distinct library feature we use.

| Field | Meaning |
|---|---|
| `id`, `lib`, `feature` | `<lib>/<slug>`, owning crate, short label |
| `items` | Defining paths (at most 6), as rust-analyzer or the skills' indexes name them: `arrow_schema::schema::Schema`, `sqlx_core::transaction::Transaction::commit`. A method that implements a trait method may be recorded at either level |
| `as_written` | Spellings replaced by normalisation (facade or re-export paths our code uses), for grepping; absent when nothing was replaced |
| `use` | One line: what we use it for |
| `files`, `n_files` | At most 5 `{path, role}`, recorded roles and order first, then new evidence by number of references; `n_files` is every file with evidence plus the indirect entries kept |
| `wrapper` | Abstraction consumers go through, or `null` |
| `status`, `verified` | `used`, `test-only` or `dormant-only`; stamp |

`role`: `impl`, `wrapper`, `consumer`, `test`, `dormant`, `macro-expansion`, `sql-string`.
`dormant` means under `crates/cpg-core/tests/dormant/`, which is not compiled.

**Granularity.** A capability is a distinct decision a reviewer might replicate, not an import.
Heavily used libraries (Arrow, DataFusion, sqlx) get about 8-10; small ones (petgraph,
biodivine-lib-bdd, leiden-rs, salsa, pgpq) list every file. Excluded: `third_party/`, `.sqlx/`,
`target/`, `build/`, `crates/lctx-workspace-hack`, `*.snap`, `.claude/skills`, `libraries/`, Python.

## Generating it by script

Stages S0 (manifests), S1 (source scan), S2 (semantic resolution) and S3 (canonical names) exist:
`scripts/library_utilization.py` drives `scripts/library_scan.py`, `scripts/library_semantic.py`,
`scripts/library_names.py` and `tools/lu-resolve`.

```
uv run python scripts/library_utilization.py           # dry run: prints drift, exit 1 if any
uv run python scripts/library_utilization.py --write   # regenerate the catalog
uv run python scripts/library_utilization.py --resolved FILE   # reuse a saved lu-resolve output
```

No stage builds the workspace. S0, S1 and S3 take about two seconds; S2 takes one to two minutes
and several GB (it type-checks the function bodies that contain method calls) and builds
`tools/lu-resolve` on first use, offline, on its own pinned toolchain. The order, and who wins a
disagreement: S1 finds direct references; S2 adds what S1 cannot see to each library's `used_in` and
`status`; S3 rewrites an item to the skills' defining path unless S2 already resolved that exact
path (the compiler's path wins); S2's evidence then rewrites the items no index could place and
regenerates each capability's `files`, `n_files` and `status`.

Generated: every mechanical `library` field (`pin`, `features`, `default_features`, `dependents`,
`skill`, `skill_pin_delta`, `status`, `used_in`), the `not-used` records, and each capability's
`items`, `as_written`, `files`, `n_files` and `status`. Kept as written: `wrappers`, `note`,
`feature`, `use`, `wrapper`, and the roles of files that still resolve. Entries the resolver cannot
see are kept: a `consumer`, `macro-expansion`, `sql-string` or `dormant` file, and any non-Rust
file. `verified` is restamped only where a generated field changed. A capability none of whose
items resolves (derive-only or macro-only use) keeps its files as recorded, and the run says so.
Advisory sections list what needs a human:

- `unlisted`: direct dependencies no skill covers and the catalog does not list (the utility crates).
- `capability files dropped (no resolution)`: recorded `impl`, `wrapper` or `test` files where none
  of the capability's items resolves any more.
- `items not resolved by rust-analyzer`: recorded items no reference resolved to, or that resolved
  to several candidates. Mostly derive and macro use (`serde_arrow` output, `sqlx::FromRow`).
- `resolved library items no capability records`: items resolved in two or more files that no
  capability lists, top five per package. New usage to triage, and the way new capabilities start.
- `scan vs ripgrep`: libraries where S1 and an independent `rg` file list disagree; the usual cause
  is a package that uses a path without declaring the dependency (a proc-macro crate emitting
  `serde_arrow::` tokens, a local function that shares a crate's name).
- `items not in the skill index`: recorded items whose crate a skill indexes but which the index does
  not list. Today these are pyrefly items that only exist or are public through the fork patch; a
  version delta from `skill_pin_delta` is shown when there is one.
- `items in crates no skill indexes`: a count per crate (sqlx, pyo3, pgpq, ...); S2 places these.

Tests: `tests/scripts/test_library_utilization.py`, `test_library_scan.py`,
`test_library_names.py`, `test_library_semantic.py`.

**How S1 works.** A lexical pass, so it runs the same on a tree that does not compile. It masks
comments and string and char literals, then finds `root::` paths, `use root;`, `::root::`,
`extern crate root` and the `$crate::__private::root::` macro re-export form, where `root` is a
dependency **the file's own package declares** (renames map to their own record, so `_ty` files
never count for the 0.0.11 crates). It tags references inside `#[cfg(test)]` and `#[test]` items
(and `#![cfg(test)]` files) as test, and files by location (`tests/dormant/` is `dormant`,
`tests/`, `examples/`, `benches/` and `tests.rs` are `test`, `build.rs` is `build`). It resolves
and expands nothing, so a file that reaches a library only through a re-export or an inferred method
call is not counted for it; S2 covers that.

**How S2 works.** `tools/lu-resolve` (its own Cargo workspace; `ra_ap_*` 0.0.352 and `salsa`
0.28.2 pinned exactly in its `Cargo.lock`, on the toolchain the rust-code-model skill pins) loads
the workspace with `ra_ap_load_cargo::load_workspace_at` and no build: `load_out_dirs_from_check`
off, no proc-macro server, no cache priming, all features, `cfg(test)` on. It resolves every path
node (`Semantics::resolve_path`) and method call (`resolve_method_call`) in the workspace's own
files and prints, per file and library item, the defining path, package, version and lines. A
path that names a re-export resolves to the defining crate and module. A method that implements a
trait method is reported as `Type::method` and `Trait::method`. Only items from non-workspace
crates are printed. The Python side joins that to the catalog by exact path: a capability's files
are the files where its items resolve, and a recorded item no index could place (`sqlx::query_as`,
`tracing::info!`) is rewritten to the unique resolved path that shares its last segment, crate
family and owner type, searched in the capability's own files first. Not visible by design:
references inside macro expansions and derive output (the proc-macro server is off, since starting
it means building proc macros), and files outside the module tree (`tests/dormant/`). Evidence for
this choice over `rust-analyzer scip`, which builds build scripts and proc macros whatever its
config says: [the spike](design_review/evidence/2026-09-29_library-utilization-semantic-stage/README.md).

**How S3 works.** Each enabled skill ships `content/index/{symbols,aliases,methods}.tsv` (defining
paths, the paths items are reachable by, and methods). Each recorded item resolves against their
union: an exact defining path; an alias (re-export or facade) rewritten to the defining path; a
`Type::method` with the type resolved and the method listed; or a unique same-crate name for
crate-root re-exports such as `arrow_schema::Schema`. The method reading comes before the name
reading so a method is never taken for a free function of the same name. The index is the version
each skill pins, so a mismatch with ours shows as `skill_pin_delta`.

| Stage | Source (rust-code-model layer) | Produces | Limits |
|---|---|---|---|
| S0 manifest (built) | cargo-metadata (`cargo_metadata::MetadataCommand`, `--no-deps`), `Cargo.lock`, each skill's `build/manifests/<skill>.json` | `library` records: pin, features, dependents with dev/normal kind, renames, skill, `skill_pin_delta`, `not-used` records | Declared features, not the resolved build (PL003); `resolve` is null under `--no-deps` (PL001), so resolved versions come from the lock |
| S1 syntax (built) | syntax layer's job (`ra_ap_syntax`, tree-sitter), done lexically over non-excluded `.rs` | `status`, `used_in`, the ripgrep cross-check | Parses non-compiling code (SY001). Resolves and expands nothing (SY003) |
| S2 semantics (built) | project-load + hir: `load_workspace_at` (`LoadCargoConfig`), `Semantics::resolve_path`, `resolve_method_call`, `ModuleDef::canonical_path`, `Crate::origin` and `version` | Library-level references through re-exports and imports; canonical `items`; `files`, `n_files`, `status` per capability; the uncatalogued list | Macro and derive output not visited; needs a loadable project (`cargo metadata` and sources), not a passing build; rust-analyzer's inference over a mid-refactor tree is best effort |
| S3 names (built) | Skill `content/index/{symbols,aliases,methods}.tsv` | Normalized `items`, `as_written`, the not-in-index list | Only skill-covered crates; relative to the version each skill indexes |

**Later enrichment.** S5 reachability: from the same resolved references, file to module to crate,
then a use graph from `lctx` `main` and `#[pymodule]`, to distinguish `used` from reachable from a
binary (today DataFusion in `cpg-core` and the `lctx-postgres` serving queries are referenced but
have no production caller). It reflects the tree's current wiring, so it moves during the cutover.

Rejected layers: MIR and dataflow (no source names, and MIR refuses a tree that does not compile);
rustdoc-json for our own code (no bodies, RD002).
