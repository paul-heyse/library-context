# Library utilization catalog

A tabulation of which third-party Rust libraries and features this repository uses, and in which
files. `docs/library-utilization.jsonl` is the data; this page is the schema, the query recipes
and the plan for generating it by script. Use it **before** assessing a library: see whether we
already use it, through which wrapper and where, or that it has no local precedent, then go to the
[library skills](../.claude/skills/README.md) and [pins](pins.md).

Iteration 1: capabilities compiled by hand from reading the code on 2026-09-29; `library` records
generated by script (below). `verified` stamps are `YYYY-MM-DD@sha` (`2026-09-29@a738da7` for the
hand-compiled records). Rust only. Nothing here depends on the tree compiling, so a mid-refactor
tree does not invalidate it; files drift as the cutover proceeds.

## Querying it

The file is large; query it, do not read it whole.

```
# libraries, pins, dependents
jq -r 'select(.kind=="library") | [.lib,.pin,.status,(.dependents|join(","))] | @tsv' docs/library-utilization.jsonl
# features of one library and the files using each
jq -r 'select(.kind=="capability" and .lib=="petgraph") | [.feature,(.files|map(.path)|join(" "))] | @tsv' docs/library-utilization.jsonl
# skill-covered libraries with no local precedent
jq -r 'select(.kind=="library" and .status=="not-used") | [.lib,.skill] | @tsv' docs/library-utilization.jsonl
# who uses what in one crate
jq -r 'select(.kind=="capability" and (.files[].path|test("crates/cpg-flow/"))) | [.lib,.feature] | @tsv' docs/library-utilization.jsonl
```

## Records

One JSON object per line, sorted by `lib`, library record first; `kind` discriminates.

**`library`**

| Field | Meaning |
|---|---|
| `lib`, `pin`, `features`, `default_features` | Crate as Cargo spells it (renamed keys such as `ruff_python_ast_ty` are their own records), workspace pin, enabled features, `false` when default features are off (absent otherwise) |
| `skill`, `skill_pin_delta` | Covering library skill (`null` = none) and where a covering skill indexes a version other than ours |
| `dependents` | Crates that declare it; `(dev)` and `(build)` mark the dependency kind |
| `used_in` | Files referencing it per workspace package, by role: `src` (production code, build scripts included), `test` (`tests/`, `examples/`, `#[cfg(test)]` items), `dormant` (uncompiled) |
| `crates` | On a `not-used` family record, the skill crates it stands for |
| `status` | From the source scan: `used` (any production file), `test-only`, `dormant-only`, `declared-unused` (declared, no reference); `not-used` (skill-covered, no direct dependency: no local precedent; the note says if it is locked transitively) |
| `wrappers` | The local abstraction other code goes through, `{path, symbol}` |
| `note`, `verified` | One-line caveat; `YYYY-MM-DD@sha`, restamped only when a generated field changes |

**`capability`**: one per distinct library feature we use.

| Field | Meaning |
|---|---|
| `id`, `lib`, `feature` | `<lib>/<slug>`, owning crate, short label |
| `items` | Defining paths (at most 6). Rewritten by S3 for skill-covered crates; adjacent crates (sqlx, pyo3, ...) keep the path as recorded |
| `as_written` | Spellings S3 replaced (facade or re-export paths our code uses), for grepping; absent when nothing was replaced |
| `use` | One line: what we use it for |
| `files`, `n_files` | At most 5 `{path, role}`, best example first; total files using it |
| `wrapper` | Abstraction consumers go through, or `null` |
| `status`, `verified` | `used`, `test-only` or `dormant-only`; stamp |

`role`: `impl`, `wrapper`, `consumer`, `test`, `dormant`, `macro-expansion`, `sql-string`.
`dormant` means under `crates/cpg-core/tests/dormant/`, which is not compiled.

**Granularity.** A capability is a distinct decision a reviewer might replicate, not an import.
Heavily used libraries (Arrow, DataFusion, sqlx) get about 8-10; small ones (petgraph,
biodivine-lib-bdd, leiden-rs, salsa, pgpq) list every file. Excluded: `third_party/`, `.sqlx/`,
`target/`, `build/`, `crates/lctx-workspace-hack`, `*.snap`, `.claude/skills`, `libraries/`, Python.

## Generating it by script

Stages S0 (manifests), S1 (source scan) and S3 (canonical names) exist:
`scripts/library_utilization.py`, `scripts/library_scan.py` and `scripts/library_names.py`.

```
uv run python scripts/library_utilization.py           # dry run: prints drift, exit 1 if any
uv run python scripts/library_utilization.py --write   # regenerate the library records
```

It needs no build and runs in about two seconds. It regenerates every mechanical `library` field
(`pin`, `features`, `default_features`, `dependents`, `skill`, `skill_pin_delta`, `status`,
`used_in`), the `not-used` records and each capability's `items`; keeps `wrappers`, `note` and the
hand-written capability fields; and restamps `verified` only where a generated field changed.
Advisory sections list what needs a human:

- `unlisted`: direct dependencies no skill covers and the catalog does not list (the utility crates).
- `capability files`: files a capability cites that are gone, or (for `impl`, `wrapper`, `test`
  and `dormant` files) no longer reference the library. `consumer`, `macro-expansion` and
  `sql-string` files are only checked for existence.
- `scan vs ripgrep`: libraries where the scan and an independent `rg` file list disagree; the usual
  cause is a package that uses a path without declaring the dependency (a proc-macro crate emitting
  `serde_arrow::` tokens, a local function that happens to share a crate's name).
- `items not in the skill index`: recorded items whose crate a skill indexes but which the index
  does not list (`absent`), or lists more than once by that name (`ambiguous`). Today these are all
  pyrefly items that only exist or are public through the fork patch; a version delta in
  `skill_pin_delta` is shown when there is one.
- `items in crates no skill indexes`: a count per crate (sqlx, pyo3, pgpq, fixedbitset, ...), left
  as recorded.
- orphan capabilities: a capability whose library record is gone.

Tests: `tests/scripts/test_library_utilization.py`, `test_library_scan.py`, `test_library_names.py`.

**How S1 works.** A lexical pass, so it runs the same on a tree that does not compile. It masks
comments and string and char literals, then finds `root::` paths, `use root;`, `::root::`,
`extern crate root` and the `$crate::__private::root::` macro re-export form, where `root` is a
dependency **the file's own package declares** (renames map to their own record, so `_ty` files
never count for the 0.0.11 crates). It tags references inside `#[cfg(test)]` and `#[test]` items
(and `#![cfg(test)]` files) as test, and files by location (`tests/dormant/` is `dormant`,
`tests/`, `examples/`, `benches/` and `tests.rs` are `test`, `build.rs` is `build`). It resolves
and expands nothing: a file that reaches a library only through a re-export
(`cpg_schema::arrow_array::X`, `lctx_model::__private::...`), an inferred method call, or code a
macro generates is not counted for that library. That is why S1 shows Arrow and serde_arrow with
fewer files than a reader might expect, and why capabilities carry hand-tagged `macro-expansion`
files. The semantic stage below closes that gap.

**How S3 works.** Each enabled skill ships `content/index/{symbols,aliases,methods}.tsv` (defining
paths, the paths items are reachable by, and methods). Each recorded item resolves against their
union: an exact defining path; an alias (re-export or facade) rewritten to the defining path; a
`Type::method` with the type resolved and the method listed; or a unique same-crate name for
crate-root re-exports such as `arrow_schema::Schema`. The method reading comes before the name
reading so a method is never taken for a free function of the same name. The index is the version
each skill pins, so a mismatch with ours shows as `skill_pin_delta`.

Not built: the merge of S1 references into capability `files`, `n_files` and `status`. The target
is what needs no build: manifests and source text. Hand-written fields (`feature`, `use`,
`wrapper`, the capability grouping) stay in the data and are merged by `id`.

| Stage | Source (rust-code-model layer) | Produces | Limits |
|---|---|---|---|
| S0 manifest (built) | cargo-metadata (`cargo_metadata::MetadataCommand`, `--no-deps` is enough), `Cargo.lock`, each skill's `build/manifests/<skill>.json` | `library` records: pin, features, dependents with dev/normal kind, renames (`Dependency::rename` maps `_ty` keys to their package), skill, `skill_pin_delta`, `not-used` records | Declared features, not the resolved build (PL003); `resolve` is null under `--no-deps` (PL001), so resolved versions come from the lock |
| S1 syntax (built) | syntax layer's job (`ra_ap_syntax`, tree-sitter): done here lexically over non-excluded `.rs` | `status`, `used_in`, the capability-file and ripgrep cross-checks | Parses non-compiling code (SY001). Resolves and expands nothing (SY003) |
| S3 names (built) | Skill `content/index/symbols.tsv`, `aliases.tsv` and `methods.tsv` (defining path, re-export aliases, methods) | Normalized `items`, `as_written`, a list of recorded items the index does not list | Only for skill-covered crates; adjacent ones (sqlx, pyo3) keep names as recorded; relative to the version each skill indexes |

**Later enrichment, not this target** (each depends on a loadable or compilable project, so a
transient break in the tree would change its output):

| Stage | Layer | Adds | Why later |
|---|---|---|---|
| S2 semantics | project-load + hir: `ra_ap_load_cargo::load_workspace_at`, `ra_ap_ide::StaticIndex::compute`, `Analysis::moniker` (`PackageInformation` name and version, defining path) | Canonical `items` through re-exports, globs, renames and inferred calls (petgraph `edges_directed`); derive-emitted `serde_arrow` use with proc macros built | Needs `cargo metadata` and sources; proc macros must be built to expand; the skill's evidence (HI001) covers a loadable project only, so behavior on a mid-refactor tree is unverified |
| S5 reachability | hir references: file to module to crate, then a use graph from `lctx` `main` and `#[pymodule]` | `used` vs reachable-from-a-binary (today DataFusion in `cpg-core` and the `lctx-postgres` serving queries are referenced but have no production caller) | Reflects the tree's current wiring, so it moves during the cutover |

Rejected layers: MIR and dataflow (no source names, and MIR refuses a tree that does not compile);
rustdoc-json for our own code (no bodies, RD002). If S2 is built: an own Cargo workspace under
`tools/` with exact `ra_ap_*` pins (every release is semver-breaking; the skill pins 0.0.352 on
`nightly-2026-09-13`, not this repository's toolchain), after a spike comparing `rust-analyzer scip`
(present here, not covered by the skill's probes) with a `StaticIndex` binary.
