## Useful abilities already present

**Documented/source-inspected, not locally exercised:** `INFO FOR DB`, `INFO FOR TABLE <table>` and the structured `STRUCTURE` form expose definitions, fields and indexes. This can answer whether a fixture actually holds the intended physical schema rather than inferring it from Rust declarations. Official MCP adds `info` and `list` for scoped schema inspection. `list` can restrict inspection to fields or indexes for a named table, avoiding a large dump. [Official INFO documentation](https://github.com/surrealdb/docs.surrealdb.com/blob/main/src/content/reference/query-language/statements/info.mdx); [3.3 MCP schema implementation](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/tools/schema.rs).

**Documented/source-inspected:** installed `surreal validate --stdin` and file-glob validation use `syn::parse`. They require no datastore. They reject grammar errors before a compile/test/database run, but establish neither schema compatibility, permissions, planner support nor runtime correctness. An empty file-glob match is an error. This is a low-burden candidate for agents drafting generated SQL. [3.3 validation implementation](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/server/src/cli/validate.rs).

**Source-inspected:** 3.3 includes both suffix SELECT explain forms and prefix `EXPLAIN SELECT ...`; the pinned language corpus also contains `EXPLAIN ANALYZE ...` and JSON analysis tests. Use a statement and shape actually supported by the pinned planner, rather than assuming PostgreSQL syntax or one historical EXPLAIN output shape. Static explain can reveal scan/index and filter placement; analysis executes work and must use an owned fixture with a bounded query. Neither is evidence of representative journey latency. [3.3 planner tests](https://github.com/surrealdb/surrealdb/blob/v3.3.0/language-tests/tests/language/statements/explain/analyze_json.surql). Local source-corpus route: `.claude/skills/neo4j-surrealdb/surrealdb/content/corpus/language-tests/language-tests/tests/language/statements/explain/` and `language/planner/select.surql`.

**Source-inspected:** the SDK distinguishes request errors from per-statement errors. `query(...).await?` can succeed while a statement failed; `.check()` rejects a failed response, while `.take_errors()` preserves indexed errors for diagnosis. Streaming has an additional outer transport error plus `StreamItem::StatementEnd { result, ... }`. Rows are provisional until completion; stopping at a row or statement success can miss later errors. Some transports replay buffered results, so the API name alone proves no memory/latency improvement. [3.3 SDK query contracts](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/src/method/query.rs), especially lines 124–220, 281–350 and 704–753.

The current native consumer already handles ordered terminal events, missing terminals, sticky failures, late drainage errors and session retention in `crates/lctx-surrealdb/src/reader.rs:404` onward. Those dirty edits and synthetic streaming tests are **untested in this investigation**. An MCP query is buffered through datastore execution and cannot substitute for a production gRPC stream lifecycle probe.

## Three connection choices

| Choice | Established capability/lifecycle | Fit and burden for this workstation |
|---|---|---|
| Installed `surreal mcp` over stdio | Opens its own embedded datastore; default `memory`. Calls run with `Session::owner()`. Datastore startup/maintenance/shutdown belongs to that command. User/password initialize a root user; they do not turn stdio into a constrained remote login. | **Proposed** only for independent scratch experiments. It would not inspect the existing fixture. Pointing it at a fixture storage directory introduces a second datastore owner and lock/lifecycle conflict. `--log none` is the skill's historical stdout recommendation, not newly tested here. |
| Existing server's built-in `/mcp` | 3.3's HTTP route shares the running datastore. It is gated by HTTP route capabilities and uses the authenticated HTTP session. It exposes schema/query tools without an external SDK bridge. | **Proposed** strongest discovery/diagnostic route. Requires fixture-scoped connection metadata/token, a live fixture lifetime, explicit namespace/database and an actual Codex connection. Dynamic fixture ports and retained content matter. No server startup change is established as necessary. |
| Thin CLI/SDK diagnostic binding | Installed `surreal sql` supports endpoint, namespace/database, username/password/auth-level or JWT. Existing fixture `/sql` already returns per-statement envelopes; Rust SDK can retain typed errors and stream terminals. | **Proposed** likely lower setup burden for occasional diagnostics or authoritative stream investigation. Must read attachment config and own lifetime explicitly. A small fixture-scoped command may be sufficient; do not build a permanent bridge merely to expose library methods. |

Lifecycle evidence: [3.3 stdio implementation](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/server/src/cli/mcp.rs), [3.3 HTTP route](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/server/src/ntw/mcp.rs), [3.3 session implementation](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/session.rs), [current embedded MCP documentation](https://github.com/surrealdb/docs.surrealdb.com/blob/main/src/content/build/ai-agents/mcp/embedded.mdx).

An official current Codex plugin offers `surrealdb-local`: an HTTP URL pointing to the instance `/mcp`, plus a bearer-token environment variable. This is a client connection to the built-in service, not a distinct datastore proxy. Its README distinguishes the managed cloud endpoint from local/private instances. Managed cloud MCP adds account/infrastructure capabilities but does not supply access to this workstation's loopback fixture. This investigation did not install the plugin or verify local Codex compatibility. [Official plugin README](https://github.com/surrealdb/ai-codex-plugin), [local plugin configuration](https://github.com/surrealdb/ai-codex-plugin/blob/main/plugins/surrealdb-local/.mcp.json). Plugin `main` was inspected on 2026-10-09; its contracts are not a 3.3 server release pin. No official standalone remote bridge was established by the bounded search; the built-in HTTP route makes one unnecessary for this candidate.

## Failure and session contracts agents must preserve

**Source-inspected:** MCP `query` supports parameter bindings and per-call namespace/database. Typed Surreal values can be represented by `$ql` wrappers; raw JSON strings must not be silently treated as record IDs. The service also exposes mutation tools. A `read_only_hint` annotation is descriptive, not a permission boundary. Use an appropriately scoped authenticated fixture session; verify whether its role permits INFO/schema visibility as well as intended query access. [3.3 query parameters](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/tools/query.rs), [service dispatch](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/service.rs), [authentication binding](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/auth.rs).

**Source-inspected:** mixed successful/failed MCP statements deliberately leave `is_error = false`. Agents must inspect `results[].status` and `has_errors`; a successful tool invocation is not query success. Single failed statements report an error. Default tool-result payload cap is 256 KiB per statement, replacing oversized values with an explicit truncation marker. Default MCP outer query timeout is 60 seconds; fixture server query/transaction timeouts are 20s/10s. These controls bound different things, and a serialized output cap does not bound database compute or complete buffered allocation. [3.3 output implementation](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/tools/output.rs), [configuration](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/mcp/src/cnf.rs).

**Source-inspected:** HTTP service supports initialized sessions and explicit stateless requests. `use` requires stateful session context; per-call scope avoids mutable selection dependence and is appropriate for fixture attachments. HTTP auth/session identity is rechecked; MCP session ID alone is not login authority. Connection initialization, token expiry, scope preservation and termination remain integration questions, not verified workstation behavior.

**Source-inspected:** CLI `sql --json` turns per-statement errors into strings in the result values (`result.unwrap_or_else(|e| Value::String(e.to_string()))`). Thus JSON output and shell exit status are weaker machine evidence than the SDK or `/sql` statement envelopes. A diagnostic adapter must not identify an error merely by whether a result is a string: legitimate string results exist. [3.3 SQL CLI source](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/server/src/cli/sql.rs), lines 292–311.

## Actual fixture consumers and command evidence

The live fixture source already supplies HTTP and gRPC endpoints plus owned credentials and scope in private config files (`scripts/surrealdb_fixture.py:85`, `:456`, `:880`). It sets `LCTX_SURREAL_TEST_CONFIG` and `LCTX_COMPILER_RUNTIME_CONFIG`; neither is an automatic CLI/MCP connection. Every new attachment gets a fresh namespace and `core`, `compiler_cache`, `compiler_products` databases. `--attach ID` alone is therefore not proof that an inspection command sees a previous producing command's records. Retained serving content has its own viewer config and `--serving NAME` route (`:955`, `:1489`). Current production authentication explicitly uses gRPC in `crates/lctx-surrealdb/src/reader.rs:637`.

Existing fixture `Server.query` checks every HTTP SQL statement status and suppresses error bodies that might include secrets (`scripts/surrealdb_fixture.py:791–820`). **Proposed** diagnostic reuse must preserve that privacy boundary while providing enough redacted context to explain failures; dumping private config or SQL containing bound secrets is not required to inspect schema.

`just fixture -- COMMAND` in `docs/surrealdb.md:221` is a placeholder, not a supported executable name. The fixture parser removes the first `--` and passes remaining argv to `spawn_group` (`scripts/surrealdb_fixture.py:1407`, `:1346`). A literal `COMMAND` would attempt to launch that program and may report `blocked: launch: cannot start 'COMMAND': ...`; that is a source-derived prediction, **not an observed failed command receipt**. No SurrealQL parser evidence suggests `COMMAND` is a query grammar construct. The coordinator must use the actual retrospective command/output to attribute the user's historical failure.

Read-only evidence retrieval had concrete failures: upstream URLs lacking the repository's leading `surrealdb/` directory returned 404, and local searches for uncaptured `cli/sql.rs`, `cli/validate.rs` returned missing-path errors. The tagged GitHub tree resolved the correct paths; both files were fetched successfully. These are research lookup failures, not product or fixture failures.

## Candidate opportunities and decisive probes

| Proposed opportunity | User-facing ability and friction addressed | Smallest decisive probe, separately authorized |
|---|---|---|
| Syntax validation route in agent instructions | Detect malformed drafted/generated SurrealQL immediately with installed tools. Minimal integration; does not depend on server state. | Feed one valid and one invalid query to installed 3.3 `validate --stdin`; capture output/status. Do not imply schema qualification. |
| Fixture-scoped built-in MCP connection | Agent asks for table/index definitions, verifies physical schema and compares a query plan interactively. Useful even if no past failure is prevented. Setup must follow fixture lifetime, scope and credentials. | On one owned disposable fixture with known schema/content: connect Codex, inspect one table/index, run bounded EXPLAIN, confirm namespace and scoped permissions, then terminate client before fixture cleanup. Confirm tool visibility in that task. |
| Structured diagnostic envelope via existing `/sql` or SDK | Explain exactly which statement failed; keep useful successes distinguishable from overall operation acceptance. May be cheaper than permanent MCP for occasional work. | One successful and one intentional runtime-failing statement in a disposable fixture; verify statement IDs/statuses, redacted failure context and caller result. Repeat through MCP to show `is_error=false` does not hide mixed failure. |
| Native gRPC stream/session oracle | Inspect rows, StatementEnd failures, late transport failure and handle lifetime without converting the product into a buffered query path. Existing Rust SDK and native reader are the right consumers. | Reuse the responsible worker's focused real-SDK test: same selected profile, row then failed terminal, outer late error, dropped/retained client, complete drain and cleanup. Capture the actual error/cause; MCP success cannot close it. |

The candidate order follows library-first and thin-adapter principles (DP-13/14/15) and lifecycle proportionality (H25–28): try the installed syntax tool and already-running server route before adding a remote bridge. This is qualitative fit, not a quantified effectiveness claim. No permanent global connection, plugin installation, server policy change or new gate is recommended merely because it exists.
