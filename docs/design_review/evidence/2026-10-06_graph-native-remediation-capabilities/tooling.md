## Native frontends and deployment boundaries

SurrealDB 3.3 MCP supports query/gql/graphql/run and CRUD/schema operations, with namespace/database arguments and session switching. Its generic tools can use typed bindings but some select/delete/update clause parameters are raw expressions. Its own prompts/resources describe database operation. This is useful database administration functionality, not equivalent to the project's bounded semantic operation contract. A VIEWER user can still receive silently empty writes; absence of an error does not establish permitted mutation. Stdio `surreal mcp` requires `--log none` to avoid mixing logs with protocol stdout (SB087).

DEFINE API handles SurrealQL at `/api/<ns>/<db>/<path>`. Pinned probe SB136 found string/bytes/NONE bodies work while object bodies fail over HTTP; unauthenticated callers reach the handler unless it enforces admission. GraphQL needs DEFINE CONFIG GRAPHQL and defined fields, and its generated ID argument expects record key rather than the full returned record ID. Postgres wire carries SurrealQL or GQL, not ANSI SQL; prepared and simple row shapes differ. None replaces the current original-source byte anchoring, failure taxonomy, immutable snapshot or complete MCP-envelope admission.

Core maintenance defaults should remain enabled for anything serving queries. The pinned builder warns disabling them prevents index delta compaction, detached namespace data cleanup, changefeed GC, interrupted index resumption and heartbeat refresh. SB104 demonstrates missing async events/changefeed GC; the broader cleanup obligations are source-supported. Do not disable maintenance because snapshots are immutable: indexes and lifecycle deletion still have physical obligations. Modules/files/buckets need separately enabled features and an actual consumer; they are unnecessary for this repair.

## RocksDB controls: server exposure versus underlying library

Context7 current docs returned conflicting `SURREAL_ROCKSDB_*` and `SURREAL_DS_ROCKSDB_*` names; current observability documentation also discusses an Enterprise durable configuration. The **v3.3.0 source is decisive for the selected community server**: `ConfigMap::from_env` strips `SURREAL_` and lowercases; RocksDbConfig parses `rocksdb_block_cache_size`, `rocksdb_write_buffer_size`, `rocksdb_max_write_buffer_number`, etc. Thus selected controls are **SURREAL_ROCKSDB_BLOCK_CACHE_SIZE**, **SURREAL_ROCKSDB_WRITE_BUFFER_SIZE**, **SURREAL_ROCKSDB_MAX_WRITE_BUFFER_NUMBER**. Do not copy DS-prefixed keys or old BACKGROUND_FLUSH settings without checking selected source. The source also has grouped commit, file compaction, jobs, subcompaction, blob GC, readahead, prefix/bloom and shutdown controls; choose only those needed by the deployed consumer.

Block cache default is memory-derived `max(total_memory/2 - 1 GiB,16 MiB)`; write buffers and background jobs are also resource-derived. This does not justify assuming host RAM reflects the deployment's desired bound. Specify an explicit small deployment policy when the server has a constrained allocation. `SURREAL_MEMORY_THRESHOLD` defaults disabled; tracked allocation/cache pressure is a guard, not a complete RSS cap. A threshold at/below a full block cache can refuse all queries; leave sufficient overhead and distinguish server memory, Rust request budgets and Python workers. Limits on result rows or unit pages do not bound fanout expansion or engine scans (audit F11).

Underlying RocksDB APIs such as custom WriteBufferManager/cache construction/manual compact range and per-option tuning are not automatically SDK/server controls. Current project connects remotely and does not own the RocksDB process internals. Use controls wired by RocksDbConfig; do not add a rocksdb dependency just to expose options the remote server does not consume. `SURREAL_DATASTORE_SYNC_DATA` owns synchronization policy in 3.x; preserve the durable setting instead of adopting stale 2.x WAL flush configuration. Keep compaction/GC enabled and let lifecycle retirement perform actual store deletion; no new maintenance command or accounting layer is presently required.

Primary sources: [environment parser](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/cnf/src/config/mod.rs#L42-L60), [RocksDB config](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/kvs-rocksdb/src/cnf.rs#L654-L752), [memory guard](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/cnf/src/lib.rs#L98-L169), [RocksDB backend](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/kvs-rocksdb/src/lib.rs). ## Cancellation/deadlines: composed route

Current `NativeExecutor` owns a semaphore slot in a shielded worker, includes embedding in a 30s request deadline, passes remaining milliseconds into NativeSession, and drains workers before close (`native.py:27-100`). NativeService bounds admission and awaits operation dispatch with `timeout_at` (`service.rs:75-204`). A timeout checked around a synchronous kernel cannot preempt that kernel while it does not yield: inspect actual long kernels and add cooperative checks only at material bounded work boundaries where required. Keep Python ownership/drain, even when caller interest ends.

Pinned gRPC ordinary SDK `.query()` opens a streamed server response and assembles checked statements (`engine/remote/grpc.rs:771`). Server streaming has a `CancelHandle` and `ReleaseOnDrop` trips it when the client stops reading (`server/rpc/grpc.rs:1687,2266`); shortest requested/server deadline also trips cancellation and closes the item channel (:1733). Therefore there is a source-supported cooperative remote cancellation path already, and neither direct core embedding nor a generic query-cancel endpoint is required. `cancel_transaction` cancels an explicit transaction and `KILL` targets live subscriptions; they should not be treated as cancellation of any ordinary query.

Client `Config::query_timeout` is carried into gRPC RequestContext; server `--query-timeout` is the fallback outer/executor guard. Per-operation remaining deadline propagation is a candidate if source-supported connection-level limits are too coarse, but ordinary SDK sharing must not be retargeted or globally mutated. Current runbook's server limits bound residual immutable reads conservatively; a targeted native cancellation/late completion journey is still required before claiming actual interruption. No timing measurement required unless making a quantitative claim.

## F10: exact FastMCP typed error bridge

Installed distribution metadata confirms FastMCP-slim **4.0.5**, MCP and mcp-types **2.2.0**. Context7 `/prefecthq/fastmcp` returns current methods but only lists 3.2 version IDs; transfer claims only after checking installed 4.0.5 source and skill captured contracts. Existing owned `PublicFailure` has five causes and fixed messages; Rust classification must preserve cause before generic conversion, with internal diagnostics separate.

**Tool route:** catch only the native typed exception carrying Rust-emitted PublicFailure JSON; obtain the model-owned error CallToolResult (`is_error=True`, `_meta.lctx_failure`, fixed public text), then return `ToolResult.from_mcp_result(...)`. Installed `fastmcp/tools/base.py:160-188` retains the raw CallToolResult and returns it verbatim, preserving metadata/error flag. Existing `SchemaTool` already uses this seam for success. `ToolError(str(exc))` reduces to text; avoid it for recognized failures. Envelope middleware admits the resulting complete result with request ID/protocol metadata.

**Resource route:** raise `mcp.shared.exceptions.MCPError(code=<fixed owned mapping>, message=<PublicFailure fixed message>, data={"lctx_failure": <owned DTO>})`. Constructor stores ErrorData data (installed source :24-39). FastMCP concrete/template resource dispatch explicitly re-raises MCPError (server.py:1659,1718). `fastmcp.exceptions.to_mcp_error` returns an existing MCPError unchanged (:136-137), so existing `EnvelopeLimit.on_read_resource` can admit complete ErrorData including domain data, then re-raise it. ResourceError has only message and is translated without the DTO. Modern MCP runner preserves recognized MCPError ErrorData, and legacy dispatcher likewise uses its error; do not wrap it in ResourceError.

**Unexpected exceptions:** build the fixed owned unavailable/corrupt fallback according to Rust classification/transport context rather than exposing `str(exc)` or credentials. Native PyO3 exception may have a payload attribute or a dedicated typed DTO accessor; catch the distinct type and validate payload shape, never infer kind from its displayed message. Python admission/closed/deadline failures need model-owned fixed mapping too, since they arise before native execute. Invalid public request fields and resource key validation should retain the declared failure classification. Final-envelope byte refusal must use the same safe route when it fits, with one minimal fallback and no recursive encoding. Do not catch cancellation as a generic failure.

Meaningful implementation checks: actual native-to-MCP tool recognized causes retain isError/_meta; actual resource read yields JSONRPCError/ErrorData.data; unexpected diagnostics become fixed safe messages; oversized error metadata refuses before emission; request cancellation still drains owned workers. Source feasibility **passed** as inspection only; these runtime controls **not_run**.
