### Observations from the synthetic runs (2026-10-05, qualitative; no timing)

**Sharing ratio.** Row versions shared between A and B: 606,691 of 612,137 B rows (99.1%).
Union stored under M1: 617,410 content rows against 1,224,101 rows for two full copies.
- **PG physical size**, tables plus indexes (`raw/pg_sizes_synthetic_v*.txt`):
  - v1, integer columns: the two full copies `g_a` + `g_b` are 154 MB; M1 is 87 MB of content
    plus **252 MB of membership**; M2 is 104 MB.
  - v2, bigint columns: 168 MB for the copies; M1 is 92 + 297 MB; M2 is 110 MB.
  - Those membership figures include dead tuples from the snapshot-3 integrity test. After
    `VACUUM FULL` the membership is **151 MB** for 1,224,101 rows. M1 is therefore 92 + 151 =
    243 MB against 168 MB for two full copies.
- For narrow, id-dominated rows, which describes this model's relations, per-snapshot membership
  rows cost as much as the content they share. **Explicit-membership M1 does not save storage**
  in PG; validity intervals (M2) do, but require a linear history.
- A compact membership (a dense surrogate per content version plus a bitmap per snapshot and
  relation) would be needed. That is Proposed and untested.
- **Dolt:** storage grew by 40.7% of A for B after `dolt_gc` (v1: 40.1%), with no change hints
  (full delete and reinsert). Prolly-tree chunk sharing is real but coarse: about 1% row churn
  spread across all tables rewrote about 40% of the chunks.
- **TerminusDB:** the storage volume was 85 MB after A, B and the diff (v1).

**Correctness traps found.**
- **Shared content must be keyed by (id, payload digest), not id.** The model allows the same id
  with a different non-key payload across states (provider-symbol `name`/`kind`, evidence detail).
  SurrealDB `INSERT IGNORE` keyed on id alone silently keeps the stale payload. Plain `INSERT` of a
  batch containing one existing id fails the whole statement.
- **Referential integrity inside a snapshot is not a store FK under sharing.** A FK over shared
  content proves "exists in some snapshot". In PG and in SurrealDB the snapshot-scoped check is a
  membership anti-join / `record::exists(type::record('member', [s, rel, ref]))`. With one
  referenced occurrence or source removed, both harnesses found the dangling referrers (3 and 301)
  where a FK would not.
- A SurrealDB record link from shared content to a content *version* is ambiguous across
  snapshots; links have to target the identity and resolve through membership.
- **Dolt FK/CHECK.** Enforced on statements (1452, CHECK 1105). With `FOREIGN_KEY_CHECKS=0`
  (the documented bulk-import mode) a dangling row is accepted **and `DOLT_COMMIT` commits it into
  history**. `DOLT_VERIFY_CONSTRAINTS('--all')` then finds it, but needs
  `@@dolt_force_transaction_commit=1` to record it (otherwise error 1105 rolls the call back)
  (`raw/dolt_fk_commit.txt`). A Dolt-based loader therefore has to keep FK checks on (parents-first
  order, which worked for 612k rows) or verify before committing.
- **TerminusDB.** Typed links are enforced: a dangling link is refused with
  `SchemaCheckFailure / references_untyped_object`. A `PUT` with `full_replace` kept A-only
  documents, so B must be a `POST … full_replace=true`.
- **SurrealDB.** SCHEMAFULL types and `ASSERT` are enforced; plain string reference fields are
  not. With the namespace undefined, the first statement of a request failed while later
  statements in the same request ran. `set::difference` is symmetric (A3b); `array::complement`
  is directional and was used.

**Feasibility (qualitative).** Everything completed. Server memory, from `docker stats` after the
runs:
- SurrealDB: 3.4 GiB (v1, uncapped) and 6.6 GiB (v2, under the 8 GiB cap), holding 617k content
  records, 1.22M membership records and the M2 fields. A real-scale run (about 10x) needs a
  deliberately larger cap.
- Dolt: 0.5 to 1.2 GiB.
- TerminusDB: peaked at 1.7 GiB while loading two 612k-document states and fell back to 1.0 GiB
  after the diff.
- PG: the shared local cluster.

### Probe 3: quantifier scope of the 119 checks

| Class | Count | Shape seen in source | Delta-checkable? | What would make it incremental |
|---|---|---|---|---|
| R: streaming forward reference or row predicate | 21 | Target relation loaded into a `ChargedMap`; each referrer checked in `visit`; `finish` empty. Examples: `occurrence_source_bounds`, `call_target_ownership`, `declaration_links` | **Yes, forward.** New rows probe the new snapshot's target index | **Reverse:** a removed or replaced target needs a referrer (reverse) index to prove nothing dangles. Content keys help: a changed source artifact gets a new id, and so do its occurrences |
| K: key-local group (the parent carries a digest of its children) | 16 | Children ordered by parent key, `flush` per parent, and `finish` asserts no parent was left without its children. Examples: `artifact_chunk_content`, `call_origin_membership`, `input_manifest_membership`, `callable_parameter_membership`, `literal_set_membership` | **Yes, per parent key.** Recheck only parents that are new or whose children changed | A children-by-parent index in the snapshot. Note: `input_manifest_membership` is key-local, not global as Phase A3b listed it |
| F: multi-hop forward closure in `finish` | 20 | Several relations indexed in memory; for each row, its referenced closure must exist and agree. Includes per-group cardinality (`subject_boundaries`) and transitive parent chains (`document_structure`, `invoked_guard_origins`). Examples: `complete_signature_membership`, `export_enumeration_membership`, `structural_type_shapes` | **Mostly yes, per row**, if every hop has a forward index plus a reverse index for deletions; transitive chains need the affected ancestors or descendants | Reverse indexes per hop; ancestor and descendant expansion for the transitive ones |
| G: global or closed-world | 11 | Reverse completeness (`canonical_condition_catalog`: no unreferenced node), whole-graph property (`derivation_acyclic`), orphan sweeps (`flow_use_inventory_replay`), and the 8 publication checks that compare counts and profiles of runs against invocations | **No** in general. The count and profile checks are cheap; acyclicity and unreferenced-node checks need a global pass or maintained reference counts | Reference counts (or a reverse index) for "no unreferenced"; incremental cycle detection for the derivation graph |
| D: derivation replay (`output == f(inputs)`) | 51 | `finish` recomputes the owning stage from all its declared inputs and requires exact equality (`self.output.matches(&normalize(&self.data, …))`, `build(…)`, `verify(…)`). Covers all of normalized, catalog, evidence, retrieval, selection, synthesis, execution, local semantics/theory/fields, conditions entry/stability, analytics, structural and projection frames, and the analysis families | **No.** Cost equals rerunning the stage. Several replays already loop `for invocation in self.invocations` (atom decision, local_*, seeds, execution), so they have a natural partition | Partitioned derivation (per invocation, module or source) with memoised partition results, keyed by (definition digest, partition-input digest): incremental view maintenance, or salsa-style memoisation of the stage function. This is model and validator work in any store |

Store-level checks outside `Invariant` (unique keys, reference completeness and subtype in
`memory.rs`) are R/K-like. The relation content digest (`RelationContent`/`hash_rows` in `model.rs`)
is a sequential hash over strictly increasing ids, so it cannot be updated from a delta. A
multiset/additive digest or a Merkle tree over sorted ids would make it O(Δ).

**Reading.** About 48% of checks (R+K+F, 57/119) can be checked over a delta once reverse indexes
exist. The other 52% (D+G, 62/119) are closed-world. The 51 replays dominate: they re-derive whole
stages, so the stage computations set the validation cost. A structurally shared snapshot alone
therefore removes copy and storage cost but not most validation cost. That cost falls only with
partitioned and memoised derivation, and no candidate store provides that.

### Probe 2: cross-version correspondence keys (static)

From the declarations (`source.rs`, `calls.rs`, `normalized/entities.rs`, `symbols.rs`,
`declarations.rs`):
- `SourceArtifact` key = (input revision, path, **content hash**). `Occurrence` key = (source, start,
  end, syntax kind, role, structural path). Any byte change in a file therefore changes that file's
  source id and every occurrence in it. An edit also shifts the spans of everything after it.
  In a new input revision every source id changes.
- `CallableEntity::Source`, `ClassEntity::Source` and `ParameterEntity::Source` are keyed by
  `declaration: Id<Occurrence>`. Their identity is "a definition at this span of this content". It
  is not a semantic key and cannot correspond across versions.
- `Module` key = (source, `qualified_name`). `qualified_name` is the only declared qualified-name
  field on an entity. It is not unique: `.py` and `.pyi` both carry it (§15.3 keeps them distinct),
  so the candidate key is (qualified_name, stub flag).
- `ProviderSymbol` key = (provider, context, provider module, `native_key`). The static reading
  took `native_key` to be close to a qualified name. **The real data refutes that: it is a
  positional index** (see "Probe 2 on real data"). Provider and context ids
  change with the pinned provider and the input. The model explicitly refuses cross-provider
  spelling joins ("never a spelling join", `calls.rs`). `Synthetic` and `External` entities are
  keyed by a `ProviderSymbol`.
- `PublicExposure` / `PublicNameObservation` give (access module, public `name`). Through the module's
  `qualified_name`, that is the best existing *derived* key for public-API diff ("`pkg.mod.name`").
  It needs no new declaration.
- Parameters: `NativeSlot` goes through `SignatureParameter`. A derived key would be (callable
  correspondence key, parameter name) and ordinal or kind.

**Conclusion (static, Proposed).** A semantic diff requires a declared correspondence key:
- for callables and classes, a derived qualified path or the public path. The originally listed
  `native_key` is refuted by the real data;
- (callable key, name) for parameters.

The real `Signature` key includes its `parameters` digest (`calls.rs` l.296-312). A changed
parameter list is therefore a removed and an added signature at the identity level. Only a
correspondence key shows it as "changed"; the synthetic v2 runs reproduce this in all four stores.

Its uniqueness and stability are unverified. Overloads, conditional redefinitions, property
accessors and the `.py`/`.pyi` pairs are the expected collision cases. Once the key exists, every
store reduces semantic diff to a keyed full outer join over two snapshots. SurrealDB has no JOIN:
it needs two keyed range reads merged in the client, or a record-link/`<~` lookup per key.

**Correction to the static reading.** `ProviderSymbol.native_key` is *not* a qualified name:
- It is the analyzer's **positional** index within a module: `0`, `1`, `2` for classes; `F:n`
  for functions and methods; `CF:class:n` for class fields. For example, in
  `fastmcp.server.server`, `F:12` is `name` and `CF:2:59` is `_lifespan`.
- Inserting a definition earlier in a file renumbers everything after it, so `native_key` is
  **unstable across versions by construction** and unusable as a correspondence key.
- Provider symbols appear once per analysis context (2 contexts here).
- Only 15,945 of the 29,257 symbols have a source declaration.

**Conclusion (Tested on one generation, 2026-10-05).** In the facts layer the only workable
correspondence keys are derived:
- the qualified path from syntax containment: unique for classes, unique for callables except
  redefinitions, which need a declared disambiguator such as the definition ordinal among
  same-name siblings;
- the public path (module `qualified_name`, name).

Both are model work: a declared, derived correspondence relation. Stability across library
versions is `not_run`, because a second FastMCP version would have to be compiled.

1. **SurrealDB `INSERT IGNORE` silently drops rows that violate field types** (a NONE in a
   non-`option` field, a string in an int field). The statement returns OK and nothing is
   reported (`raw/surreal_insert_ignore_probe.txt`). In the first attempt this lost all of
   `ruff_context_observations` and `provider_modules`, and part of three other relations.
   - Membership still loaded, so **the membership-only identity diff "passed" over missing
     content**. A snapshot store needs a content-completeness check against membership.
   - Plain `INSERT` fails the whole batch atomically instead.
2. **SurrealDB refused a 3.5M-row single-statement snapshot copy**
   (`INSERT INTO member (SELECT … FROM member:[2,..])`) with
   `Commit failed: Memtable arena is full` on SurrealKV (`raw/surreal_real_attempt1.txt`). Large
   writes must be batched.
3. **SurrealDB `/sql` rejects bodies over 1 MiB by default** (HTTP 413;
   `SURREAL_HTTP_MAX_SQL_BODY_SIZE`, `surrealdb/server/src/cnf/mod.rs` at v3.3.0).
4. **TerminusDB** rejected NULL integer fields until they were declared `Optional`.
5. My own export bugs, fixed: an edited file with no occurrences, added rows that were key-identical
   copies, and type-invalid key perturbations. A type check now guards the export.
