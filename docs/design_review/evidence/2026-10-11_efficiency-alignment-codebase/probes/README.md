# Light probes

These probes are part of the [efficiency-alignment review evidence](../README.md). Each is
read-only: no build, service, fixture, SurrealDB query or `just` recipe. All ran on 2026-10-11 on
the shared host:
- 32 logical CPUs with SHA-NI;
- about 188 GiB RAM, warm page cache;
- load average about 6 from other sessions' work;
- `python3 -I` (CPython 3.14.7).

| Probe | Question | Result | Strength and limits |
|---|---|---|---|
| [P1](p1_executable_sha256.py) ([output](p1_executable_sha256.txt)) | How long does one full SHA-256 pass take over the installed 368.7 MB SurrealDB server executable? The fixture tooling computes the same digest with `scripts/storage_service.py::digest` (`hashlib.file_digest`). | 0.155–0.161 s per pass, 5 passes, warm cache | **Measured** for that file under these conditions. It does not establish how many passes a boundary performs or any end-to-end boundary time. |
| [P2](p2_storage_records.py) ([output](p2_storage_records.txt)) | How large is the storage-lifecycle object registry, and what does a glob plus JSON parse of every object cost (mirroring `Storage.records` without validation or locks)? | 700 objects (635 KB); 695 paths, 683 scopes, 1,241 admission lock files; 5.7–6.8 ms per full parse | **Measured** at the current registry size. Lock acquisition, fsync and validation are excluded. Growth is linear in retained objects. |
| [P3](p3_run_summaries.py) ([output](p3_run_summaries.txt)) | In the existing `build/runs/*/summary.json` records from 2026-10-08 to 2026-10-11, how much boundary wall time do the steps not account for? That time covers readiness, fixture attachment and release, evidence capture and cleanup. | Fixture-backed boundaries: median 1.1–2.8 s unaccounted, max 5.1 s. The steps themselves take minutes; for example the `store:rust` nextest step has a median of 273 s. | **Historical receipts** across mixed revisions, loads and cache states. They are not fresh runs and attribute no cost to a mechanism. |
| [P4](p4_junit_times.py) ([output](p4_junit_times.txt)) | Within steps that have an ADR-0147 JUnit capture, how much time is test execution and how much is outside it (build, list, setup)? Which tests are slowest? | Only 3 invocations had JUnit, all from run `20261011T071240`:<br>• `model:rust`: step 128.6 s, JUnit suite 2.7 s, 809 tests;<br>• `analytics:rust`: step 6.8 s, suite 0.1 s;<br>• `providers:extract`: step 632.6 s, suite 280.8 s, 76 tests whose summed test time is 8,984 s. About 28 `cpg-extract::extraction_calls` tests each took about 280 s, and 4 acquisition tests took 59–157 s. | **Historical receipt** from one run with unknown cache state. It cannot distinguish compilation from test listing. **Correction, after inquiry F2 and coordinator check V03:** the run's `termination` is `interrupted`, and `providers:extract` is `not_run: interrupted`. In that step's `junit.xml`, 32 cases are `process aborted with signal 15`. So the uniform ~280 s durations mark the cancellation instant. They are not completed per-test work. The original hypothesis, repeated per-process `OnceLock` preparation (`crates/cpg-extract/tests/typed_driver/mod.rs::fixture_model`), is unsupported by this data and is withdrawn. The data still shows that at least 32 tests were each in flight for at least 280 s. |
| [P5](../README.md#coordinator-checks) | Inquiry L1's proposed probes (read-only). Is there any KNN or HNSW consumer? Do conflict errors appear in run logs? Is `parquet` reachable only through DataFusion's feature? | KNN: one consumer, `scripts/programmatic_native.py` (`vector::distance::knn()` with `<|k,128|>`, an evaluation worker check), and none in serving or compile. Conflicts: only deliberate conflict controls in `20261008T225907…/store-rust.log`. Parquet: reached only through `datafusion feature "parquet"`, and brotli only through parquet (`cargo tree --offline`). | Static or read-only. Retries are silent, so the absence of conflict text proves nothing about contention. |
| [P8](p8_phase_receipts.py) ([output](p8_phase_receipts.txt)) | Which `lctx_phase` phases dominate in existing run logs? | The recent catalog-profile fixture native journeys are single tests on small fixture libraries, 2026-10-11 runs `090609…6c0bdc` and `095410…4cb00b`:<br>• `artifact_admission` 109–162 s;<br>• `artifact_manifest` 65–89 s;<br>• `native_batch_write` 67–76 s summed over 548–596 calls;<br>• `publication_seal` 63 s;<br>• `native_content_freeze` 34–38 s;<br>• the nine unrequested behavioural phases sum to 32–33 s, against 33–81 s for the five catalog product stages.<br>Earlier runs (2026-10-09) show `normalized_admission` and `artifact_invariant_admission` at 750–870 s, and normalization stages at 230–1,030 s. | **Historical receipts** across mixed revisions, fixtures and host load. Phases nest, so their sums are not additive. They show which phases can dominate small-fixture journeys and attribute nothing to a mechanism. |
| P6 | (Inquiry H, P-H1.) Has a streamed query hit the server's 20 s query timeout? Command: `journalctl --user -u library-context-surrealdb.service --since 2026-10-08`. | The retained journal starts at 2026-10-09 21:00 and has 420 lines. It contains one `Streaming query did not stop within the grace period after its timeout … timeout=20s` (2026-10-10T02:34:23Z), plus one unrelated RocksDB compaction-drain timeout. | Read-only. This is weak support for H-02: a stream reached the deadline at least once. No call site is attributed, and the journal window is short. |
| [P7](p7_json_byte_array_expansion.txt) | (Inquiry C, LP-C1.) How much does serde_json's integer-array encoding expand a representative byte string? | 6,420 bytes become 21,222, ×3.31 (one run `summary.json` used as the sample). | **Measured** for that sample. The ratio depends on the byte distribution. |
