# SurrealDB lifecycle, integration and development target review

**Principal independent design/target review · 2026-10-12 · Revise.**

The best fit remains a Rust-owned, version-pinned API and evidence catalog with SurrealDB supplying shared immutable persistence, transactional ownership, indexed connected access and search. The existing separation between content, completion, semantic admission, publication, selection and reader lifetime is valuable. Replacing it with a generic scratch/permanent flag, database history, automatic cascades or a database event queue would discard consequential guarantees. Conversely, adopting one database platform does not require putting host process ownership, executable installation, raw test captures and every temporary buffer into the canonical database.

The enclosing implementation needs revision. A reachable serving path still interprets physical membership using the removed logical-view field, despite the native selector having moved to exact realizations. Independent physical auditing also introduces scalar network crossings and repeated whole-original scans; normal equal-content completion can spuriously reject a concurrent successful peer. These are concrete source findings, distinct from the unresolved qualification campaigns. Durable completion receipts preserve safety-relevant outcome axes, but flatten typed failure causes needed for agent-assisted recovery.

The recommended target corrects those boundaries, preserves native ownership and adds **SurrealKit 1.0.0-beta.1**, including its Rust library integration, as a schema and database-contract development capability. The operator selected that beta target during this review; 0.7 is background, not a competing recommendation. Beta status itself is no objection. Its actual targeting and cleanup behavior must shape integration rather than being assumed equivalent to the repository's lifecycle owner.

## The model worth preserving

| Owner | Meaning and responsibility | Consumer boundary and reason for change |
|---|---|---|
| lctx-model | Typed facts, identity, qualification, coverage, exact completed descriptors, recovery closure and effect-free completion outcomes | New phenomena or changed semantic contracts belong here; physical table names and host process mechanics do not |
| cpg-core and providers | Pinned observation and requested compiler frontiers | Analyzer changes remain provider-owned; orchestration supplies declared completed inputs |
| lctx-compiler-store | Exact contributions/views, current semantic admission and privately constructed admitted/export/restored capabilities | Consumers receive earned capabilities, not deserialized assertions of eligibility |
| lctx-native | Physical codecs, selected realization membership, originals, transport finality, effects, holds, incarnations and bounded retirement | Engine/schema/transport changes belong here and must preserve model meaning |
| lctx-publisher | Manifest sealing, executable epochs, logical backup and independent restore composition | Publication consumes semantic admission; it does not select an operator snapshot |
| lctx-serving | Model-owned operation selection, evidence hydration and bounded presentation | It should consume protected native selection rather than reconstruct its storage interpretation |
| Host service, fixture and storage owners | Executable and process identity, maintenance admission, attachment receipts, evidence retention and host-file disposal | They coordinate external lifetimes and consume native outcomes; they do not infer database disposal from a dead process |

This is a useful dependency direction, not a certificate of every consumer. [ContributionSpec and CompletedView](../../../crates/lctx-model/src/domain/completed.rs), lines 47–157, distinguish producer/profile/model/implementation/configuration and ordered input roles from view membership and count. Count is metadata rather than proof of exact membership. [RecoveryTraversal](../../../crates/lctx-model/src/domain/recovery_closure.rs), lines 43–126, checks exact descriptors, complete contributor inventories and dependency views, including empty outputs. Neither structure grants semantic admission.

Physical and logical identity are deliberately separate. An installed view records the selected contributor copies and their incarnations; the realization owns immutable member rows, while an epoch-qualified completion witnesses their valid installation. [Installed member schema](../../../crates/lctx-native/src/installed_view.rs), lines 181–190, is the relevant current physical authority. A logical view hash cannot choose an arbitrary physical copy, and a matching content hash cannot replace current ownership or producer eligibility.

The fidelity distinctions carried through this scope are:

| Family | Attribution/fidelity and uncertainty | Identity and consumers |
|---|---|---|
| Provider observations | Pinned provider and constructed configuration; extracted or provider-inferred facts retain coverage and disagreement | Typed facts and source spans feed normalization and admission |
| Public catalog/configuration | Model-owned normalized/derived interpretation; declared, effective and unresolved forms remain distinct | Public member, exposure and signature identities feed exact selection |
| Original documents and usage evidence | Captured authored bytes and explicit associations; a mention does not become behavioral proof | Source/layout/blob/chunk identities feed evidence windows and derivation packets |
| Search and analytical values | Declared encoder/projection/ranking specifications; heuristic nomination remains distinct from eligibility and truth | Derived realization and actual value dependencies feed ranking, followed by evidence hydration |
| Completion/admission/publication | Physical completeness, current semantic eligibility and committed visibility are different claims | Attempt/product/view/publication handles feed publisher, serving and recovery |

The review does not requalify Python semantic analysis or evaluation. The lifecycle must preserve those distinctions, and no examined proposal requires widening the behavioral model.

## A lifecycle taxonomy with independent axes

The [simulation white paper](../../white_paper_on_surreal_db_in_simulation_state_management.md)'s central distinction transfers: execution lifecycle and retention lifecycle are independent. Its scenario/checkpoint vocabulary does not transfer literally. In this product, the useful objects are acquisition input, execution attempt, pending contribution, completed contribution, exact view, admitted artifact, publication, selected binding, reader pin, reusable product, backup, operation outcome, native recovery obligation and host attachment. The [code-intelligence white paper](../../surrealdb_white_paper_code_intelligence.md)'s unified graph/search platform is useful where it reduces movement; its proposed features must still satisfy this product's exact selected scope, attribution and failure contracts.

Classify each by **authority, mutability, visibility, semantic eligibility, retention consumer, liveness/uncertainty and recovery obligation**. These are independent axes, not one universal status enum. A completed contribution can be retained but currently ineligible; a publication can be unselected but pinned; an abandoned attempt can still own unresolved effects; a successfully exited test can retain failed native cleanup. A reference baseline can be immutable yet explicitly retired later. An expiry timestamp only makes something a candidate for policy evaluation.

Existing code already captures much of this. [Completion](../../../crates/lctx-model/src/domain/completion.rs), lines 41–130, separately carries local terminality, remote certainty, storage outcomes, committed effects and finalization failures. [Attempt closure](../../../crates/lctx-native/src/control.rs), lines 515–584, fences writes, establishes durable cleanup work and preserves independently retained product roots. [Retirement registration](../../../crates/lctx-native/src/control/retirement.rs), lines 109–159, gives exact root sets and incarnations a recoverable identity before destructive advancement. These protections should survive any simplification.

The target should make these distinctions easy to inspect through existing owner interfaces. It does not need a new global ontology, universal lifecycle registry or second scheduler. Add a type or structured projection only where an actual consumer must decide, reconcile or explain an operation. Local disposable buffers need normal scoped ownership; not every temporary calculation needs a durable attempt or checkpoint.

“Promote references, not payloads” is appropriate for admitted immutable content. The [publication workflow](../../../crates/lctx-publisher/src/native_publication.rs), lines 18–101 and 143 onward, consumes private admission owners and constructs a manifest over exact bindings. It can reuse unchanged publications while retaining current executable identity. Promotion must not turn a physically complete capture into semantic eligibility simply because its retention class changed.

## Cross-owner effects, visibility and recovery

There is no distributed transaction spanning the database, filesystem selection, systemd process and backup file. The appropriate contract is an owned, resumable composition with each authority acknowledging its effects. Removing these distinctions in favor of “one canonical SurrealDB platform” would hide the actual failure domains.

[Runtime selection](../../../crates/lctx-native/src/config.rs), lines 131–211 and subsequent commit methods, serializes lifecycle changes with a file lock and durable pointer publication. Publication and selection are separate. The lock is local selection authority; it is not a replacement for database reader pins or an invitation to coordinate every operation through the selection file.

[Native request issuance](../../../crates/lctx-native/src/control/authorization.rs), lines 45–79, captures the installation era before assigning the operation identity. [Control coordination](../../../crates/lctx-native/src/control/coordination.rs), lines 6–30 and 215–219, uses admission stripes and explicit drainage predicates. Object guards, incarnations and native holds protect concurrent creation, retention and retirement; ordinary predicate reads do not provide the same exclusion. Child nomination before hold removal preserves recoverable cleanup scope. These are concrete obligations beyond generic transaction support.

[Host borrowing](../../../scripts/surrealdb_service.py), lines 939–975, establishes admission and lifetime borrower protection before executable/admin proof. Maintenance, lines 989–1098, closes admission, drains borrowers and native scope, and preserves a maintenance marker on interruption. [Fixture release](../../../scripts/surrealdb_fixture.py), lines 875–900, separately considers command cleanup and native completion before marking the attachment released. [Local attachment recovery](../../../scripts/surrealdb_fixture.py), lines 1204–1237, cannot infer native completion from process cessation. [Executable storage](../../../scripts/storage_service.py), lines 1–5, explicitly excludes database payload authority.

These seams are strengths. Their static inspection does not prove every public low-level native entrypoint registers with the host receipt mechanism, nor every interruption interleaving. Named production owners do register durable started receipts before native work, and dropping them leaves uncertainty rather than success. The review found no basis for claiming that ordinary process failure silently erases native obligations.

[Selected backup](../../../crates/lctx-publisher/src/backup.rs), lines 13–92, retains the publication pin, uses a dedicated exact exporter session and one external transaction, explicitly cancels and invalidates that session, and publishes staged bytes only after finalization. The logical export is independent of a whole-service cold recovery archive. [Recovery metadata](../../../crates/lctx-publisher/src/backup.rs), lines 95–147, explicitly preserves that distinction. Replacing this with a generic CLI export would require equivalent selected closure, coherent snapshot and finality contracts; an available export command alone does not supply them.

## Findings requiring revision

<a id="F01"></a>
### F01 — Serving reconstructs a retired membership namespace

**Priority: highest product correctness. Owners: lctx-serving selection/evidence and lctx-native protected selection. Principles: FP-02/03/04/06, DP-08/17/24, CI-05/13; A1–A3 and G6/G7.**

[Serving members](../../../crates/lctx-serving/src/selection.rs), lines 179–205, binds NativeReader::view_bindings. The [bindings](../../../crates/lctx-native/src/reader.rs), lines 805–818, contain logical compiler_view record IDs. Serving selection lines 260–267 and 370–371 then query compiler_view_member using a field named view. The current SCHEMAFULL [physical member schema](../../../crates/lctx-native/src/installed_view.rs), line 190, has realization, relation, semantic_key, node and content, with indexes keyed by realization. It has no view field. This is reachable from [operation choice](../../../crates/lctx-serving/src/operations.rs), lines 80–89, and operation/get/search/compare paths. [Evidence derivations](../../../crates/lctx-serving/src/evidence.rs), lines 529–538, repeat the incompatible subqueries.

The mismatch establishes that those queries cannot express the current selected member namespace. No fresh database probe establishes whether a particular call returns empty or refuses; this review does not infer a false absence response, cross-snapshot citation or corrupted evidence from the static mismatch. The correction is nevertheless mandatory for the supported retrieval journey.

Consume a protected exact-realization selection operation owned by lctx-native, including selected contributor-held aliases where required. Serving supplies library/member/path or evidence intent and receives scoped candidates or rows. It stops interpreting logical view IDs as physical membership. Do not add a legacy view column, global logical-copy fallback or compatibility reader.

A legitimate counterexample constrains the remedy: two equivalent logical contributions may have distinct physical copies, and an alias may be owned only by a selected contributor. Selecting by logical hash alone or traversing every alias in the database would reintroduce the problem. Closure requires all reachable member and derivation consumers to use exact protected namespace bindings, plus a minimal actual native journey with populated members, a foreign same-nominal copy and selected aliases. The existing correct [SelectedPayloads preparation](../../../crates/lctx-native/src/selection.rs), lines 259–347, is the preservation baseline, not evidence that the later serving bypass is already fixed.

<a id="F02"></a>
### F02 — Independent membership auditing crosses the server per record

**Priority: high execution fit. Owners: installed-view audit and native batch access. Principles: FP-07, DP-10/14/20; A4.**

[audit_memberships](../../../crates/lctx-native/src/installed_view/audit.rs), lines 148–190, iterates selected mappings, issues an ordered LIMIT 1 query for each membership, fetches backing and its guard, checks its hold and audits its payload. [Endpoint auditing](../../../crates/lctx-native/src/installed_view/audit.rs), lines 225–230, performs further item-specific reads and hold checks. The normal [compiler installation caller](../../../crates/lctx-compiler-store/src/compiler.rs), lines 1210–1233, reaches this audit while constructing exact predecessor views.

Complete output auditing, including unrelated outputs and explicit empty outputs, is necessary. Serial network granularity is not. As a pinned library grows, every fact and endpoint adds crossings even when the final demand is compact. Bounded memory and correct EOF checking do not establish a suitable execution route for this avoidable amplification. No timeout attribution or numerical speed claim is needed.

Preserve the independent observer while reading indexed membership windows, fetching backing/guards/holds in keyed batches and validating exact correspondence under one charged window. Established SurrealDB set queries and existing native batch/terminal ownership are suitable mechanisms; a new generic query engine is unnecessary. Preserve ordering, duplicate detection, undeclared-output rejection, exact counts/digests and all final owner comparisons. A batch that internally performs scalar RPCs does not close the finding.

The revealing legitimate case is a large payload or high-degree assertion that cannot fit the nominal row window. Admission must charge actual bytes and partition safely, not silently skip its endpoints or impose test concurrency caps. Closure requires source showing bounded set-oriented crossings and a minimal multibatch control with missing/duplicate/foreign backing and late terminal error. The amount of latency removed remains unmeasured.

<a id="F03"></a>
### F03 — Original and view audits repeatedly reconstruct unchanged completeness

**Priority: high execution fit. Owners: originals, installed-view completion and compiler preparation. Principles: FP-07, DP-09/10/19, heuristics H12/H18–20; A4.**

[audit_original](../../../crates/lctx-native/src/installed_view/audit.rs), lines 234–250, verifies a typed chunk's range digest and then calls validate_blob over its entire backing original. [validate_blob](../../../crates/lctx-native/src/originals.rs), lines 169–186, reads every physical piece to EOF and recomputes the whole hash. Because audit_backing invokes this for each original chunk, a multi-chunk original can be fully re-read repeatedly within one protected audit. Equal-content layouts can repeat the same work as well.

Additionally, [install_live_view](../../../crates/lctx-native/src/installed_view/live.rs), lines 29–40, audits the complete dependency closure, memberships, aliases and logical roots, then constructs root members before examining the already-sealed realization branch. Distinct roots can overlap heavily. This does not mean every reader lookup performs the full audit: the [compiler's installed_views cache](../../../crates/lctx-compiler-store/src/compiler.rs), lines 1181–1205, reuses already-held identical views. The concern is first construction, overlapping roots and reconstructed/cold owners.

The minimum correction is operation-scoped deduplication of full blob verification by exact blob identity and protected incarnation, with each typed range and layout still checked. This removes demonstrably repeated work without trusting producer hashes. A further proposed direction carries independently established physical completeness across operations while its exact ownership, generation, validity epoch and immutable membership premises remain true. Current semantic eligibility remains a separate check. Cold import, changed definitions, uncertain ownership or changed incarnation must re-establish the affected properties.

Do not close this by skipping readback or treating a completed flag as a universal certificate. A legitimate same-content original may have a different source identity and layout; both source associations must survive while bytes are shared. Closure requires one full blob observation per protected audit scope, exact range checks, and a traced reuse route that states what invalidates it. Corrupt/missing pieces and an ABA reincarnation must still refuse. Broader retained-witness design remains Proposed until its mutation coverage is specified and independently checked.

<a id="F04"></a>
### F04 — Durable finalization diagnostics discard typed recovery causality

**Priority: medium, with higher leverage during interrupted maintenance. Owners: model diagnostic projection and native signal receipts. Principles: FP-05/06, DP-21; diagnostic MUST gap.**

[NativeRequestError, NativeAttemptError and NativeLifecycleError](../../../crates/lctx-native/src/control/authorization.rs), lines 10–38, carry typed operation/attempt/lifecycle identity, issuance generation and era. [Receipt::finish](../../../crates/lctx-native/src/signal.rs), lines 159–171, serializes finalization failures as step plus error.to_string(). A persisted consumer therefore cannot recover those typed cause fields without interpreting human prose.

This is a narrow finding. Local/remote outcome axes, committed identities and storage outcomes remain structured, and [fixture classification](../../../scripts/surrealdb_fixture.py), lines 209–247, conservatively protects failed/unknown completion. The finding does not establish unsafe deletion or erase the in-process typed errors.

Add an owned diagnostic projection retaining stable failure class/code, stage, relevant native identity and issuance, recursively bounded secondary causes, and a safe remediation route where known. Human messages remain presentation. Unknown third-party causes need an explicit opaque classification rather than guessed fields. Consumers should be able to name the actual recovery obligation without parsing error text, while the original error and protected receipt remain available.

A legitimate case is a failure before an attempt or request exists: the schema must permit absent native identity without inventing one. Closure is a persisted failure example round-tripped through the actual receipt reader, retaining typed request information and independent committed/cleanup outcomes, plus opaque pre-admission failure. This needs no new recovery service or mandatory tracing stack.

<a id="F05"></a>
### F05 — Equal concurrent blob completion encounters an unrecovered audit conflict

**Priority: high correctness of supported concurrency. Owners: original completion and native retry composition. Principles: FP-02/04/07, DP-08/19/20; A2/A4.**

Two valid callers can capture the same active blob incarnation/revision in [complete_blob](../../../crates/lctx-native/src/originals.rs), lines 194–207, and independently verify the same bytes. The first final effect sets completed=true and increments the guard revision. The second final effect, line 212, rejects revision inequality before considering that the exact blob is now validly completed. Callers at lines 221 and 650 propagate the error. The [transaction retry classifier](../../../crates/lctx-native/src/control.rs), lines 65–86, retries native transaction conflicts, not this application THROW. No enclosing recapture loop was found in those callers.

The counterexample proves a legitimate peer completion can fail; it does not prove corruption or an unsafe commit. Incoming hold changes update native_predicate through native_touch, a distinct table, so this review does not attribute all hold churn to the blob guard. The narrow equal-peer interleaving is sufficient.

Completion should converge on the same independently valid immutable content, or recapture and re-audit under an owned retry policy when its premise changed. Do not accept arbitrary revision differences: retirement, recreation, changed chunk membership or another mutation could invalidate the earlier audit. A Proposed exact chunk-set/completion witness must govern those differences; merely moving the completed check before the guard check is insufficient.

Closure requires actual equal concurrent completion, same-content distinct layouts, invalid chunk mutation/retirement/ABA refusal, and canceled-waiter ownership. Preserve normal available parallelism. Globally serializing compiles, weakening readback or capping test workers would hide the defect. F03's deduplication may reduce exposure but cannot establish this concurrency contract.

## Native capabilities and the complete alternatives

SurrealDB remains technically suitable for the examined product if the adapter uses its complete indexed/bulk capability. It provides one physical transaction domain for content and ownership, attributed graph relations, lexical/vector nomination and selective evidence access. Rust owns interpretation. Native execution can reduce movement without acquiring semantic authority.

The [physical graph schema](../../../crates/lctx-native/src/schema.rs), lines 171–183, already preserves nominal anchors, full payloads, attributed relation roles, position and derivation. Lightweight relations are unsuitable for those attributed facts because existence alone is not their meaning. They may suit a separately rebuildable property-free adjacency projection, if a real consumer benefits. Inline adjacency, count indexes and extra materialized views likewise need workload-specific justification: high-degree hubs can turn a read convenience into write and retention amplification. A new semantic family should not automatically create a table, execution stage and maintenance job.

Lexical analyzer improvements and native vector/hybrid operations are eligible lowerings under one declared retrieval specification. Ranking must follow eligibility and preserve winning evidence and exact encoder/projection identity. ISO GQL is a genuine query-access option in the pinned engine, not a parser-only placeholder, but it does not automatically replace model-owned scope, multiplicity, qualified facts or bounded program-analysis kernels. Adopt it where a complete operation is simpler; keep the existing semantic contract as the comparison criterion.

Native record references can express sequential deletion protection. The inspected [reference documentation](https://surrealdb.com/docs/reference/query-language/language-primitives/record-references) establishes REJECT semantics; it does not by itself establish the concurrent reference-create/delete exclusion required by this application's incarnation/hold protocol. Supporting pinned-source research likewise leaves that substitution unqualified. Use REFERENCE for a suitable declared relation, but do not replace all native holds or add CASCADE to shared evidence without settling the actual concurrency and ownership contract. Database deletion is appropriate for an exclusively owned isolated workspace, not a shared published content graph.

[Async event documentation](https://surrealdb.com/docs/reference/query-language/statements/define/event) distinguishes atomic enqueue from later execution and repeatable delivery; its commit-conflict retry exemption begins in 3.3.1, later than this pin. Events are not elapsed-time schedulers. A notification or idempotent auxiliary update can be event-driven; canonical admission, publication finality and external process cleanup cannot depend on an assumed exactly-once callback. Changefeeds and live subscriptions can notify a worker or UI, with replay/reconciliation after gaps; they are not complete dependency keys or durable product checkpoints. Database history is useful for diagnosis but does not replace explicit immutable manifests and pinned original evidence.

The simplest retention mechanism is an explicit owner-directed bounded sweep, optionally invoked by a systemd timer after its acceptance boundary. An event bus, queue service or second canonical database is unnecessary for the present participants. Eligibility must be rechecked with protection/reference obligations at the destructive boundary. Age, logical deletion and immediate physical reclamation remain different observations.

The white paper's database-hosted APIs, Surrealism modules and file buckets are genuine mechanisms, rather than speculative platform names. Supporting pinned-source research gives them bounded dispositions: DEFINE API adds an HTTP authorization/execution boundary; a module adds executable provenance; a file bucket introduces object-store bytes and their independent retention. None currently supplies a simpler complete replacement for the Rust product operation layer or exact original/layout/blob contract. In particular, exporting bucket definitions is not backing up the referenced bytes. Revisit files for a demonstrated large-object workload only with coherent selected-byte backup, immutable identity, access and disposal contracts; revisit modules or HTTP APIs when an actual operation is simpler through that boundary. These features need no adoption framework in advance of such a consumer.

The complete storage alternatives are:

| Alternative | Merits | Total burden and decision |
|---|---|---|
| Current shared SurrealDB baseline | Unified transactions, immutable content reuse, connected retrieval and common test engine | Retain foundations; fix consumer mapping, audit amplification and completion concurrency |
| Corrected SurrealDB plus SurrealKit 1.0 beta | Same product authority; generated schema tooling, database-contract isolation and useful native access | Preferred target; tool owns reconciliation/testing mechanics, repository retains semantic and host/native lifecycle contracts |
| Simpler immutable files with a small local index | Clear artifact publication and pure component testing; few service participants | Credible for a smaller catalog-only product, but current connected exact-view queries, shared retention and native search would require substantial replacement machinery; not presently a simpler complete migration |
| Separate specialized graph/search services | Potentially useful for a demonstrated specialized workload | Adds consistency, transport, recovery and deployment surfaces without a demonstrated current need; revisit on a concrete operation that the native engine cannot realize suitably |

The preferred choice is not a claim that SurrealDB wins every storage workload. It is a judgment about this catalog's useful combination and the cost of replacing already meaningful contracts. Native functions and set operations should discharge complete bounded capabilities where possible. Bespoke code remains justified for semantic admission, exact selected ownership, remote-effect uncertainty and host processes; it is not justified merely because the same logic already exists.

## SurrealKit 1.0 beta and connection customization

Adopt the selected beta as an integrated development capability, preferably through its Rust library surface where that removes a second command/configuration interpreter. The database must not become the editable source of semantic schema. Model/native declarations generate the DDL and owned query assets consumed by SurrealKit; resulting introspection/types/reports remain derived artifacts. Schema sync and watch belong to explicitly disposable developer targets. Beta tracking/pruning can replace or remove answer-affecting definitions: unrestricted watch against the canonical database is unsuitable beneath live pins. Canonical evolution uses existing maintenance/drain ownership or a complete retained executable-epoch inventory, accounting for publication definitions, active readers, producer eligibility and recovery. Modules should follow genuine schema-management ownership and dependencies, not automatically mirror every relation or record kind.

The [testing documentation](https://surrealdb.com/docs/manage/schema-migration/testing) describes database-contract categories, retained databases and machine-readable output. These complement compiler/provider known-answer controls and actual server/transport tests. [Supporting beta-source research](../evidence/2026-10-12_surrealdb-lifecycle-target/library-contracts.md) reports that module/target options are not uniformly implemented by test/seed/type generation. The [tagged beta tester](https://raw.githubusercontent.com/surrealdb/surrealkit/v1.0.0-beta.1/crates/surrealkit/src/tester/runner.rs), lines 198–202 and 863–880, warns on cleanup errors and discards removal statement checks. Those details are integration constraints, not grounds to reject the chosen beta. The tool cannot be assigned successful disposal merely from command success. A repository-owned test attachment must retain the database and a cleanup obligation until actual disposal is acknowledged, including setup failures and interrupted cleanup. Supporting evidence also qualifies pinned references, events, GQL and SDK behavior; those source findings supplement the reviewer's repository inspection rather than establishing runtime acceptance.

Use three complementary boundaries: pure Rust/model controls without a database; isolated schema/query/permission contracts on an owned beta-managed target; and the actual pinned remote server for transport, authentication, publication, backup and process failure. Embedded engines can support the second boundary where their semantics fit; they do not qualify the network or server process. Container ownership is useful for a real deployment/termination test but need not be imposed on ordinary developer controls. Existing stable logical validation attempts remain useful for product persistence journeys.

This target introduces a legitimate exception to the present “main/validation only, no per-test database” rule. It does not require moving all tests to disposable databases. The isolation unit follows the effects: an ordinary data attempt can share compatible installed schema; a schema mutation, permission contract or destructive process test needs an owned boundary capable of absorbing that effect. Preserve failed databases only for a named diagnostic consumer and dispose through checked ownership. Dropping an exclusively owned database does not authorize deleting a shared server or interpreting background reclamation as instantaneous freed bytes.

[RuntimeConfig::read](../../../crates/lctx-native/src/config.rs), lines 57–85, currently hardcodes loopback gRPC and main/validation. [authenticated](../../../crates/lctx-native/src/reader.rs), lines 2426–2437, explicitly chooses plain Grpc. This is an honest current local deployment restriction, not itself a current defect. For beta isolation, separate installed service/target binding from the catalog's semantic contracts. Permit an explicitly authorized test target with the same identity, strict-schema, credentials and ownership checks. A later TLS/remote target can use a qualified secure connector; it is not a requirement to build every transport now.

Current [SDK documentation](https://surrealdb.com/docs/reference/rust/methods/connect) distinguishes incremental gRPC from buffered HTTP/WebSocket. The repository's exact adapter also extends stock behavior: [SDK provenance](../../../third_party/surrealdb/README.lctx.md), lines 29 onward, describes exact-session transaction finalization, retained begin failure and finite batch streaming. A cloned SDK handle shares connection infrastructure but creates a new session; it cannot cancel an earlier session's transaction. Authentication invalidation is likewise distinct from rollback. Keep explicit cancellation, terminal drainage and session invalidation as separate owned steps.

Connection customization should expose actual needed endpoint/TLS/authentication/message and deadline choices as an installation binding, not arbitrary request SQL or an unchecked options bag. Report the installed server/SDK/patch/capability identity. [Server recipe](../../../scripts/surrealdb_server.py), lines 42–108, includes a selectable execution-drain patch; source availability does not prove which daemon is installed or qualified. [Pins](../../pins.md), lines 131–135, currently describe a narrower baseline than all vendored extensions. Reconcile those descriptions without replacing current installed generations or replaying migrations during review.

## Diagnostics, agent access and operational integrations

The operator's useful first question is “which exact owner blocks this operation, what is known, and what can be inspected next?” Build on existing status, runs, evidence, fixture and native inspection routes rather than adding a compulsory dashboard. F04 supplies the missing durable cause projection. A composed read-only view can link host attachment, service generation, native request/attempt, pin/backup/retirement and retained evidence without making any one observer their authority.

SurrealDB's native schema/query tools, Studio, EXPLAIN and index diagnostics are appropriate generic inspection instruments. Product operations still belong in the domain MCP layer because generic CRUD does not know selected realizations, admission, evidence closure or operator adoption. A generic database MCP session should use an explicit target and least privilege; it must not create an owner-level embedded database as an unnoticed substitute for the installed service. ## Decision and next architectural choice

**Revise the enclosing lifecycle/serving architecture at Interface-checked strength.** Retain the Rust semantic authority, exact immutable content and current-admission distinction, separate publication/selection, native effect/hold/incarnation protocol, coherent selected backup and host/native completion separation. Correct the serving bypass first. F02's bulk access and F03's scoped completeness reuse are compatible improvements; neither waives independent observation. F05 needs an independently stated convergent completion contract. F04 is a lower-priority contract correction that enables more reliable agent/operator recovery and helps qualify later tooling integration.

The next design decision belongs to the coordinator and model/native/serving owners: specify the protected selection boundary and exact original-completion validity scope, then incorporate the selected SurrealKit 1.0 beta through generated schema inputs and explicitly owned test targets. Consequence priority and prerequisite order differ: correcting the selected-namespace contract may be a small enabling change for the highest-priority serving repair; defining completion validity can enable both F03 reuse and F05 convergence. Beta tooling, generic diagnostics and reactive integrations must not delay those product corrections or silently expand the first product into the research backlog.

This review accepts the direction of one shared native product store, not the current enclosing implementation, assembled qualification, measured performance or operator adoption. The preferred target removes unnecessary crossings and repeated reconstruction while keeping the evidence and failure guarantees that make the catalog useful.
