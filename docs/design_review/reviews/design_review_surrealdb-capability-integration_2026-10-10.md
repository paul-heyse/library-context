# SurrealDB capability integration: recoverable operations and selective access

**Design / Target review · 2026-10-10 · Decision: Revise**

The assembled SA0–SA9 correction has a coherent foundation: immutable completed views, separately owned host authority, bounded atomic native progress, operation-local definition preparation, exact membership answers, frozen lexical ranking, and guarded lifecycle pages. These responsibilities compose without a second canonical store or general workflow framework.

One material execution defect remains. Limited relation reads now avoid preparing unrelated relation families, but nominate every retained physical payload of the requested relation before testing selected membership. Their work therefore grows with unrelated retained releases, including for an empty selected answer and limit zero. F01 requires a selected-view relation route preserving aliases, global ordering and conflicts.

This is a source-scoped architectural judgment. It does not certify the pending assembled qualification, generic collection, installed maintenance executable refresh, SM8, BC3, real-library qualification, or operator adoption.

## 3. Recovery and lifecycle composition

The preserved format3→4 source recognizes original and enumerated repairable forms, assigns complete rows, and keeps legacy retirement jobs non-executable. Its preflight, translation, protection, nested cleanup and verification passes share a bounded progress owner. The reviewed migration source validates original attempt/contribution/product relationships and rechecks observations with page publication.

The progress primitive commits effects and cursor advancement under exact installation, contract, execution and revision checks. A failed acknowledgement reads the authoritative progress slot instead of blindly repeating effects. Compatible successor execution retains acknowledged work; incompatible preflight/protocol identity refuses reuse, while verifier changes restart the affected verification meaning. Host predecessor fencing supplies the exclusive-effects premise.

The actual format3→4 completion receipt `638d38` records exit 0 and confirmed cleanup for the immutable candidate. The later format4→5 transition explicitly changes runtime identity for typed history-page receipts. Current source does not retain an ordinary compatibility reader for the retired format.

Current history collection preserves the original horizon and examined cursor. Each page rechecks candidates, relevant parents, references, holds and generation inside the transaction, then publishes removed/protected partitions with the checkpoint revision. The corrected implicit IF values permit subsequent checkpoint publication; final transaction result extraction checks statement errors before accepting the outcome. Reconciliation replays the exact last page, and changed or older requests refuse.

Retirement batches root/child incarnation observations but rechecks each guard with effects. Child nomination and outgoing-hold removal remain atomic. High-degree work is bounded by actual effect windows; final retirement still requires an empty proof. Slim guards, original migration references and opaque recovery consumers remain protected.

These are **Implemented** mechanisms with the dated focused evidence described below. They do not authorize generic legacy collection.

## 4. Catalog, search and cold admission

`loader/catalog.rs` captures actual definitions once for an installation operation, prepares desired declarations, rejects same-name drift before effects and applies missing declarations in windows. Unknown DDL acknowledgement refreshes affected groups and reconciles their actual meanings. Required indexes are checked for readiness even when their definitions were already present. This avoids transferring installation success into a global admission certificate.

Publisher inspection and backup retain independent actual inventories. Selected backup captures manifest, definition metadata and content within the same transaction-bound snapshot. Portable restore treats definitions as inert comparison metadata, reconstructs typed data, and compares actual derived claims with regenerated state. The migration overlay remains outside selected portable authority.

Search uses native FULLTEXT table nomination plus exact-name/path/option branches. Eligibility precedes ranking quotas. Window hydration deduplicates dependency demand, checks every dependency and the unit payload, then verifies hydrated identity and dependency correspondence. Nomination streams, sessions, reader ownership and charges survive delivery cancellation through drainage.

Frozen lexical statistics retain ranking authority. Native global BM25 scores and approximate vector search do not silently replace the selected policy.

## 6. Findings

### <a id="F01"></a>F01 — Limited relation nomination grows with unrelated retained releases

**Owner:** Native reader/selection; SA5/SA9 and adjacent HS4/UP5.  
**Judgment:** A4 violated; FP-07 and DP-10/14/20, informed by H5–H10.  
**Priority:** Required before acceptance of the supported limited-relation growth scenario.

**Evidence.** `reader.rs:238–263` constructs:

```sql
SELECT id FROM {physical_table}
WITH INDEX {semantic_key_index}
WHERE semantic_type=$type
```

It supplies no selected-view restriction. `selection.rs:445–461` exhausts these nominations in windows, probing each against selected views and reverse aliases. It hydrates selected payloads, finishes and validates the global sort at `481–485`, and only then does the outer reader apply the output limit. A nonempty selected-view set with limit zero takes the same route.

**Consequence.** Hold a selected publication’s relation empty or tiny, then retain more unrelated releases containing that relation. The answer is unchanged, but nomination and membership work increase with all those unrelated physical payloads. Bounded windows and spilling bound portions of live state; they do not remove this repeated work. The correction to original F04 removed unrelated relation families, but leaves this distinct growth dimension.

**Correction — Proposed.** Nominate direct members through the existing exact `view_key(view, relation, semantic_key)` membership index. Add alias endpoints reached from selected source membership using the model-governed alias source/target relation contract. The current model’s `Entity::canonical_place_endpoint` defines Place→EntityRef; the reader must not independently recreate that classification.

Use indexed `alias_source` traversal for these sources, or an equivalent qualified indexed composition. Merge/deduplicate the complete relevant relation and retain selected nominal conflict checks before exposing a limited prefix. Do not substitute a per-view early limit, filter alias sources to the target relation, or restore complete unrelated-view startup. Zero output demand should preserve required authority/schema checks and then avoid row nomination.

No new persistent representation or schema transition is inherently required.

**Closure evidence.** Independently inspect that nomination is restricted to selected direct relation membership and relevant selected alias sources. Use a minimal native case with fixed tiny/empty selected relation and additional unselected same-relation content; establish the selective access route as well as exact output. Retain union ordering, duplicates, aliases from a different relation, late selected conflicts, cancellation and charge-release controls. A timing campaign or permanent accounting mechanism is unnecessary.

**Disposition:** Transfer this stable source ID to coordinator §8. A bounded follow-up may close it after the correction; the original dated finding remains.

## 8. Library fit and alternatives

SurrealDB 3.3.0, pinned in `Cargo.lock`, supplies the transaction, indexed access and FULLTEXT mechanisms used here. The selected library skill informed inspection; no claim is transferred from a different engine/version.

The small native progress protocol is justified by same-database atomic effects/progress and exact successor fencing. Generic rollout planning does not remove those requirements. Frozen ranking legitimately remains project-owned because native corpus scores have a different scope. Explicit holds remain appropriate because reference existence/deletion behavior alone does not express epochs, incarnations, cutoffs or recovery lineage.

For F01, the simplest viable alternative uses existing view and alias indexes. A new cache or materialized relation projection would add invalidation and lifecycle work without first exhausting that route.

Retaining the installation guard is a deliberate tradeoff: it orders era cuts and delayed effects. Removing it requires equivalent interleavings, rather than optimistic reads alone. No engine tuning, worker cap, notification consumer or new transport is justified merely by availability.
