## Assessment and scope

**Decision: Revise.** The consequential revision is small: Structural analysis must own the operation that determines its computation outcome and replay that outcome at publication. Current architecture prose also needs reconciliation with the expanded extraction implementation. These are F01 and F02 below. The evidence does not support replacing the pipeline or adding another general inference framework.

The system has a useful separation of responsibilities for its [API and evidence product](../../design/sections/api-and-evidence-product.md): source observations identify and characterize pinned APIs; normalized operations establish correspondence and admitted invocation shapes; finite behavioral operations answer specific questions under explicit premises; Structural and Analytic results enrich navigation and explanation; catalog/selection determine what an answer supports; synthesis renders canonical evidence; serving preserves one generation and its original sources. This conclusion rests on executing operations and replay/admission contracts, rather than crate names or domain records alone.

The expanded factbase makes several useful answers possible without another extractor. The strongest additions are role-qualified callable comparison, source-field/constructor-option explanation, conditional entry-value provenance, and diagnostic/use correlation. Import/re-export explanations are another credible use of an existing relation. These are opportunities, not claims that every retained fact must acquire a consumer. Contextual expected types and ty semantic reference search offer additional supply, but their integration burden and different fidelity warrant demand-led selection. A returned ty IDE signature hint is specifically not proof of type applicability.

The review covers acquisition, native facts and source views; normalization, binding and projections; finite behavior and Summary; Structural/Analytic composition; C0/C1/C2; S0 and retrieval; Rust wire, Python adaptation and PostgreSQL serving. Workloads considered are catalog compilation and discovery, explicitly requested behavioral compilation, inspection of operation shapes/options/source uses, bounded predicate comparison, retrieval and original-evidence expansion. It examines domain extension and mechanism substitution as well as present output correctness.

The implementation reduces repeated preparation through a generation-owned graph cache and borrowed graph views. Allocation reservations remain with materializations/schedules; charged Rows and work bounds constrain semantic kernels. Moving CPU work to a retained worker does not by itself prove cooperative cancellation; current static contracts and previously scoped receipts must remain separate from new scale/lifecycle measurements. There is no evidence here for a new universal graph executor or query planner.

Publication and serving are also substantive operations. [The cumulative pipeline](../../../crates/cpg-core/src/normalize/pipeline.rs) preflights the frontier/schedule, performs stages in one attempt, aborts failure and publishes no intermediate selected generation. Packet reads check relation authorization before even an empty ID read. Serving preparation retains one generation and cleans up on preparation failure. Optional packet sections retain availability, omission and continuation; evidence original bytes are bounded rather than silently manufactured. The static implementation supports these lifecycle distinctions; fresh live interruption/recovery qualification was not performed.

## Findings requiring revision

<a id="F01"></a>
### F01 — Structural computation completion is interpreted by orchestration and not reconstructed by the owning replay

**Priority: consequential ownership/validity gap. Diagnosis: Implemented / Interface-checked, 2026-10-04.** Relevant principles: FP-01, FP-04, FP-06; DP-03, DP-08, DP-17; A1 and A2; G3. This is an architectural defect even if the current producer normally emits the intended statuses.

The core Structural adapter decides the meaning of a method's execution outcome at [structural.rs:232–294](../../../crates/cpg-core/src/structural.rs#L232). It maps each method to capability, checks traversal stops and profile, and emits `NotRequested/NotRequested` for catalog controls, `Partial/BudgetReached` for bounded traversals, `Partial/IncompleteDomain` for requested controls, otherwise `Completed/None`. These are domain decisions about the completeness of a computation, not just writing a returned result.

The model owns actual Structural production and replay, but [frames.rs:18–64,162–226](../../../crates/lctx-model/src/domain/structural/frames.rs#L162) loads only parent Local outcomes and does not hydrate its own Structural outcomes. Replay reconstructs typed output and exact invocation/parent membership and ends in `actual.matches(expected)`. [The shared outcome validator](../../../crates/lctx-model/src/domain/analysis/family/invocation.rs#L65) enforces status/reason grammar. [Coverage replay](../../../crates/lctx-model/src/domain/analysis/family/coverage.rs#L303) then derives expected coverage using the **stored** computation status/reason; it does not recover the Structural execution status from traversal output. Its correct source-membership check is not a replacement for that missing semantic check.

A realistic extension—another Structural method, a widened control domain, or a different stop policy—therefore requires hidden semantic edits in the core adapter as well as the owning transformation/replay. There is also a specific enforcement gap: a coupled change to stored computation status and corresponding coverage is not checked against the Structural stops by these validators. The review did not run an adversarial PostgreSQL publication or demonstrate a false served assertion. The static gap in the outcome contract is sufficient for revision; it is not evidence that every stored coverage row or current normal output is wrong.

**Proposed correction.** `domain::structural` should own a bounded operation deriving the computation outcome from its exact invocation/method, selected profile and produced typed result/stop inventory. Production and stored replay should use that operation. The core adapter would prepare inputs, invoke it and publish its output. Keep source coverage and computation completion separate; do not replace their composition with “any partial source makes every result partial.” Preserve catalog controls as legitimately unrequested and preserve completed exact finite questions where the contract permits them. This is a narrow owner operation and replay extension, not a generic analysis-status framework.

A simpler relocation of the match into a helper is insufficient if replay still trusts stored statuses. Conversely, duplicating the match inside validation would create two independently maintained interpretations. Closure requires the shared operation and the deletion of the core interpretation. Its input contract should make the legitimate cases explicit: direct usage without a traversal stop, finite delegation stopped by a budget, requested controls with an incomplete supported domain, and catalog controls never requested.

**Closure evidence.** Static owner/consumer inspection can establish the corrected dependency direction. A focused independent status/result mismatch control should change the stored outcome and matching coverage together while preserving traversal stops and show rejection by the actual shared publication path; positive controls should preserve the legitimate cases above. These controls are Proposed / not_run. No detailed implementation schedule is authorized by this review.

**Disposition: Deferred in this source review; not scheduled.** Responsible component: `lctx-model::domain::structural`, with `cpg-core` adapter removal. Trigger: the next authorized architecture correction, and before adding a Structural method or widening its completion claim. Deferral does not establish acceptance of the enclosing outcome contract. No identical active-plan obligation was found in the bounded current finding-owner search; this review owns the new F01.

### F02 — Current architectural prose still describes obsolete parse authority and discarded facts

**Priority: lower than F01; misleading extension guidance. Diagnosis: Interface-checked, 2026-10-04.** Relevant principles: FP-02, FP-06; DP-22, DP-24; G7. This is stale authority/documentation, not a demonstrated second writable runtime authority.

[Semantic model §15.4](../../design/sections/semantic-model.md#section-15-4) still says “The Pyrefly/Ruff parse owns occurrence identity.” The current binding §B1 and accepted extraction target assign canonical syntax/lexical ownership to independent latest Ruff, and [the executing stage](../../../crates/cpg-extract/src/pyrefly_stage.rs#L806) actually obtains canonical syntax from `CanonicalSyntax::parse`, even when the native Pyrefly parse is unavailable. The module's introductory comment also still describes the retained Pyrefly parse as emitted canonical syntax.

[Extraction §3.4's Pysa mapping](../../design/sections/acquisition-and-extraction.md) groups `Target::FormatString` and `captured_variables` with other payloads as “not carried.” These particular claims are no longer accurate: [call_records.rs:236](../../../crates/cpg-extract/src/call_records.rs#L236) retains `SyntheticFormatting`, and [capture_records.rs](../../../crates/cpg-extract/src/capture_records.rs) carries native captured-variable origins. Those current routes do **not** establish that every older return shim, global-target projection or unused native field is consumed. Newly retained protocol return observations also have their own source/role contract; they cannot be used to declare every older return-type lane consumed. The correction must state actual supported subpayloads and limits rather than invert the whole row into “all carried.”

An agent extending a provider could follow the wrong parse boundary or add redundant extraction because current owning prose says the facts are absent. The executing types presently protect much of this mistake, but discovering the right contract requires knowledge beyond the owner page. This is the same general navigation concern as the earlier alignment review's F08, whose [current plan disposition](../../plans/semantic-model-incremental-alignment-plan_2026-10-02.md#7-current-disposition--sole-execution-owner) remains scoped to its earlier correction. The newly expanded extraction creates a distinct current mismatch; this review does not retroactively negate that receipt or reopen its status.

**Proposed correction and closure.** Reconcile the current semantic/extraction owners and local stage comment with the actual parser and retained facts, linking executable definitions instead of maintaining another field inventory. Remove superseded present-tense claims or label historical context explicitly. Accepted ADR history remains immutable. Shared-skill project notes are independently stale and must be revalidated when used; they are navigation, not repository authority, and their maintenance is outside this review's write scope. Closure is a focused owner→code reading plus the existing document publication check; no product rebuild or analyzer upgrade is required solely for this prose correction.

**Disposition: Deferred in this source review; not scheduled.** Responsible components: current semantic-model and acquisition/extraction owner sections and `cpg-extract` module guidance. Trigger: the next authorized documentation correction, before provider-extension guidance is used as current instruction. The technical target itself need not change.

### O01 — Compare callable contracts by role, then add typed applicability only when demanded

**Recommended incremental candidate; existing facts first.** Agents need to understand why a wrapper's source signature differs from its effective callable, which generated constructor fields exist, or which overload/specialization a particular example illustrates. Current [callable records](../../../crates/lctx-model/src/domain/normalized/callables.rs#L64) retain identity/signature/descriptor/body dimensions, role-specific variants, adjustment and receiver paths. Slots and structured type observations retain source/native formal identity. [Selection's specialization path](../../../crates/lctx-model/src/domain/selection/evaluate.rs#L307) currently answers an exact-site/native-declaration/single-member question and refuses absent, ambiguous and wrong-member inputs; it is not a multi-variant compatibility operation. [Operation packets](../../../crates/lctx-model/src/domain/serving/packets.rs#L71) already contain much of the corresponding evidence.

**Cascade.** Pyrefly source/effective/synthesized signatures and existing structured generic/overload observations → exact normalized variant and formal correspondence → a model-owned role comparison operation → a typed difference result for slot presence, requiredness/default knowledge, receiver adjustment, return/type evidence and unresolved correspondence → operation comparison/explanation and role-qualified retrieval text. New extraction is unnecessary for the initial structural comparison. This should compare what the supported contracts actually state, rather than promise runtime or cross-release compatibility.

Existing chosen/candidate overload traces can improve the source-example answer only when an owned **unique association** establishes native origin, normalized variant and specialization correspondence. [Source-use serving](../../../crates/lctx-postgres/src/generations/source_usage_service.rs#L427) currently correctly marks normalized variant identity unavailable. Equality of type display, structural term or closest candidate index cannot fill that gap. The inspected Pyrefly API returns the closest index in `get_all_overload_trace` even when it is not chosen, whereas `get_chosen_overload_trace` checks `is_closest_chosen`; see the [exact supplier contract](../evidence/2026-10-03_code-facts-analytical-architecture/provider-capabilities.md#51-contextual-expected-types-and-overload-evidence).

Bound variants/ports/type nodes and charge structural comparison work. Partial type closure or ambiguous correspondence yields an explicit unresolved part, not incompatible or absent. A full typed-call applicability extension is a separate semantic question; prefer the current model binder and attributed Pyrefly traces over implementing a second type checker. ty's [resolved_call_signature](https://github.com/astral-sh/ruff/blob/3265ed1f944c98bb4c04d632fbefb1257cdb583d/crates/ty_python_semantic/src/types/ide_support.rs#L1553) falls back to arity-matched hints when every overload has type errors. If used, it supplies candidate/mapping evidence or a differential oracle, not an accepted-type proof.

**Alternative and validation.** If the needed change is only visibility, enrich existing packet/text rendering rather than introduce a new comparison result. The current API-unit renderer emphasizes names, shapes, required/default slots and options; typed packet evidence can supply role-qualified text without another interpreter. A comparison operation is justified when selection or repeated agent reasoning consumes its differences. Independent controls: decorated ParamSpec wrapper, generated dataclass constructor, bound/unbound receiver, identical-shaped overload variants with different origins, closest-but-not-chosen trace, unknown default expression, and shadowed generic binder identities. Comparison should retain each role and explanation in every ambiguous case.

<a id="O02"></a>
### O02 — Make the retained constructor-formal → field → reader relation useful to Selection and inspection

**Recommended incremental candidate; consumer gap, not extraction gap.** The agent question is “Which constructor option initializes the field this method reads?” [Normalized source-field associations](../../../crates/lctx-model/src/domain/normalized/symbolic_fields.rs) and [C1 SourceFieldLink](../../../crates/lctx-model/src/domain/catalog/evidence/symbolic.rs) already retain exact parameter/field/read correspondence. C1 deliberately records `source_association=Known` and `runtime_value=Unknown`. Current [ConfigurationRelationship evaluation](../../../crates/lctx-model/src/domain/selection/evaluate.rs#L1183) returns unknown for `FieldTarget::Parameter` and `DeclaredParameter` rather than consuming that source-field relation.

**Cascade.** Existing Pyrefly record/member/formal observations and canonical stores/reads → normalized exact supported-record association/reader links → C1 field-option/parameter-option identity → a Selection-owned source-association predicate or typed relationship operation → initializer/field/reader result with original premises → `get_operation`, option relationship search or evidence expansion. The first new decision belongs in Selection/catalog relationship meaning, not a serving SQL join that invents it. No additional provider is needed.

Admission must use the link's exact member/context/native formal identity and refuse unsupported record classes, ambiguous owner correspondence and incomplete links. Separate source initialization/read association from later runtime instance value, mutation and temporal alias closure. A same-named field in another class is not a match. Bound returned associations and pages; missing association remains unresolved where coverage cannot establish absence.

**Alternative and validation.** A direct relationship packet may be simpler than widening the query predicate if agents only inspect a known option. Retaining current unknown is also coherent until a supported query is selected; the enum branch alone is not a false claim. Controls should distinguish `Config(timeout=t, title=n)` readers, inherited/generated fields, absent/ambiguous formal links, mutation after initialization, unsupported alias storage and separate instances. The result must continue to say source association, not “this runtime read equals the caller's argument.”

### O03 — Derive a guarded entry-value origin from a complete alternative reaching set

**Recommended bounded behavioral extension; use current ty flow first.** Current Entry admission is deliberately conservative. [entry.rs:639–674](../../../crates/lctx-model/src/domain/conditions/entry.rs#L639) refuses multiple supported reaching alternatives or loop-carried state before proving that the access condition is covered by the selected origin. This safely avoids asserting an unqualified original parameter value. It can also limit a narrower question: “Under this admitted guard, does this joined use still forward the original parameter?”

**Cascade.** Already retained ty core per-use reaching candidates, definition/place identity, region/narrowing/precision observations and original/runtime-view correspondence → a complete admitted use inventory and explicit query condition → a model-owned Entry alternative operation checking candidate coverage and disjointness under that condition → qualified conditional-origin witness or exact refusal → Local/Structural controls and exact value/path inspection. This is a new analysis of current evidence, not a new general dataflow extractor.

The operation would consider **all** admitted candidates and establish that other definitions cannot reach under the requested finite condition. It must preserve undefined/deleted alternatives, lost precision, loop-carried uncertainty and evaluation-occurrence identity; it may only use already supported guard semantics. BDD/candidate/work budgets are part of its result/refusal contract. A new finite guarded result must not silently broaden the current unqualified Entry witness or create heap/alias authority.

**Alternative and validation.** Expose the existing candidate inventory and current `EntryValueUnknown` first if it answers the explanation journey; do not add proof machinery just to hide an unknown. Independent controls: a joined call after conditional rebind where the requested guard excludes that rebind; a guard where it does not; undefined/deleted or exception alternatives; loop-carried rebinding; changed guard value; same-spelled tests at different evaluation occurrences; original typing view versus TYPE_CHECKING-adjusted runtime view. Use the actual retained inventory to confirm the revealing case—simple branch-local uses may already have one native reaching candidate. Python runtime observations can challenge selected known programs, but cannot certify general static completeness.

<a id="O04"></a>
### O04 — Correlate original diagnostics with admitted API uses and scenarios

**Recommended source-evidence enrichment; do not define a “clean example” verdict.** Agents selecting a documented example should see an exact selected diagnostic that affects its resolved API use, and should understand whether a test declares skip/expected failure. Current [characterization](../../../crates/lctx-model/src/domain/catalog/evidence/characterization.rs#L164) validates diagnostic run/support and original byte span; its scenario association is source containment, not API resolution or execution. Existing scenario intent and source-use associations supply the additional exact identities.

**Cascade.** Retained selected Ruff/Pyrefly diagnostic channels, original annotation spans and settings/run identity → exact normalized occurrence/use plus C1 API/scenario association, where it exists → a C1-owned diagnostic-use correlation operation → API/use/scenario-scoped note with unassociated remainder and explicit support → evidence/source packets and relevant retrieval text. First interpret source support and target association in the model; location overlap or a diagnostic's displayed symbol name is insufficient to give member authority.

Bound overlap/correspondence work and preserve foreign/missing span refusal, rule selection, suppressed/disabled/baseline distinctions and version alignment. The absence of a returned diagnostic still proves neither valid code nor execution. Pytest fixture definitions, skip and expected-failure intent are authored source evidence; passing test observations require their own exact execution receipt. Empty or partially correlated sections remain explicit.

**Alternative and validation.** Existing artifact characterization is enough where no exact API association is available; a renderer can show it alongside source rather than manufacture a new conclusion. Add correlation only when it reduces a real repeated inspection step. Independent cases: same-spelled unrelated call, diagnostic outside the selected snippet, missing/secondary-only or foreign source span, suppression/configuration differences, duplicated diagnostics, resolved versus candidate target, and an expected-exception test not executed. Positive evidence can improve relevance/explanation without becoming a rejection gate.

### O05 — Explain public import/re-export routes from the existing ImportReference relation

**Useful new navigation result; confirm demand before persisting another graph.** An agent sometimes needs to know how a public import path reaches the declared API, or why a re-export is uncertain. [ProjectionSpec](../../../crates/lctx-model/src/domain/projection.rs#L53) already declares ImportReference and its coverage families; normalization emits it. The bounded search of core, Structural and Analytic consumers found those analyses use invocation and/or containment projections, not ImportReference. An unused declared projection is not itself a defect.

**Cascade.** Existing canonical aliases/binding events, Pyrefly resolved import handles and partial/computed exports → normalized import/reference identity and public exposures → a model-owned bounded exposure-route operation → ordered supported alias/re-export edges, original evidence, ambiguity/cycle/coverage boundary → operation access explanation and source/document navigation. Direct exact joins should precede generic traversal. Only persist a new result or relation family if another consumer, such as a selected RCA/navigation question, needs it.

Each edge needs original resolution support, scope and direction. Parallel import/reference meanings must remain separate; traversal closure requires a declared captured-module universe. A wildcard candidate set is not proof that every name is definitely bound. Per-name ty core StarImport placeholders have module/symbol identity that could make an uncertainty explanation more specific, but current opaque lowering is an explicit support boundary. Do not use Pyrefly wildcard membership as the truth of a different ty reachability predicate or introduce a second export authority.

**Alternative and validation.** Current public access provenance plus original imports may answer the question without a graph operation. A bounded on-demand route is preferable to a general composition planner. Controls: explicit alias and re-export, cross-module cycle, two same-named targets, partial/dynamic `__all__`, unresolved importer, stub/source distinction and omitted context module. If a later setup/install-requirements journey is selected, join captured distribution/declaration evidence separately; source import and declared dependency are not installability or runtime requirement proof.

<a id="O06"></a>
### O06 — Give contextual Expected evidence a first interpretation before broadening its extraction

**Conditional correct-use extension; selected new argument subpayload only after a useful consumer.** Pyrefly's inspected `Answers::get_expected_type_trace(range)` returns an optional recorded contextual trace. Current [type_records.rs:1773–1790](../../../crates/cpg-extract/src/type_records.rs#L1773) queries Expected only for selected attribute/assignment/return value children; [location validation](../../../crates/lctx-model/src/domain/types/locations.rs#L61) encodes those roles. Arguments have actual type traces, but no Expected query there. This finite supported slice is not a defect by itself. The bounded consumer search did not identify a dedicated Expected interpretation beyond location validation and generic reads/projections.

**Cascade.** Existing Expected/actual type observations at selected supported locations → exact contextual subject/view/run/term evidence → a model-owned contextual-type explanation operation → actual/expected evidence with candidate basis and unavailable parts → “What typing context does this example receive?” source/operation output. If argument explanation changes that answer, extend extraction with an explicit argument-context location role and call/candidate basis, using the same optional trace API. Do not call the contextual expected type a declared formal type or a runtime violation.

Bounds cover selected argument/type closure and comparison work; absence of trace is unavailable. Overload ambiguity and a trace obtained from an erroneous call remain attributed contextual evidence. The role/location invariant must evolve deliberately; expanding the extractor while leaving existing Expected validation unchanged would be invalid. No textual type-name comparison should supply compatibility.

**Alternative and validation.** Native slot/declaration types often answer correct-use questions with less new machinery, and O01 may supply the necessary explanation. Independent controls: contextual empty container, overload ambiguity, missing trace, wrong parent/source role, same range in a different view, and expected trace from an error-recovered call. This opportunity is lower priority than consuming existing actionable signature/field evidence.

<a id="O07"></a>
### O07 — Treat ty semantic navigation as a scoped reference product or oracle, not another typing authority

**Demand-triggered new output family; not recommended as a default dependency expansion.** A concrete additional agent journey is “Where is this public member or parameter referenced outside call syntax?” Existing source-use packets focus on normalized call events. ty's [find_references](https://github.com/astral-sh/ruff/blob/3265ed1f944c98bb4c04d632fbefb1257cdb583d/crates/ty_ide/src/find_references.rs#L14) and reference search retain Read/Write/Other and explicit alias policy, including keyword-parameter references. They require semantic/IDE/project database contracts that the current core flow adapter does not implement.

**Cascade, if selected.** Exact captured project/file universe, original program file/offset, alias/declaration policy and explicit semantic environment → ty candidate references → model-owned entity/source correspondence and bounded incoming-reference classification → attributed non-call-use inventory with coverage/refusal → a reference inspection packet or independent oracle report. Native salsa handles remain invocation-local; persist model IDs and owned observations. Missing modules or dynamic/external consumers prevent complete absence claims.

The semantic Db adds analysis settings, rule/program-file/open-file/version/dependency state; IDE/project adds environment ownership and unpublished matching source crates. This is substantial integration cost even with the pinned source family already available. Selected query/captured-universe work needs allocation/work/cancellation contracts and original-view attachment. Likewise, `static_member_type_for_attribute` describes the descriptor object, not the value returned by descriptor access; `all_members` is crate-private, and supplied-module subtype search is not whole-world hierarchy closure. These semantics cannot be substituted for current Pyrefly member/MRO/type facts merely because they are richer IDE APIs.

**Alternative and validation.** Final Ruff local lexical facts, existing Pyrefly definition answers/Pysa origins and source field links are lower-coupling inputs for many local questions. Use ty as a differential oracle when disagreement classification can improve confidence, or integrate the narrow reference journey only after its product need is demonstrated. Controls: shadowed names, alias resolve/preserve policy, keyword argument label, decorator/property/member read, augmented assignment, typing-only/unreachable use and omitted module. For descriptor oracle work, compare descriptor identity and typed access value separately. No blanket third type authority is proposed.

<a id="O08"></a>
### O08 — Revisit generic algorithm fit through bounded contracts, including FCA, without discarding domain meaning

**Conditional mechanism substitution / independent validation opportunity.** The current graph and condition library choices already remove much generic machinery: petgraph SCCs/traversal/topology, bounded biodivine BDDs, leiden-rs and the current Arrow/DataFusion compute family. Domain-specific attachment, typing premises and finite transfer remain legitimate custom semantics. A new multirelation recursive query has not been demonstrated merely by listing new facts.

For finite nonrecursive relation recipes such as O02/O04, current DataFusion join/group/distinct may be preferable to bespoke repeated scans if it improves the selected contract. Explicitly state bag multiplicity, null-key behavior, ordering and charged hydration; a SQL row or empty relation does not establish coverage. A single relation closure can use existing petgraph/SCC mechanisms. Ascent or Datafrog would become credible alternatives only for several shared recursive families with real reuse; neither is currently a direct workspace dependency. Rules/stratification, conversion and resource control are costs, not automatic improvements.

FCA merits a renewed technical comparison. The older ADR-0044 rationale partly rejects `odis` on AGPL licensing; current user instructions explicitly disallow licensing as the reason for rejection. That makes the old reason unavailable for a new choice, but does not establish technical equivalence. Current FCA combines bounded NextClosure, implication/minimum-support work, charged retained state and explicit partial outcomes, with fcars as an oracle. Odis 2026.9.1 [concept enumeration](https://docs.rs/odis/2026.9.1/odis/traits/concept_enumerator/trait.ConceptEnumerator.html) exposes an iterator a caller can stop between concepts; [compute_basis](https://docs.rs/odis/2026.9.1/odis/traits/implication_engine/trait.ImplicationEngine.html) returns a `Vec` without a work/cancel parameter; [iceberg enumeration](https://docs.rs/odis/2026.9.1/odis/traits/iceberg_enumerator/trait.IcebergConceptEnumerator.html) returns a whole lattice. These inspected interfaces are not a confirmed drop-in for the existing charged partial kernel.

**Cascade.** Existing typed finite attribute/incidence context → adapter to a selected generic library/oracle operation → independently compared concept/implication result and explicit resource boundary → stronger kernel assurance, or a replacement implementation behind the same model contract → unchanged finite-context findings and S0 output. Preserve context identity and evidence; library algorithms do not become another persisted semantic authority.

**Alternative and validation.** Retain the bounded kernel if library work/memory behavior cannot meet the contract; qualify odis as an additional independent small-context oracle before considering production substitution. Controls should compare extents/intents and valid basis consequences across empty/singleton contexts, duplicate incidence, low support, deterministic shuffled input and exhaustion. Whole-call internal work/memory and cancellation remain unresolved, with no benchmark or production-boundary probe here. A new ADR is required only if an architecture choice changes; accepted ADR history is not rewritten. This is a technical adoption question, not an automatic G8 failure or a mandate to install another engine.

### Opportunities deliberately not promoted into requirements

The supplier audit also identifies discarded `definitions_with_usage` Booleans, end-of-scope binding iterators, class metadata subpayloads and getter traces. Each has possible explanatory value, but current Ruff unused diagnostics, Pyrefly metadata and capture/per-use flow already answer substantial portions of those questions. Add a usage Boolean only for a scope-qualified overwritten/unused declaration explanation that improves a selected answer; it is not runtime liveness or proof of no external references. Add `has_base_any`/getter details only where they improve an existing class/dispatch refusal or origin distinction. Framework flags, completions and total-ordering metadata do not justify a new ORM/runtime capability catalog.

A broad directional protocol/dataflow graph is also not yet a recommended separate output family. Existing invocation/capture/terminal/transfer results can support a selected producer→consumer path, but node/port identity, condition, phase, relation direction, transfer and closure must be specified first. A graph merely connecting compatible types would answer a different question. O03 is a concrete bounded extension; a general graph should wait for a query that current handoff/value-path operations cannot answer.

## Change scenarios, alternatives and complexity

The following scenarios assess model adequacy independently of gate compliance. Multiple touched contracts are legitimate for a new semantic category; the problem is independently repeated meaning or hidden unrelated decisions.

| Scenario / change kind | Correct owner and propagation | Current evidence and architectural consequence | Settling evidence / proposed route |
|---|---|---|---|
| Another provider observation for an existing role — binding | Adapter observation plus exact attachment; canonical relation and existing consumers reuse meaning | Nominal AST/view isolation and support checks make this credible; no new type authority is needed | Exact provider/source/role mismatches and unchanged normalized identity; no full product gate for each helper |
| New contextual argument expectation — domain category | Type role/location contract, provider extraction, one contextual interpretation and its packet/rendering | O06 requires a real contract migration, not “Expected is just another term” | Actual/expected/overload error controls; absence stays unavailable |
| New signature/field explanation — composition | Existing normalized identities and C1 evidence; model comparison/relationship operation; serving projection | O01/O02 have credible incremental routes and do not need new capture or a new store | Independent ambiguity/source/runtime controls; rendering alone is an alternative |
| Widen Structural control completion — policy/domain extension | Structural operation/result/outcome contract and shared replay | F01 requires hidden core classifier knowledge and omits semantic outcome replay | Move authoritative outcome operation into owner, remove core interpretation and challenge paired outcome/coverage tampering |
| Replace graph representation/algorithm — mechanism | Same named projection and canonical IDs; qualify native conversion/results and resource behavior | Prepared borrowed materializations separate persistent identity from indices; SCC scheduling is explicit, heuristics retain settings | Isolates, parallel arcs, self-loop, reconvergence/cycle, unresolved targets, shuffled input; compare partition membership rather than labels |

The simplest useful architecture is the current layered pipeline plus narrow owned operations. It localizes provider changes while avoiding a parallel evidence store or Python semantic implementation. A wholesale analytical graph or general rule engine would add identity/projection/closure/cancellation and replay burdens before its consumer is established. Persisting every available fact would increase acquisition, type conversion, validation and packet cost without establishing useful meaning. Conversely, refusing every new output family would leave agents repeatedly reconstructing comparisons and source relations from packets. O01–O05 identify the middle course: bounded results whose inputs and downstream questions are concrete.

Library fit therefore concerns total burden: generic implementation removed, conversions and environment construction added, resource semantics retained, qualification/oracle maintenance, and replacement/deletion obligations. A library is not technically rejected because it is GPL/AGPL/MPL, but neither is a named library adopted because it has a similar algorithm. No measured speedup, simplification count or scale benefit is asserted.
