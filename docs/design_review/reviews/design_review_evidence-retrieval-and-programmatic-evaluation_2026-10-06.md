# Evidence-preserving retrieval and programmatic evaluation — design review

**Decision: Revise.** The proposal supplies a credible architecture for the settled target: programmatic evaluation is the primary engineering loop, and an outer agentic loop challenges both the retrieval system and the evaluator's task models, coverage and judgments. Its most valuable change is to make applicable, actually delivered information the object of evaluation. Exact bindings, interpretation context and independent witness alternatives address failures that improving embedding similarity alone cannot fix.

Three corrections remain before adopting the complete proposal as the governing design. Changes to evaluator meaning need an owned, versioned adjudication boundary; the full-vector migration needs an explicit policy for its analytical consumers; and the library appendix must reconcile its solver-first recommendation with the finite-first core and preserve actual solver status. These are distinct causes. The first concerns what an improvement means, the second concerns the meaning of reused numerical values, and the third concerns conflicting mechanism priorities and a conditional Rust binding hazard that can erase a required outcome. They do not justify restarting the paused graph remediation or making agentic judging the primary loop.

The production architecture otherwise has a credible Proposed route: retain the Rust semantic graph and store-free compiler, use native indexed candidate discovery, expand named qualified relations, select context-closed bundles, and evaluate the final bytes through a separate offline process. Heavy references, countermodels and mutation campaigns remain bounded offline work. Optional neural scorers and advanced solvers must earn a named capability and an acceptable total lifecycle burden. No speed, quality, capacity or real-library acceptance follows from this static review. The appendices' unresolved `:chatgpt-content-reference` placeholders should be replaced with concrete primary links before publication; their existence is a citation repair, not independent evidence of a design defect.

## 3. Production contracts and retained strengths

The proposal's §4 distinctions are substantive, not cosmetic schema proliferation. A window is the searched payload; a binding states which primary material can nominate which target; a part mapping explains assembled text; interpretation dependencies explain what cannot be omitted; a packet map connects the final exposed fields/spans to their premises. Logical kinds need not become separate tables or stages.

Current source corroborates the attribution problem. `retrieval/build.rs:1101` and `cpg-core/src/retrieval_preparation.rs:346` select the member's access-module artifact for source material. `lctx-publisher/src/search.rs:315–367` combines each fragment with parent subjects and anchors. Streaming this product bounds construction state but does not establish per-fragment applicability. The proposed exact binding lowering replaces that causal mechanism. A source root must also support ambiguous, external and non-callable definitions rather than assume every public member has one source callable.

Preserve the existing distinctions already available upstream: catalog invocation owns its variant; option subjects distinguish effective slots, fields and source parameters; scenario intent/setup/association statuses are explicit in `catalog/evidence/mod.rs:56–130`. Standalone document roots already exist. The proposal correctly extends finer window/target applicability rather than requiring a new document store or erasing the current unknown vocabulary.

| Operation | Required behavior and rejection boundary | Independent check or revealing case |
|---|---|---|
| Construct window/bindings | Retrieval construction/validation uses exact primary segments, applicable context and original/projection mappings; reject invalid ranges or incompatible premise ownership before publication | Sibling A/B on one page; only A's primary passage nominates A, setup import B remains navigation/context |
| Partition/admit encoder input | Count complete assembled input with immutable matching tokenizer assets; context/special tokens count; no silent truncation | Unicode and synthetic header do not shift original coordinates; oversized mandatory context remains addressable with explicit partial search |
| Group/expand/select bundle | Compatibility includes invocation/configuration context; preserve AND dependencies, qualification and contradictions; candidate suggestions never become proof | Same member has incompatible overload options; independently useful-looking snippets cannot be joined into a false contract |
| Deliver/expand | Final serialized fields and readable content, not just hidden IDs, govern immediate sufficiency; actual expansion tools and total journey budget govern expandable sufficiency | Condition ID present but definition omitted; immediate failure, possible expansion success only if actual route supplies it |
| Continue | Bind snapshot, query/scorer/channel/fallback/ordering realization; refuse incompatible continuation | Scorer unavailable on second page cannot silently replace the original candidate ordering |

Existing exact member promotion (`lctx-serving/src/operations.rs:332`), evidence byte expansion, assertion qualifications and channel/snapshot-bound cursor refusal are foundations to retain. They are not wholesale missing capabilities. Current cursors already include vector spec/query digest and policy identity (`domain/serving/cursor.rs:10–45`); the proposed bounded search-result/query realization addresses recomputation/order stability beyond that binding. A permanent session registry is unnecessary when returning one bounded result or a reproducible pinned ordering suffices.

## 4. Composed execution and workload fit

### Analysis and projection records

| Stage/question | Universe, relationships and selection | Method/model/settings | Limits, outcome and evidence linkage |
|---|---|---|---|
| Window construction: what can be searched honestly? | Selected admitted root and its exact parts/bindings; standalone source/document roots permitted | Deterministic render/partition spec with original byte/projection mapping | Bounded semantic windows and context; explicit exceptional/lexical-only policy; no support invented from proximity |
| Candidate discovery: which places might help? | Eligible scoped exact identifiers, lexical matches and shared projected values; contextual occurrences retained | Exact lookup/match plus heuristic BM25/HNSW; tier policy and ties declared | Raw caps are examined candidate limits, not complete-domain absence; widening uses distinct contexts/roles and common request limits |
| Expansion: which applicable evidence completes a candidate? | Named typed relations and support/context; physical participant hops are not semantic hops | Native batched restrictions/hydration; domain operations own meaning | Bound useful frontier/degree/intermediate bytes and expose partial outcome; do not enumerate all paths |
| Rescore/fuse/rerank: how order valid candidates? | Retained candidate union and compatible connected bundles | Full-vector numeric score, family-normalized fusion and optional scorer identity; all heuristic | Full rescoring cannot recover missed candidates; consistent pool fallback; no heuristic proof or raw-score calibration assumed |
| Delivery: what meaningful information survives? | Context-closed bundle alternatives and mandatory identity/qualification/signature | Domain bundle selection using actual rendered cost; heuristic packing, no optimum/submodularity claim | Final structured/text response and exact maps; omitted and expandable differ |
| Evaluation: what is sufficient under this task? | Private scoped source/fact oracle, independent AND/OR alternatives with existential compatible context | Finite reference scans/circuits; selected bounded models, optionally BDD/SMT; F01 governs revision | Actual response and allowed observations; unsupported/inconsistent/unknown remain separate; evidence inventory completeness explicit |
| Numerical reference: where is approximation loss? | Same eligible admitted values at full and projected dimensions | Blocked exhaustive scoring with precision/tie policy | Bounded matrix blocks/top-K; exhaustive does not mean exact real arithmetic or semantic relevance |

The main proposal is well fitted qualitatively to the ordinary workload. Indexed access reduces unrelated-content work, contextual aggregation avoids spending the entire raw pool on one prolific API, and scoped native expansion avoids whole-graph hydration. Shared values and exact binding sets remove vector-per-anchor amplification while preserving provenance. Root construction can remain per grain and inference can batch a bounded number of finalized windows with backpressure. This retains the current immutable winner, shared decode and terminal reconciliation strengths.

`search.rs:61` applies `score>0` and document `LIMIT 100` before grouping; `:145` uses HNSW `<|100,200|>`. SurrealDB's captured 3.3 documentation explicitly permits matching BM25-zero records. The proposed bounded match route and exact identifier extension solve eligibility loss without arbitrary relevance bonuses. Distinct-target/context tiers address crowding, but 128/256/512/1024 and preferred 1024-token windows remain Proposed experimental settings, not optimal defaults. Finite tiers cannot guarantee a witness in an unbounded skewed corpus; approximate discovery remains distinct from complete selection.

Native predicates also need honest physical interpretation. The inspected 3.3 KNN implementation has residual traversal predicates, bitmap allow-list paths and a small-list exact tier. A correlated occurrence EXISTS is not automatically a bitmap prefilter. A few typed scalar projection scope fields can improve common filtering while exact semantic bindings remain separate. Alternatively, derive a small eligible distinct value set and score it directly. Both are credible; choose by the supported access shape and inspect the composed plan when implementing, rather than adding another vector store. A projection per value minimizes duplication; per value/family/capture scope may buy selective access at a write/index burden. Neither is universally preferable. Native DISKANN is also a conditional mechanism alternative when index residency becomes the limiting premise: inspected SurrealDB3.3 KNN source (`exec/operators/scan/knn.rs:658–701`) implements its search and requires a 64-bit non-WASM platform; the skill brief's actual-execution body corrects its stale summary row. This does not require a new backend, establish scoped-query parity or prove superior latency/capacity. Select it only against the relevant query/representation contract and workload; HNSW remains the initial experiment. See the [official vector-index documentation](https://surrealdb.com/docs/learn/data-models/vector-search/vector-indexes).

Retaining full 4096 F32 values uses four times the payload of 1024 values; a 1024 search projection adds another value representation. This buys candidate-union rescoring and isolated representation/index comparisons, so it has a real consumer. Share it once, avoid full arrays per occurrence, and hydrate only retained candidates. It does not establish a quality improvement; that remains an experiment. F02 must settle analytical consumer semantics before this tradeoff is complete.

Offline operations have a different envelope. Finite fixture countermodels and small minimum-packet inventories are suitable for enumeration or selected solver calls. Larger numerical references can process blocks and retain bounded top-K. BDDs may compress repeated Boolean queries but ordering/node growth can make a direct circuit preferable. Full witness-set enumeration, dense all-pairs storage, exhaustive production queries or a solver per request would be avoidable amplification; the proposal excludes these. Optional reranking buys a specific candidate ordering experiment but adds checkpoint acquisition, preprocessing, device residency/admission and cancellation/fallback obligations. Reusing vLLM's engine does not establish model co-residency or make the current embedding process a reranker. The no-reranker indexed baseline is credible; live optional scorer capacity remains unknown and must not be claimed until separately qualified. No work accounting system or formal cost proof is required to make these choices.

The positive countermodel design deserves explicit preservation. Main §8.5 requires a satisfiable observable model first, permits only delivered content/allowed interpretation, excludes opaque IDs as semantic observations, scopes no-countermodel results to a finite class, and keeps inconsistent/unknown oracles inconclusive. In the `override is None` versus `override or default` twin-program case, signatures and hidden IDs must leave both behaviors possible. The fixture source oracle may know the answer; that knowledge cannot become packet-observable background and predetermine it. These safeguards are already stated, so their absence is not a finding. Independently authored observation encodings and seeded counterexamples should challenge their realization. Witness leaves must yield compatible binding assignments: All joins on shared context variables, Any preserves alternative assignments, and the existential context encloses the whole conjunction. Independently finding a context for each role would mix overloads. Delivered presence variables must be fixed to actual availability; leaving them free asks about a possible completion. Countermodel worlds must agree on the task input/context before different answers establish lost information.

## 7. Material findings

<a id="F01"></a>
### F01 — Evaluator evolution lacks a governed comparison boundary

**Priority: high. Principles:** FP-01/FP-04/FP-05, DP-05/DP-08/DP-09/DP-24; A1/A2, G1. **Evidence:** main §9.6 freezes meanings within a configuration comparison, and the evaluation appendix §11 (`:1028–1044`) identifies task/model coverage and usability gaps. Neither specifies the operation that promotes outer observations into changed task meanings/judgments, how its independent basis is admitted, or how comparisons distinguish evaluator changes from system changes.

**Consequence:** an outer study reveals that users require configuration precedence or a more legible expansion path. One implementation weakens an existing witness requirement, another changes the allowable follow-up calls, and a third adds a new task stratum. Each may be a legitimate correction, but their resulting scores are not comparable as unchanged engineering improvements. Treating agent success/failure as oracle truth can also introduce the very subjective/circular judging the primary loop avoids. The missing boundary affects a required change scenario, not merely report formatting.

**Correction — Proposed:** the offline evaluator owns a versioned task/model/oracle judgment contract and a small adjudication operation. It consumes grounded outer observations, identifies whether they imply a production defect, missing task/model coverage, or presentation/navigation mismatch, and records the independent source/fixture/runtime basis for any new semantic expectation. It produces an explicit evaluator revision and support limits; system changes go to their existing owners. Freeze one such revision within an inner experiment. When meanings change, declare a new baseline/stratum; where old and new contracts address the same task and retained outputs are available, score both against the same packets to isolate the evaluator change. Keep only comparison artifacts needed by a named current experiment, not a permanent historical corpus or compatibility runtime.

**Revealing valid case:** a packet is formally sufficient but several agents repeatedly miss its expansion affordance. This supports a usability/presentation change and possibly a new realistic task, even though the old formal result stays valid. It does not prove a source fact or justify silently relabeling the old task. Conversely, agent misuse alone need not invalidate a sound evidence contract.

**Closure:** inspect one grounded outer observation flowing into a system correction and one into evaluator coverage/judgment revision; show explicit version/comparison semantics and no automatic promotion of agent opinion to truth. A source walkthrough can close the target-design gap; later controls protect the realized boundary. **Disposition:** Deferred in this source review until a subsequent authorized design/plan incorporates it; trigger is adoption or implementation of the outer feedback loop.

<a id="F02"></a>
### F02 — Full values and split specifications omit analytical consumer policy

**Priority: high. Principles:** FP-02/FP-04, DP-04/DP-08/DP-09/DP-11/DP-24, CI-05/CI-09/CI-13; A2, G2/G6. **Evidence:** main §6.2 (`:216–233`) changes stored values to 4096 and derives search1024, while its integration map names embedding owners without deciding analytical consumption. Current synthesis/serving §11.1, semantic model §15 and DESIGN §B14 select one shared spec for analytics and retrieval. `analytics/neighbours.rs:256` uses every accepted dimension in pair scoring; `:441–463` uses them for centroids. `analytics/vectors.rs` derives API pairs, passage links and community labels from that accepted domain. `scripts/embed_serve.py:45–58` only admits1024; installed `pooling_params.py:165–192` rejects a dimension outside the configured Matryoshka list. Native `materialization.rs:61` fixes schema/index1024.

**Consequence:** implementers can choose either full4096 or search1024 for E1 incidentally. Both satisfy the words “retain full values” but yield different analytical scores, selected pairs/passage evidence and labels, different receipts and working sets. Splitting only search/client identities can leave analytical values attached to an incompatible all-in-one spec or force unrelated query-only changes to rebuild them. The installed service will also reject a client-only full-dimension change. These are an unresolved domain transformation and launch boundary, not a demand to preserve old numerical outputs forever.

**Correction — Proposed:** the embedding owner declares the exact encoder input/full-value identity and mechanically derived consumer projection policies. Choose deliberately whether analytics uses a declared normalized1024 projection of the accepted full value or moves to full4096 under new analytical policy/results. The first retains a clear dimension policy, not guaranteed bitwise endpoint parity; the second is an intentional analytical change requiring fresh result/receipt qualification. Preserve winning bytes and complete consumption identities. Query instructions belong in query dependencies, not unchanged document value keys. Update launch admission, clients, cache/receipts, transport, native search schema/reconciliation and restore together; existing1024 bytes cannot supply lost components.

**Revealing valid case:** two query-task instructions change ranking but document text, checkpoint and encoding remain identical. Reuse the admitted document/full value; replace query/search realization and continuation identity. An analytical policy change may reuse the full input value but must replace affected analytical results. No old reader or selected-snapshot mutation is required.

**Closure:** explicit analytical policy and dependency mapping; narrow full/projection/client admission and finite-precision parity controls; one analytical consumer receipt/result under the chosen policy; detached canonical roundtrip and restore rebuilding the new projection without inference. The target policy can be closed by inspection; actual live checkpoint usability/quality stays separate. **Disposition:** Deferred in this source review until authorized adoption/planning; trigger is shared spec/full-value implementation.

<a id="F03"></a>
### F03 — Solver-first appendix conflicts with the core; consequence integration needs a status-preserving binding

**Priority: medium. Principles:** FP-02/FP-03/FP-06/FP-07, DP-11/DP-15/DP-16/DP-21; A3, G2/G7. **Evidence:** main §8.5 (`:371`) starts with enumeration and optional Z3; the evaluation recommendation prioritizes witness checking/loss localization (`:1026`); the library recommendation calls Z3 the most valuable immediate integration (`:1074`) and closes by prioritizing its adapter (`:1451`). Its consequence extraction advice (`:1128`) recommends a native capability, not a particular Rust method, and coexists with a requirement to distinguish solver status. If the Rust route selects `Solver::get_consequences`, the following exact-version integration hazard applies. Inspected pinned Rust `z3`0.21.1 `source/solver.rs:236–252` calls `Z3_solver_get_consequences` but discards its return status and returns only `Vec<Bool>` ([exact versioned source](https://docs.rs/z3/0.21.1/src/z3/solver.rs.html)).

**Consequence:** an implementer can make solver/native-library integration a prerequisite for a witness circuit that ordinary finite operations already evaluate. That adds encoding, platform and unknown-handling obligations before the central evaluator is useful. If an implementation selects this Rust convenience method and interprets its returned vector as successful consequence extraction, an empty vector cannot establish “no forced distinctions” separately from an inconclusive underlying call. The isolated vLLM Z3 dependency does not qualify a Rust evaluation worker or make that service its owner.

**Correction — Proposed:** make the main finite-first boundary govern the appendices. Use direct contextual circuits/sets and enumeration for straightforward finite references, BDDs only for a named repeated Boolean/quantification need, and one optional Z3 encoder for a named theory-sensitive or optimization task. A selected solver operation must return status, reason and result separately. For consequence queries use status-preserving explicit checks or a thin qualified raw binding that retains the actual return/error outcome; a preceding check does not establish that a later consequence extraction completed. Unsat cores are model explanations, not unique/minimum-cost evidence. Feasible optimization is not automatically an optimum; rendered token costs require verification.

**Revealing valid case:** finite context-compatible witness alternatives suffice without arithmetic. Requiring Z3 would reject a useful evaluator deployment because a native library is unavailable. Conversely, `override` arithmetic/value theory may justify Z3; preserving Unknown makes the result unscorable rather than successful determinacy.

**Closure:** reconcile appendix priorities and declare an optional solver escalation/use case; inspect a status-preserving result boundary and a finite lane that operates independently. No solver install or proof campaign is needed for this design correction. **Disposition:** Deferred in this source review until authorized adoption/planning; trigger is evaluator mechanism selection.

## 9. Alternatives and interacting remedies

The present member-level byte-fragment baseline has low migration burden but retains source-attribution and target-crowding mechanisms that defeat valid evidence sufficiency. It is not the target to freeze. Conventional relevance metrics or exact nearest-neighbor comparisons can diagnose channel loss, but cannot judge jointly necessary compatible context. The recommended main design extends existing semantic owners and uses native search plus explicit bounded bundles. A solver-first evaluator is viable for a selected value/theory task but disproportionate as a universal prerequisite; F03 chooses by operation rather than package availability. Pure agent judging alone cannot make exact attribution/context losses reproducibly local, while programmatic judging alone cannot establish broad natural-language usefulness. The settled two-loop arrangement retains their distinct roles.

Corrections fit together. F01 versions the yardstick; F02 identifies system representation changes scored under that yardstick; F03 provides honest reference mechanisms behind it. The evaluator version boundary cannot become a second production classifier, and the consumer projection boundary cannot become a compatibility bridge retaining obsolete runtime formats.
