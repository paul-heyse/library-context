# Graph compilation, relation kernels and hashing

**Design / target review · 2026-10-09 · Decision: Revise.**

The current system has strong nominal identity, attributed facts, explicit uncertainty, exact completed inputs and controlled publication. These are useful foundations for a broader graph-based compiler. They do not establish that the current composition fits relation-heavy compilation. The source shows two material problems: repeated physical preparation and hydration beneath one-root operations, and class/body/coverage scope rules interpreted separately in model code and compiler selectors. The second problem concerns the operations governing the model, not the adequacy of its record names.

**Proposed direction:** use a bounded, model-owned relation-operation compiler and shared prepared selectors. Let its lowerings use topology libraries, transfer/fixpoint kernels, indexed native queries or relational operators according to their contracts. Retain ordinary functions where they already supply a complete operation. Hashing should support selected reuse boundaries and persisted fingerprints; it is not the organizing principle of the semantic model, a replacement for dependency completeness, or a reason to replace BLAKE3 identities.

This is a review of architecture and alternatives, not implementation authorization or release qualification. No product code, dependency, operator state or repository file was changed by the reviewer. No tests, real-library journeys or benchmarks were run. Source inspection establishes the diagnoses; the replacement and its runtime benefit remain **Proposed**, with selected library interfaces **Interface-checked**.

## Findings: work granularity and operation authority

<a id="F01"></a>
### F01 — Shared edge preparation still leaves repeated one-root traversal, planning and rich hydration

**Implemented/source-inspected diagnosis, 2026-10-09.** Relevant foundations are FP-03/06/07; supporting rules DP-08/10/16/20 and CI-07/08; A4 is violated for the overlapping-root scenario.

`NominalClosure::prepare` already distinguishes indexed native references from compact bulk contextual adjacency, retains exact providers and charges its state ([consumed_rows.rs:403–586](../../../crates/cpg-core/src/consumed_rows.rs#L403)). It is not uniformly a full rich-source scan. `PreparedEdges::grain_roots` nevertheless constructs a fresh selected-root query, visited/pending state, frontier accesses and temporary key/table bindings for each requested grain ([consumed_rows.rs:960–1160](../../../crates/cpg-core/src/consumed_rows.rs#L960)). Aspects invokes `grain` for each root and then `load_data` queries every declared input; execution fidelity similarly invokes an invariant check and ordered input streams per root. Support admission already batches up to 128 compatible roots, showing that physical root grouping is distinct from semantic identity ([scoped_admission.rs:276–329](../../../crates/cpg-core/src/scoped_admission.rs#L276)).

A class grain needs field initializer metadata, while the separate field grain reads that initializer again; roots also share qualification, provider/run/coverage and ancestor/type premises. The source-local `ClassInventory` builds compact references and coverage adjacency from supplied data, then allocates per-class visited state and computes an exact inventory digest ([symbolic_fields.rs:403–544](../../../crates/lctx-model/src/domain/normalized/symbolic_fields.rs#L403)). Faster hashing cannot remove those repeated closures, query planning or decoding.

The consequence is avoidable work proportional to root count times shared selected premises/planning, even where the immutable dependency set is unchanged. The present per-grain lifetime usefully limits rich live state. That benefit does not require separately reconstructing overlapping compact selection and decoding stable metadata for each owner.

**Proposed correction:** the compiler/access owner should prepare root sets and common nominal/reference/metadata indexes once over their valid completed inputs, batch physical demand where compatible, and retain owner-specific partition/membership labels. Hydrate shared premises once per bounded batch or retain compact handles; execute each domain result against its exact owner partition. A huge union that widens validity, retains every rich payload or makes all roots one admission outcome is not a conforming remedy. High-degree roots can remain separate/streamed where that controls live state. Simplest alternative: improve `PreparedEdges` and scoped loaders directly without a new operation graph.

**Closure:** a traced overlapping assessment/class/field case shows one preparation and bounded shared demand, exact per-owner results, unchanged negative coverage and same-key conflict behavior; an outlier shows bounded combined live state and cancellation/drain. Compare independent expected membership and clean computation, rather than only the number of helper calls. Measurements are required only for a quantitative improvement claim.

**Disposition:** this review retains **Deferred — architectural target decision**, until subsequent plan creation schedules the correction. Existing repeated-access/timeout obligations remain at the populated companion §6 and persisted coordinator; this finding neither renames nor closes them. Responsible components: `cpg-core` selection/normalization/admission and the owning model kernels. Trigger: selecting the relation-operation/prepared-selector redesign or adding another materially overlapping consumer.

<a id="F02"></a>
### F02 — Class/body and coverage scope semantics are independently interpreted in model and compiler selection

**Implemented/source-inspected diagnosis, 2026-10-09.** FP-01/02/03/04/05/06 and DP-01/06/08/17 apply; A1/A2/A3 are violated in the operation-scope extension/substitution scenario; G1 fails for this scoped duplicated meaning.

The model's `AspectScope` declares three roots, advertised admission roots and typed memberships ([callable_aspects.rs:1169–1285](../../../crates/lctx-model/src/domain/normalized/callable_aspects.rs#L1169)). It does not carry the complete body-domain and contextual coverage operations its physical selector requires. The compiler independently authors span/structural-path containment, initializer/class expansion and qualification-to-coverage scope/context joins ([scoped_aspects.rs:106–183](../../../crates/cpg-core/src/scoped_aspects.rs#L106)). The model independently uses the same containment predicate in `contains`, repeats body expansion in `ClassInventory::for_class`, and reconstructs qualification(scope, context)→coverage edges in `ClassInventory::prepare` ([symbolic_fields.rs:355–364,430–478,528–544](../../../crates/lctx-model/src/domain/normalized/symbolic_fields.rs#L355)). These are selection meanings governing the class inventory and source-field property premises, not merely backend SQL spelling.

Changing which body events or contextual coverage belong to an operation requires understanding and updating both interpretations. Moving selection to native SurrealQL or a compact graph kernel cannot consume a sufficient model-owned scope contract; the substitute must recover domain rules from the adapter. Existing typed records and shared invariant factories do not repair this operation-model gap. No current wrong field result or known divergent predicate is alleged: the architectural failure is separately mutable meaning and required propagation.

**Proposed correction:** the normalization/model owner should define the complete relevant scope operation: actual assessment/field/class root, body/initializer membership, forward versus owned reverse edges, exact context/coverage expansion, required missing/advertised roots and outcome assumptions. Ordinary reusable domain functions may suffice; a small typed operation composition is justified where multiple lowerings must inspect and compose it. Both the inventory computation and physical selector realize that owner, with the compiler deciding indexing, batching and query layout. Remove independently authored selection meanings once consumers migrate.

This does not combine producer and admission into a circular oracle. Admission must still validate actual rows and exact stored membership under the owned contract; detached import must still detect omitted/foreign premises. Independent known answers must challenge the authoritative meaning, including a nested class, same-span different structural role, foreign context and missing advertised source. A shared declaration can derive mechanical implementations without deriving every expected answer from the same code.

**Closure:** change one relevant body/coverage membership rule at its owner and inspect both computation and selected admission/native lowering; independent cases establish complete intended domains and no foreign-context leakage. Replacing the selector mechanism requires no new independently authored domain interpretation. Responsible owner: normalized callable/source-field model with `cpg-core` scoped adapters.

**Disposition:** **Deferred — required target decision**, source-owned here until scheduled; revisit on the next callable/source-field scope extension or mechanism substitution. This finding is not a claim that every scope family has the same defect. Existing compiler/reference closure controls and their current dispositions remain independent.

F02's complete operation contract enables a sound F01 batch boundary. It is lower in immediate workload consequence but a prerequisite to sharing work without changing meaning. F01 also has narrower remedies that do not require a general compiler. Neither finding establishes that cross-run caching is necessary.

### Library fit at resolved versions

The repository locks DataFusion 55.1.0, petgraph 0.8.3 for product graph work, fixedbitset 0.5.7 on that route, SurrealDB 3.3.0, Salsa 0.28.5, xxhash-rust 0.8.19 and twox-hash 2.1.5. Other transitive petgraph/fixedbitset versions in Cargo.lock are not interchangeable product types. Capability skills were checked against these pins. The locked hash crates are transitive with XXH64/XXH32-family features, not an existing project XXH3 execution layer. No dependency change is proposed merely because a reference names a library.

Native `TableProvider` already advertises exact supported filter pushdown and projects selected fields (`lctx-surrealdb/compiler_provider.rs:179–222`); `select_table`/`select_field_table` retain charged key owners and enforce atomic-frontier conditions (`:68–132`). Thus native/DataFusion fusion is a real existing lever. A new graph program must preserve useful pushdown rather than replace every join with Rust loops.

The current graph is a multigraph with canonical entity and ArcId weights, private dense indices and borrowed visit views. petgraph 0.8.3 `Csr` does not preserve parallel edges and has a narrower visit-trait surface; a candidate must check each selected algorithm. The shared rust-graphs Csr contract and locked source establish the multiedge limit. A CSR replacement is eligible for a declared quotient/projection with a separate exact ArcId/evidence mapping and required reverse view; it is not a transparent substitute for the canonical multigraph. Bitsets or epoch-mark arrays help repeated dense visits; their universe/length must be owned, not inferred from bit equality. Existing petgraph visit maps already make a blanket “all visited sets need hashing” diagnosis wrong.

Salsa 0.28.5's locked `src/function/backdate.rs:12–54` uses output equality subject to cycle/provisional/durability restrictions. Its `persistence` feature and `src/database.rs:167–238` expose serialization/deserialization with exclusive access and worker cancellation. The offline skill is 0.28.4, so its tested receipts are historical/version-scoped; current 0.28.5 source establishes interface availability, not this project's persistence correctness. The supplied graph reference's unverified absence of Salsa persistence is not a rejection reason. Its serialized ingredients do not independently establish semantic compatibility or external admission. The workspace currently omits the optional persistence feature. At this pin input slots are not deleted/reused (`src/input.rs:487`), and mutation cancellation waits for cloned database handles (`src/storage.rs:153–191`): deletion representation and handle lifetimes need an explicit design, even when result backdating is sound.

For finite relation fixpoints, datafrog/ascent are considered through the pinned reasoning skill as candidates; neither is currently a product dependency. Differential dataflow/DBSP are discovery candidates from the supplied reference, without a qualified project integration. Multi-relation monotone delta rules can justify such engines; source-field eligibility, negative coverage and custom BDD transfer cannot be relabelled as ordinary reachability or positive closure. Datafrog 2.0.1 variables are monotone sorted sets and its antijoin uses a fixed negative relation; Ascent 0.8.1 offers generated indexed SCC/lattice and stratified-negative execution, but a retraction contract has not been established by this review. A snapshot fixpoint is feasible; incremental deletion/negative updates need another specified mechanism or fresh recomputation. Partial results after timeout cannot be admitted. A library choice must include those remaining semantic gaps and its generated Rust/build burden.

## Hashing: jobs, equality and graph synergy

| Job | Current/eligible mechanism | Required separation |
|---|---|---|
| In-memory tables | Exact key equality; ordered maps where order is useful; dense indices/bitsets before changing hashers; dedicated map hasher only on suitable trusted keys | `ChargedMap` is a BTreeMap (`charged.rs:81`), not an XXH target. Hash-table hashes never become persistent identity. Random hash iteration must not affect canonical output. |
| Preparation/result fingerprints | Existing exact completed identities; proposed role-framed canonical fingerprints of only the inputs affecting preparation or result | Prepared topology/program equality differs from result equality, attribution and complete build provenance. Equal semantic output does not authorize stale spans/support. |
| Durable identity/integrity | Existing BLAKE3 nominal keys/full content and actual-state checks | Keep model namespace/type framing and collision/conflict checks. XXH cannot weaken import/publication integrity or mint authority. |
| Sketches/bucketing/partitioning | Optional seeded/versioned fast hashes, only for a named approximate or routing consumer | Bloom/WL/sketch match is a prefilter/heuristic, not complete absence, exact graph identity or semantic proof. No current need establishes automatic adoption. |

[identity.rs:20–77,100–182](../../../crates/lctx-model/src/domain/identity.rs#L20) distinguishes 16-byte nominal BLAKE3-derived Id from 32-byte content hash and caller-selected Rust `Hash`. [graph.rs:4054–4097](../../../crates/lctx-model/src/domain/graph.rs#L4054) orders canonical key plus content, detects conflicting equal keys and hashes family content independently of IPC framing. These guarantees should survive any implementation change. Equality uses the declared full value/key where required; a noncryptographic fingerprint match alone is not an exact-equality contract.

**Graph alone:** shared operation shape, compact adjacency, batched roots, indexed membership and SCC schedules remove crossings/reconstruction without persistent memoization. **Hash alone:** a cheap precheck or persisted key can avoid loading a prior value but cannot improve missing adjacency, owner batching or hydration; key construction may repeat the work supposedly avoided. **Combined:** a prepared graph/program can retain canonical dependencies and selected result fingerprints, propagate only relevant edits, and stop at substitutable values. The benefit requires a reuse lifetime and complete dependency contract, including membership, deletion, missing lookups and negative domains. Exact in-process equality/revision cutoff remains a simpler alternative.

Do not use semantic call edges as an operation dependency graph by default. A dependency can include source attachment, absent member, provider coverage, policy, model or schema/code revision even when no call edge represents it. A span-only edit may preserve a compact computational shape while requiring new occurrence/support/output identities and current attribution. A provider/model/policy change invalidates the consumers whose contracts observe it; it need not poison every topology preparation with complete provenance.

A topology fingerprint includes nominal vertex membership, declared typed/directional arc membership, multiplicity/self-loops and policy. A cyclic content key includes internal role-labelled edges and external dependency associations as well as members. SCC merge/split edits require topology/SCC recomputation or a specifically qualified dynamic algorithm. A DAG scheduler's cycle refusal and a transfer kernel's valid fixed point are different outcomes.

The supplied [Fast hashing for graph systems](../../graph_hashing_reference/Fast%20hashing%20for%20graph%20systems.md) and [xxhash-rust and twox-hash companion](../../graph_hashing_reference/xxhash-rust-and-twox-hash_2.md) are useful research evidence, not drop-in project contracts. Their host timings, topology fixtures, versions and simplifications are not library-context speed claims. Several recipes fail legitimate project requirements if transferred literally:

- `canon/v1` NFC/default numeric normalization would change the project's exact Utf8Text/original-byte semantics; do not adopt it as the canonical model encoding.
- Endpoint-pair/lightweight edge dedup discards real parallel assertions and evidence. The model's relation identity must govern dedup.
- `deep_hashes` at graph reference lines 1813–1832 hashes SCC members and deduplicated child hashes without independently encoding internal edges. If node content stays unchanged while internal topology changes within the same SCC, the key can stay unchanged. Stable member identity does not repair omitted edge meaning.
- The database memo recipe at lines 1572–1595 sorts closure content hashes without their identity/role associations. Swapping equal-sized per-node contents can preserve that multiset while a context-specific answer changes.
- The illustrative call index drops ambiguous/unresolved calls (line 1849); it cannot support a complete negative dependency claim.
- Reference whole-graph `algo.*` examples are ArcadeDB, not SurrealDB. The reference uses SurrealDB 3.3.2; this workspace locks 3.3.0. Its native behavior/timing is not automatically transferable.

These are limits of candidate recipes, not new defects in the existing repository. Exact canonical encoding, equality checking and preserved uncertainty are prerequisites to adopting any fast fingerprint. The hash companion's warnings about `Hash` versus explicit bytes, seed/secret configuration, streaming state and SIMD deployment inform a future selected implementation; no global hasher swap or CPU target change follows from this review.

### Pinned fast-hash implementation choices

Both libraries support explicit one-shot bytes and streaming; neither makes Rust `Hash` a portable persistent encoding. Encode with the model's exact framing and ordering first. A fast digest may select a collision bucket, speed a mismatch precheck or route work; exact equality/full digest and the actual-state authority decide reuse. The 16-byte nominal Id and full BLAKE3 content identity remain unchanged.

| Contract | xxhash-rust 0.8.19 | twox-hash 2.1.5 | Consequence for these opportunities |
|---|---|---|---|
| APIs and feature selection | `xxh3_64` / `xxh3_128`; seeded/secret variants; `Xxh3Default` and `Xxh3` streaming expose `digest`/`digest128`; `Xxh3Builder` / `Xxh3DefaultBuilder`. Features default off; enable `xxh3` deliberately. | `xxhash3_64::Hasher` (`XxHash3_64`) and corresponding 128-bit type provide `oneshot` variants; `RawHasher<S>` offers explicit storage. Separate `xxhash3_64`/`xxhash3_128` features; defaults also enable `random`, XXH32/64 and `std`. | Existing transitive feature selection does not authorize assuming XXH3 is available. Select only needed APIs/features rather than adding the defaults blindly. Compare direct one-shot compact keys with building a streaming hasher for every lookup. |
| SIMD deployment | Compile-time target features select AVX-512F, AVX2, SSE2, NEON or wasm `simd128` where supported; no runtime CPU dispatch. | With `std`, long-input x86_64 runtime dispatch selects AVX2, then SSE2, then scalar; aarch64 has NEON. No AVX-512 path at this pin; normal no-`std` route is scalar. | Bulk canonical buffers may justify dispatch choices; short inputs through the XXH3 ≤240-byte paths do not gain from long-input SIMD. ### Build, preparation, execution and persistence are separate costs

The proposed compiler must be evaluated through intent construction, canonicalization/indexing, plan preparation, conversion/hydration, kernel execution, retention, final admission/sealing and rebuild/cleanup. A compact graph can improve repeated execution while making cold construction or retained state more expensive. Hash-consing can make equality cheap where substructure is shared, but introduces interner lifetime/GC and admission overhead where sharing is low. The existing BDD/typed identity sharing should be inspected before introducing another interner.

Rust code generation is a separate consideration. Current `NativeCalls` erases requests before shared scheduling (`native_calls.rs:29–65`); C1 and Structural use contained phase/typed adapters (`catalog_evidence.rs:297–365`, `structural.rs:234–255`). The compilation/coroutine plans retain historical compiler captures and their uncompleted enclosing acceptance. A new operation compiler should use a bounded program/shared execution loop with thin contained typed leaves where it reduces concrete orchestration variation. It should not expand one generic async branch per relation, decoded row or plan alternative inside one large enclosing future. Native code generation or expression specialization is eligible only when repeated execution earns its compilation cost. This source reasoning identifies a design risk; it does not establish a new LLVM cause or a measured improvement.
