# SurrealDB lifecycle: diagnostics, retention and capability integration

**Proposed, 2026-10-12.** Companion to the [coordinator](surrealdb-lifecycle-plan_2026-10-12.md), which owns all execution status and receipts. This document develops F04, useful lifecycle inspection and explicit fit decisions for every conditional avenue in the [review](../design_review/reviews/design_review_surrealdb-lifecycle-target_2026-10-12.md). No probes or product tests were run during authoring.

## 1. Model and foundation assessment

Keep execution outcome, retention and semantic eligibility separate. Native/model completion already carries local terminality, remote certainty, storage outcomes, committed effects and failures. Host fixtures observe those receipts separately from child cleanup. Native holds/incarnations/eras and publication/reader pins protect shared content; filesystem admission and executable-generation dependencies protect different host objects. These are useful foundations, not one interchangeable lifecycle status.

The current durable signal receipt converts finalization failures into step plus human text. Typed native request, attempt and lifecycle wrappers carry identities/generation/era that are lost in this projection. Correct that seam, not the entire outcome model. The review does not establish unsafe deletion or a missing-receipt defect in all owners.

The target answers: which owner blocks an operation, what is known, what inspection/recovery route is valid, and which action can actually release it? Build on existing service, fixture, run/evidence and native inspection routes. A composed observer does not become authority for the objects it describes. No new universal registry, queue service, mandatory tracing platform or second scheduler is needed.

## 2. LO00 — typed persisted failure causality

Define a model-owned diagnostic projection with stable failure class/code, stage, bounded secondary causes, optional relevant identities/issuance and a safe recovery/inspection route where the owner knows one. Native projection enriches known request/attempt/lifecycle wrappers; model code must not depend on native implementation types. Human error text remains presentation, not the machine protocol. Preserve the original typed in-process error and source chain.

Before an operation/attempt exists, represent identity as absent. Unknown third-party causes are explicitly opaque; do not guess IDs from strings or make every foreign error serializable. Bound cause depth/size under the existing receipt/output policy and mark truncation without implying the cause ended. New codes follow append-only codebook rules where applicable. Recovery routes identify an owner/action with scoped arguments; they do not grant destructive authority or trigger effects on inspection.

Enrich the current failure entry additively where its existing envelope permits, retaining step/error presentation and independent local/remote/storage/committed axes. Use one current writer/reader contract. Do not add a historical receipt translator or require old proof files to exercise it. If a current envelope change is necessary, pivot its actual producers/consumers together and regenerate fresh controls; old datasets/evidence are not a compatibility requirement. Unresolved actual live ownership cannot be released merely because a diagnostic field is absent.

Migrate native signal receipt writing, fixture status/evidence projection and agent-facing inspection/report consumers that currently expose only failure text. Nonempty failure lists or unknown remote outcomes remain protected according to actual completion, not a newly parsed code. A successful command body with failed cleanup remains a separate outcome. Do not turn F04 into a claim that every G3 validity gate was previously broken.

**Completion:** produce a real persisted native request failure with generation/era and nested finalization failure; read it through the actual host/report path and verify independently specified fields. Include pre-admission opaque failure, absent identity, truncation, committed effects with failed cleanup and Unknown remote outcome. Round-trip cannot silently turn any outcome into success. A copied test-only serializer is not evidence for the production receipt. This closes F04 after producers and consumers migrate.

## 3. LO01 — composed read-only lifecycle inspection

Extend existing status/inspection routes to relate target/service generation, host attachment/run, native request/attempt, exact view/publication/pin, backup/retirement and retained current evidence when those identities actually exist. Each entry names its authoritative owner, observed outcome, uncertainty and next valid inspect/recovery route. Keep observation date/source and unsupported/not-inspected states visible. A schema-only beta target has host/tool ownership without invented product admission or native publication.

Do not infer database release from dead processes, logical DROP, age, empty host borrower lists or missing receipt files. Do not query a closed installation by secretly bypassing maintenance or open admission simply to populate a dashboard. In that situation show host information and the valid maintenance diagnostic route; an unobserved native state remains unobserved. Native terminal phases must be emitted by actual owners, not inferred from progress messages.

Support on-demand query plans, index state and coarse native/host phase/transport correlation. EXPLAIN output is diagnostic evidence with its actual version, not an unversioned product wire format. Logs/reports are fresh generated products with named consumers; historical evidence is not carried into the target merely for comparison. Generic database tools operate on explicit authorized targets with least privilege. Domain MCP operations retain publication-scoped admission/evidence contracts.

**Completion:** a fresh run with command-terminal/native-unknown and another with committed effect/cleanup failure display the exact blocking owner and safe route. Successful disposal is independently shown only after the owning cleanup acknowledges it. Missing target, closed maintenance and diagnostic permission refusal remain truthful. Secret credentials are absent. The composed view neither mutates state nor changes which owner decides release.

## 4. LO02 — conditional capability decisions

The operator chose **decide each fit**, not blanket adoption. The table names decision scope, current source-grounded direction, consequential unresolved evidence and dependencies. Directions are Proposed decisions until supported assessment is recorded; no substitution is already Tested. Use [versioned research](../design_review/evidence/2026-10-12_surrealdb-lifecycle-target/library-contracts.md), current source and the exact beta/SDK/server profile. Use Context7 first for new documentation, then pinned primary source where current docs differ.

For every row, record the actual consumer, existing complete route, candidate mechanism, meaning/finality/resource/operational differences, decision and reconsideration trigger. Source is sufficient when it settles fit. A needed probe uses LD02's owned target, fresh data and normal concurrency; no shared/operator service or historical capture is required. Negative search alone is not proof of absence.

For an adopted mechanism, add its bounded implementation/consumer migration and verification to this companion and coordinator §4/§6 before execution. Resolve changed rule impacts explicitly. Adoption must not introduce a new dependency on old data/evidence, delay the highest-priority F01 repair, or hide unbounded movement behind a small returned limit. A rejection/deferral closes only the fit decision; it cannot close an unsatisfied mandatory finding.

### Investigation results must be usable

A decision cannot read merely “investigate later.” State the question, evidence examined, which supported outcome follows, and what implementation is then required. For C01/C08 and other correctness-sensitive substitutions, uncertainty means retaining the established protected route while the decision package gathers evidence. No unsupported native primitive is allowed into a production prerequisite. If evidence disproves the benefit or shows no current consumer, record that result and a concrete future trigger instead of inventing infrastructure to use the feature.

A retained-witness decision belongs to LN05; this document does not create another witness owner. Beta feature/API correctness belongs to LD00–LD03. Common native definition/session/ownership premises are settled once and linked, not independently redefined for each capability.

## 5. Scenarios, acceptance and cutover

Use fresh current examples to assess the composed target:

- Adding deployment evidence extends the model/fidelity/recovery declarations and selected hydration; it does not create an automatic queue, table and lifecycle job for each family.
- Adding a pinned release keeps earlier publication meaning stable while it has a current consumer. When the operator elects hard regeneration, drain readers and rebuild rather than retain obsolete historical copies by default.
- Large originals, overlapping views and high-degree hubs keep independent completeness and byte bounds while avoiding repeated observation/crossings.
- Concurrent equal compiles converge without changing eligibility; serving and backup keep exact selected owners.
- Publishing B while A is pinned preserves A only for that active reader/backup consumer, then explicit retirement can release it. There is no perpetual historical baseline requirement.
- Crash after native commit/before host acknowledgement retains truthful uncertainty and exact current recovery/discard scope; a freshly regenerated target does not rewrite the old operation into success.
- Schema/tool setup or cleanup failure leaves a whole owned target identifiable even without a beta report; checked shutdown/discard can dispose it without saving its contents.

LC01 integrates the required journeys and adopted capability controls; no full observability, historical benchmark or unrelated quality backlog becomes acceptance by association. LC02 replaces only actual selected project state under quiescence and retires obsolete data, code and evidence once their live consumer ends. LC03 updates the old plans after this track is fully delivered. All LO status, outcomes and exact receipts remain solely in coordinator §6.
