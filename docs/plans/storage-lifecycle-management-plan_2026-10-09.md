### 3.2 One small policy capability, existing semantic owners

Add a standard-library Python management capability, exposed through `just storage`, with three responsibilities: validate/evaluate lifecycle rules, inventory declared objects, and dispatch approved effects to their owners. Use ordinary modules and a fixed set of owner integrations, not a plugin framework, daemon, database or generic workflow engine. Owner facts remain with run, fixture, environment, worktree, acquisition and profile operations; the manager combines those facts with storage policy and explains a disposition.

The repository's `.config/storage.toml` owns category defaults and producer bindings. A host configuration under `${XDG_CONFIG_HOME:-~/.config}/library-context-storage/config.toml` names this repository's checkouts and optional storage destinations. It contains paths and policies, never credentials. Stateful descriptors, operation journals and locks live outside disposable roots under `${XDG_STATE_HOME:-~/.local/state}/library-context-storage/`, mode0700. A `LCTX_STORAGE_CONFIG` override selects the host configuration; it does not alter Cargo/uv cache keys. Do not export new per-run Cargo path variables for ordinary shared builds.

Host membership and object records are justified by concrete cross-repository consumers and by the need to survive parent worktree deletion. They are not a second execution-status ledger. Store one record per independently disposable group, such as a task build root or run component, not per compiler artifact. Inventory caches are derived and never supply deletion authority.

Validate schema/category/capability names, nonnegative durations, explicit owner bindings and physical scopes before effects. No arbitrary shell commands, executable policy expressions or glob-based deletion rules are accepted. Root overlap requires a declared parent/component relationship; otherwise protect both and report the conflict. A configured root/override changing does not transfer an existing descriptor's identity or obligations to the new path. Unknown schema, missing owner or contradictory membership fails closed for the affected scope. Policy changes apply prospectively; shortening a recorded temporary-use deadline requires an explicit owner update, not a timer reinterpretation of old metadata.

### 3.3 Lifecycle meaning and authoritative decisions

An object descriptor records schema1, stable object ID, category, semantic owner/reference, physical root or relative component, creation identity, sharing scope, consumer obligations, policy deadline, and any archive identity. The owner supplies current execution/cleanup/use facts at evaluation time. Do not copy mutable process state into a competing record. Physical identity includes device/inode and a producer-created nonce; paths alone are insufficient. Descriptors for unmanaged legacy roots begin protected, without inventing a historical creation identity.

Each obligation names its consumer, required availability (`immediate-use`, `raw-replay`, `restorable-replay`, `cited-report`, `receipt`, or `external-owner`), specific replay operations where relevant, and release condition. Dependencies include tools/sidecars required for replay and retained content inside a worktree. Opaque historical retention becomes an unresolved hold; missing metadata is not an empty consumer set. Current citations found by scanning docs are useful reconciliation evidence, but removal of a link does not itself release a declared obligation. Before retirement, reconcile current tracked consumer references once per sweep/explicit operation; a newly found undeclared reference protects the object as unresolved until its owner establishes the proper obligation. An unrecognized citation must not become silent permission to delete.

The governing operation returns one of `active`, `warm`, `retained`, `unresolved`, `eligible`, `archived`, `retired`, or `external`, with reasons and observations. Execution state, cleanup certainty, raw availability and policy disposition remain separate facts. Eligibility requires all of: known owner and physical scope; owner-declared release or expiry of a declared temporary-use obligation; no surviving consumer/dependent object; confirmed cleanup where applicable; no active use; and expired policy grace. Neither pressure, mtime nor missing process references can manufacture release.

Producer policy deadlines are explicit obligations, created from a known event such as confirmed cleanup or task release. They differ from guessing last use from file age. Retaining/reusing a component establishes an obligation before accessing it and prevents its deadline from expiring underneath that operation. Canonical inputs, warm native caches and external product state have no automatic age deadline.

### 3.4 Safe use, retirement and crash recovery

Managed-use and retirement operations share a per-object lock outside its removable directory. Ordinary use acquires shared ownership; maintenance attempts exclusive ownership without waiting and skips busy objects. Parallel users remain parallel. Shared Cargo, native package caches and current checkout targets are protected roots and need no new storage lock on ordinary bare commands. A root selected for automatic retirement is an explicit managed exception: `just env -- COMMAND`, worktree-owned commands, profile readers and maintenance acquire its object ownership for the complete operation.

Admission is hierarchical: creation, use, retain/release, selector changes and descriptor publication acquire shared admission on every enclosing managed lifetime before their object lock. Parent removal takes that parent's exclusive admission, which excludes new child creation/holds/use until removal ends. Descendant protection is therefore not merely a snapshot checked before deletion. Acquire storage admissions in stable outer-to-inner order, with disjoint roots ordered by canonical object ID, then the existing native resource order (all environments by path, then extension directories), then owner/record mutation locks. Nested calls reuse validated inherited admissions instead of opening competing flock descriptors; shared-to-exclusive upgrades are refused. Resolve the required ancestry before native ownership and revalidate topology after admission; retry changed topology without effects. Parent retirement tries native exclusive ownership without waiting and skips a busy parent. Adoption protects preexisting unmanaged holders until their exposure is resolved. Tests must challenge both the exclusion and the lock order with nested/reentrant owners.

For new isolated roots, the worktree/run owner allocates a unique lifetime ID and a stable path for that lifetime, records the selection once, and acquires use ownership before launch. Never recycle a released physical root name or change paths per command. Keep existing active paths untouched during adoption. Shell-only environment exports cannot claim this use guarantee; deliberate bare overrides outside managed ownership remain protected/unresolved until an explicit quiescent adoption resolves their exposure. Do not claim a `/proc` scan closes the race with a future unmanaged writer.

After exclusive ownership, re-read owner facts, consumer obligations, selectors, policy revision and physical identity. Validate the entire removal boundary: an enclosing worktree/root is ineligible if any descendant has a hold, unresolved cleanup, warm lifetime or unknown content. Source dirtiness and unintegrated Git work remain independent blockers. Recheck all Python/service environment holders, including vLLM; never signal a process as part of a sweep.

A retirement journal identifies object, policy/owner observations and physical identity. Use a validated same-filesystem rename into an owner-controlled retirement area, then descriptor-relative deletion; do not follow symlinks, cross mount boundaries or accept an arbitrary path supplied by a stale preview. Producer acquisition checks the retirement state under the same lock. A crash before rename leaves the original protected; a crash after rename resumes deletion of that exact identity. A new object at the former path is never a continuation of the old operation. Completed retirement leaves a compact tombstone while references remain; otherwise expire it after90days. Failed/unknown cleanup remains protected and recoverable through its owner, not the deletion journal.

This is a guarantee for cooperating managed lifetimes, not for arbitrary commands that bypass ownership. Default protected caches preserve bare-tool freedom. Native owners keep their own locks and deletion semantics; the storage manager does not substitute `rmtree` for those operations.

### 3.5 Library fit, alternatives and execution cost

**Interface-checked, 2026-10-09:** Context7 discovery was checked against exact-version primary documentation/source. Cargo's [pinned clean implementation](https://raw.githubusercontent.com/rust-lang/cargo/3d7cf6e93/src/ops/cargo_clean.rs) removes both target/build outputs without taking its build lock; it is unsuitable as this plan's concurrent retirement primitive. Its [global-cache GC controls](https://github.com/rust-lang/cargo/blob/3d7cf6e93/doc/book/src/reference/unstable.md#gc) govern downloaded/source material, not an application-managed LRU of compiler intermediates. [sccache0.17 Rust support](https://github.com/mozilla/sccache/blob/v0.17.0/docs/Rust.md) excludes incremental compilation and linker-producing crates, so retaining sccache cannot replace the workspace incremental/final-output caches.

[uv0.12.22 cache contracts](https://github.com/astral-sh/uv/blob/0.12.22/docs/concepts/cache.md) require native cache management; direct removal inside its cache is unsupported. Native prune can remove centralized environments, so safety in uv's terms does not alone meet immediate-availability requirements. Preserve the existing acquisition copy-isolation contract and ordinary cache placement; moving an environment away from its cache can also change link/copy behavior. Do not apply a generic deduplication or relocation optimization across these meanings.

Native mechanisms alone cannot express a cited capture's lifetime, retained content inside a worktree or a shared skill's consumers. A small declarative policy module plus owner operations supplies that concrete gap. Age/size-only `rm` is simpler but loses those meanings; a generic cache daemon/framework duplicates native owners and adds unnecessary service/registration machinery. The selected state files and timer are limited to actual shared participation, independently disposable groups and crash recovery. A new category adds its producer binding and policy; changing a native cache mechanism does not replace run/evidence semantics.

The workload is repeated local edit/build/test, concurrent checkouts and occasional large diagnostics. Keep common observations at object/owner granularity, reuse unchanged metadata and perform full accounting only explicitly. Do not hash hundreds of GiB on each status, build or sweep. Content digests are necessary at archive publication/restore boundaries, not repeatedly during ordinary observation. Full verification of an archive before source release is deliberate work purchasing replay assurance; it remains outside healthy-build critical paths. Benefits are structural hypotheses, not measured latency or compression claims.

## 5. Evidence portability and archive substitution

### 5.1 Preserve capability, not merely bytes

Implement profile-owned `archive` and `restore` operations for **closed** evidence, using a local filesystem destination and `.tar.zst` containers. Existing GNU tar1.35/zstd1.5.7 are discovery leads; qualify the exact installed contracts during SM4. No cloud service, remote transfer, deduplication store or archive daemon is required. Archive destination is unset by default; absent destination means keep raw local and report capacity, not discard it.

An archive covers raw files and every required sidecar: run/profile/unit identity and outcome records, provenance/source digest and captured diff, collector metadata/logs, closed-chunk evidence, self-profile data, mono-item and pass-timing output, copied Cargo session receipts, reader identities and cited derived reports. Preserve opaque raw bytes and original logs. Manifest entries use bounded relative paths, lengths, digests, modes and relevant timestamps; record logical run/unit IDs, original root and format/tool identities. Do not promise a source rebuild from a capture that never contained the complete source tree. Preserve its actual report/replay capability and declared limitations.

Declare replay capabilities separately: compiler summary/timeline, sampled symbolized report/import, and disassembly/source annotation. Sampled raw bytes and reader versions alone do not preserve symbolization: exact build-ID-matched executables/shared objects, debug information, and source where the promised annotation requires it are dependencies. Use the installed native perf build-ID/archive/cache/symbol-root facilities to collect and resolve this closure, rather than reconstructing ELF dependency semantics. Native `perf-archive(1)`, `perf-buildid-cache(1)` and `perf-annotate(1)` document these inputs; qualify the installed contracts in SM4. Include required immutable objects/debug/source in the bundle, with digests/build IDs and a bounded symbol-root layout. Exact reader tools may remain protected installed dependencies, explicitly identified in the manifest. Do not assume an ambient toolchain, checkout `target/`, `.debug` cache or original source path will survive retirement. Missing dependencies make the affected capability unresolved/unavailable and prevent replacing a consumer's current raw obligation with an unqualified archive. Narrowing a named capability requires that consumer's explicit release/change, never silent fallback to unsymbolized reader success.

### 5.2 Make readers independent of physical placement

The profile owner resolves raw locations relative to the current evidence root. For existing captures, build an owner-validated relocation manifest from the exact original root and unit identities. Translate only a recorded original-unit prefix into a bounded relative path; reject escapes and unrelated absolute paths. Interpret closed-chunk announcements through this resolver while preserving the original log bytes and collector signal/partial meaning. No generic text rewriting of perf data or paths.

Regenerate uncited derived reports after relocation. Rebuild symlinks locally and invalidate receipts containing old output paths. Report cache validity includes raw identity, exact measureme/perf reader identity and relevant settings; sampled reports must stop using size/mtime alone as complete reader identity. Preserve cited reports in the archive as historical observations, distinct from newly regenerated output. `status` remains read-only; `report/view` may produce explicitly derived files under owner use ownership.

Before replacing local raw with an archive, read back the entire archive, verify manifest digests/scope and exercise the declared report capability with exact readers and the bundle's symbol-root resolution. Test with the original source/output/debug-cache locations unavailable using disposable fixtures or an isolated test namespace, without removing live operator/toolchain caches. Check meaningful symbols/annotations and completed-chunk membership, not only reader exit0. Publish archive manifest/receipt atomically, then release only the redundant local raw component through the normal retirement operation. A successful compression process alone is insufficient. Partial/truncated/unreadable captures retain their actual state; do not call them completed merely because archival finished.

Restore into a new owned staging directory, validate archive entries without accepting absolute paths, traversal, external links or filesystem-crossing extraction, and verify all bytes before publishing the restored evidence root. Refuse conflicting object identities. Restore grants a temporary raw-use obligation for14days or a named consumer hold. Automatic reporting never restores a large archive silently: status says `archived`; explicit restore performs the effect. Archive remains protected until consumers release or a verified replacement exists.

Default automatic maintenance does not archive cited evidence. An operator can explicitly set a consumer's required capability to `restorable-replay` and select a qualified destination, after which its owner can archive automatically. `immediate-use`/`raw-replay` consumers keep local raw. Archiving on the same filesystem may reduce bytes through compression, but only observed allocation can support a saving claim; relocation alone frees no filesystem capacity. During creation/verification both copies may be required. Failure or insufficient destination space leaves original evidence intact.

## 6. Repository ownership, interfaces and automatic operation

### 6.1 Repository checkouts and legacy adoption

Configuration names this repository and its Git-registered checkouts, including the preserved
PC3 worktree. Missing/unreadable checkouts protect uncertain content. Registration never expands
the task to another repository. Central skill stores and their contents are outside this work;

### 6.2 Public management interface

Provide `just storage OPERATION`; use the existing pinned Python3.14.7 with standard-library-only observation, launched independently of the checkout environment, so a missing project environment does not block repair. There is no Python3.12 helper or compatibility requirement. Commands accept `--json`, explicit `--repo PATH` where applicable and `--scope repo|host`; default scope is the current repository, and shared effects require host scope. Native owner readiness is observed, never silently synchronized.

| Operation | Contract |
|---|---|
| `status [ID]` | Read-only policy disposition, current owner/consumer reasons and inventory freshness. No re-report, restore or cleanup. |
| `inventory [--deep]` | Read-only coverage and allocated/apparent bytes. Shallow default uses descriptors/top-level discovery; explicit deep census walks declared scopes without symlink/device escape. |
| `plan` | Read-only current eligible actions, blockers and policy revision. Output is explanation, not a reusable deletion authorization. |
| `apply ID...` / `sweep` | Re-evaluate selected objects / every managed eligible group under owner locks; no caller-supplied arbitrary deletion path. Normal apply cannot override a hold or unknown state. |
| `adopt PATH --owner OWNER --category CATEGORY` | Create a protected descriptor with evidence and physical scope. Adoption itself does not release consumers or delete data. |
| `retain ID --consumer REF --requires CAPABILITY` / `release ID --consumer REF --reason TEXT` | Atomically establish/release one owned obligation. Release does not assert cleanup and does not remove another consumer. |
| `register-repo PATH` / `unregister-repo PATH` | Explicit shared participation management, with outstanding-obligation checks. |
| `archive ID --destination PATH` / `restore ID` | Dispatch qualified evidence operations from §5; report exact effects, prerequisites and availability. |
| `automation install|status|disable` | Explicit idempotent installation/status/removal of this user's catch-up schedule; disabling scheduling never releases content. |

JSON includes schema, operation/outcome, observation time, policy revision, scope, object IDs/categories, dispositions/reasons, actions/outcomes and accounting limitations. Use exit0 for a completed operation, including an empty sweep; exit1 for invalid configuration or failed effects; exit75 when explicitly requested work is blocked by a prerequisite or capacity. Ordinary held/busy objects skipped during sweep are reported without making a healthy unrelated operation fail. An explicit apply/restore of the same blocked object returns75. Capacity warnings never change the wrapped compiler's exit code.

### 6.3 Scheduling, observation cost and retention of management output

Producer operations publish/update only their own small descriptors; release hooks enqueue eligible IDs for an asynchronous, best-effort sweep. They never scan the host, compress evidence or wait for retirement in a build's critical path. If enqueueing fails, preserve content and report it; the catch-up schedule supplies recovery. Invalid lifecycle metadata protects that object and does not convert a successful product command into a failed build.

Install one user systemd oneshot/timer, `library-context-storage-sweep`, daily with persistent catch-up and a15minute randomized delay. Its command runs the configured trusted checkout's storage manager in host scope. It takes a maintenance-instance lock and skips overlapping sweeps; no compiler/environment global lock, workload caps or process interruption. An absent checkout/configuration reports blocked rather than executing a different directory's code. No recurring agent conversation, shell startup hook or network notification is installed.

Automatic sweeps inspect known objects and top-level scope discovery, not every compiler file. Deep accounting is explicit and cached with timestamp/errors; stale figures cannot be labeled current. Deduplicate observed hardlinks by device/inode, distinguish apparent/allocated bytes, and state external-hardlink and shared-filesystem uncertainty. Before/after free-space values are observations, not attribution of concurrent writers' allocation.

Store the latest sweep result and30days of compact action receipts; keep unresolved operation journals until resolved. Those outputs follow their own bounded manager-owned policy and never include arbitrary source contents or credentials. Status exposes last successful sweep, skipped/failed objects, coverage gaps, protected bytes and capacity shortfall. No external message is sent.

## 7. Detailed profiling and capacity support

Preserve detailed recording, normal compiler parallelism and the separation of child outcome from observer outcome. The current perf-only8GiB floor can remain as a sampler-specific safeguard, labeled as such. It does not bound self-profile writes, and this plan adds no false hard capacity guarantee.

Report filesystem headroom and all declared diagnostic destinations before recording; track available capacity and capture allocation during observation at the existing polling cadence. Use64GiB free as an advisory for new disk-heavy work and100GiB for a detailed recording, carrying forward the review's initial suggestions solely as visible warnings. These values are configurable advisories, not admission denials, quotas or permissions to evict warm caches. Record the observation, selected destination, advisory threshold and support limitation in the profile receipt.

Add a profile-owned storage-root selection for **diagnostic output only**. Place new captures under a stable configured root with a small run-owned descriptor/pointer; preserve logical run IDs, source/settings identity and reader resolution. Do not move Cargo build/target roots or export new Cargo settings to redirect diagnostic output. Existing captures retain their current root until an explicit qualified move/archive. A selected unavailable/unwritable destination returns blocked before adding instrumentation; it does not silently record elsewhere or downgrade detail.

If capacity deteriorates after a profiled compiler has started, emit a truthful capacity/partial-observer result, use the existing sampler stop behavior where applicable, and leave healthy compiler execution unchanged. Self-profile flags cannot be withdrawn halfway through rustc. Arbitrary sustained growth on a shared finite filesystem cannot be made safe by polling or an admission estimate; record that support limit. No guarantee that an instrumented compiler cannot hit ENOSPC is made. A distinct adequate volume can reduce coupling, but this plan neither assumes a second persistent volume nor deploys one.

When all reclaimable content has gone and the warm/protected set still exceeds capacity, `status/plan` report the residual and supported choices: release specific consumer obligations, select a qualified evidence destination, or provision additional storage. No silent compression of hot caches, routine clean, reduced optimization, incremental disable or thread/job cap follows. SM7 acceptance establishes these outcomes, not a measured safe peak or a speedup.
