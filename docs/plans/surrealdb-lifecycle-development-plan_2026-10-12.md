## 1. Foundation assessment and chosen integration

The selected tool is **SurrealKit 1.0.0-beta.1**, including its Rust library; stable 0.7 is not an alternative selection. SurrealDB SDK/server remain the independently pinned patched 3.3.0 family. Existing native clients use `Surreal<engine::remote::grpc::Client>`, whereas beta `Sync` accepts `Surreal<Any>`; sharing a crate does not make these interchangeable.

Use a development-only Rust integration component outside the default product dependency closure. Exclude this component from Hakari traversal, so its remote beta features do not enter the product CLI union through transitive generation; final-output exclusion alone would retain them ([configuration contract](https://docs.rs/cargo-hakari/latest/cargo_hakari/config/index.html#traversal-excludes)). Keep existing typed native product APIs. The component generates/embeds authoritative schema assets, invokes beta Sync with an independently configured and explicitly owned Any session, and provides a worker entrypoint for the beta Rust declarative tester. Existing host run/storage owners launch and supervise the worker. Do not add a second orchestration service or expose arbitrary SQL/configuration through a product MCP operation.

The [tagged manifests](https://raw.githubusercontent.com/surrealdb/surrealkit/v1.0.0-beta.1/Cargo.toml) permit SDK/types 3.3.0 through their compatible 3.2.4 requirement. The selected workspace profile uses exact beta.1 with defaults disabled and the existing patched SDK/RPC 3.3.0 family. The [vendored profile](../../third_party/surrealkit/README.lctx.md) records two manifest-only corrections: disable upstream SDK defaults/remove its unconditional embedded `jwks` feature, and pin the macro crate exactly to beta.1. No beta source/API behavior is forked. Runtime qualification remains separate from this dependency/source decision.

The [beta tester](https://raw.githubusercontent.com/surrealdb/surrealkit/v1.0.0-beta.1/crates/surrealkit/src/tester/mod.rs) rejects embedded and unauthenticated endpoints. Its internal runner/report modules are private. Therefore declarative beta tests use a remote authenticated **entirely owned disposable service per campaign**, reused across that campaign's ordinary parallel suites. This is the default rather than depending on uncertain namespace-only actor/setup privileges. Embedded Sync is useful for narrower schema controls but is not beta declarative-test acceptance. Existing shared validation remains available for ordinary data attempts and is never a scratch fallback.

## 2. LD00 — dependency, session and target contract

Add the exact beta dependency only to the development integration. Keep its lock changes narrow, with the pinned SDK/RPC patch paths selected and one intended SDK/types family. Inspect resulting features and any additional embedded/server closure; reduce avoidable features without forking semantic behavior or wholesale updating dependencies. Compile the actual public Sync/tester/macros used by the adapter. If the advertised compatible family does not compile, repair the smallest integration incompatibility under the exact beta target, or present the specific dependency move and affected qualification; do not silently switch to stable or unpatched SDK.

For direct Sync/repository calls, construct the Any client under repository connection policy rather than beta `core::create_surreal_client`, which requests all capabilities/experimental features. Keep these directly owned sessions through setup, queries, cancellation, terminal drainage and invalidation. Qualify Any's actual gRPC route against the patched adapter; do not assume a typed native session can be converted or cloned into the same transaction session. `Surreal<Any>::invalidate().await` clears session authentication; it is not rollback. The separate transaction-session helper named `invalidate_session` is not an Any client method. A clone has a new session identity even when transport infrastructure is shared.

The public tester does not accept an injected client: its bootstrap/actor sessions use beta's internal convenience connector. Accept and qualify that behavior only inside LD02's wholly owned service, with an explicit server-side capability ceiling and actual authentication/endpoint configuration. Do not claim repository per-session cancellation handles exist for those private clients. Their final executor boundary is the drained whole service/worker; this is one reason the tester cannot attach to the canonical service. Any required non-gRPC schema-test transport remains a separately labeled schema boundary, never a product finality fallback.

Separate installation/test-target binding from semantic catalog configuration. An isolated binding is issued only by its actual host target owner, includes exact endpoint/namespace/database or whole-service scope, server generation, credentials/role and allowed effect class, and expires with that ownership. Managed local main/validation remains the default. Do not turn relaxing the database-name check into permission to attach any endpoint. Keep secrets out of receipts and diagnostics.

Expose only needed endpoint, authentication, transport/message and deadline settings through that binding. No silent buffered HTTP/WebSocket fallback is allowed where progressive/finality behavior is promised. Remote/TLS support is deferred until a concrete consumer requires it; when required, implement and qualify the secure connector explicitly. No cloud deployment is in scope.

**Investigation/completion:** narrow manifest/lock diff, actual compilation and focused connection/session controls establish SDK identity, features and directly owned Any behavior. Separately establish the tester's actual internal transport/authentication/capability behavior and server-side containment. Wrong generation, unauthorized database/target, unavailable capability, authentication failure and late terminal error refuse truthfully. A pure manifest inspection cannot close runtime connection qualification. The result enables LD01/LD02; it does not authorize a current shared installation change.

### Source and dependency decisions — Interface-checked, 2026-10-12

Context7 was the first documentation-discovery route. Its current documentation was a discovery lead; exact beta.1 registry/tag source and the selected patched SDK 3.3.0 source settle version-specific contracts. Source provenance, archive digest and upstream commit are retained in the [vendor README](../../third_party/surrealkit/README.lctx.md); the unchanged `Cargo.toml.orig` permits review of the two manifest corrections.

`default-features=false` on SurrealKit alone does not remove its unconditional SDK dependency features. In the upstream beta.1 manifest, SDK `jwks` selects `surrealdb-engine-local/jwks` and therefore an unused embedded core closure. The SDK's remote [signin implementation](../../third_party/surrealdb/src/method/signin.rs) dispatches through the selected remote engine without a `jwks` conditional; the remote server validates authentication. Removing the local JWKS feature is consequently a remote-only profile decision, requiring actual root/record/token authentication controls before Tested. It does not fix or qualify the excluded embedded engine. The upstream compatible macro requirement also admitted beta.6; exact `=1.0.0-beta.1` is required to qualify the selected beta.1 macro implementation.

The narrowly resolved development closure selects only SDK `protocol-grpc`, `protocol-http` and `rustls`, with no SDK default/parse/WebSocket/local-engine/JWKS feature. The product CLI has no SurrealKit dependency. HTTP capability in this development dependency closure does not establish a qualified HTTP operation: the worker's binding accepts the managed local gRPC runtime only, and `api_request` suites refuse before connection until a separately qualified HTTP target has a consumer. Watch, seed, rollout and type generation remain unexposed; no support is inferred from their availability upstream.

Use tracked generated assets plus an explicit development generator; avoid a native build-dependency, which would compile the large native closure separately for the host. The runtime dependency reads the same native schema authority for generation and freshness comparison. The beta.1 macro's stable keys include the declared directory and relative file name; its module inventory retains declaration order. The generator therefore uses `schema/<responsibility>/000.surql`, with directory tracking in `build.rs` for additions/removals as well as `include_str!` tracking for content edits. Ordinary Sync uses embedded bytes without writing a checkout.

The native helper's five assets cover base installation in native order: control, canonical, physical search, compiler and completion. Physical search deliberately uses the installer's existing exclusion of shared mutable blueprint function templates. Immutable per-handle published function epochs remain native publication's responsibility. This is the existing base-installation boundary, not permission to omit required control functions, fields, permissions, indexes or analyzers. Definition comparison normalizes only the application modifier (`IF NOT EXISTS`/`OVERWRITE`); function bodies, nested SQL, permissions and physical declarations remain observable. Postflight compares every required native definition while allowing beta bookkeeping and explicit fixture objects; it does not claim equality of every unrelated object in the test database.

The worker's host-issued binding names a fresh `lifecycle_<32-lowercase-hex>` database in fixed namespace `library_context`. Its existing `validation-installer.json` and sibling campaign descriptor must agree on campaign purpose, installation identity, ready phase, endpoint, namespace and generation. Before any schema effect, the directly owned Any session authenticates and reads the actual validation marker's generation, base-schema identity and schema version. Validation supplies only that proof; Sync applies to the fresh database. The host remains the authority for executable/process identity, admission, worker and datastore drainage. Tester private sessions remain contained by the whole exclusively owned campaign.

These source decisions establish no runtime connection, parser-preservation, installed-schema, permission or disposal pass. Coordinator §6 owns current compile/runtime receipts and any unresolved acceptance boundary.

## 3. LD01 — generated schema and beta synchronization

Rust model/native owners generate the complete semantic/physical schema and owned query assets. Start with [canonical_schema and compiler_record_schema](../../crates/lctx-native/src/schema.rs), plus installation/control definitions and every current required function, permission, index and metadata object. Preserve the distinction between semantic identity and physical/executable-definition identity. Do not give each relation its own module automatically.

Generate deterministic SurrealQL files, then embed them using beta `embed_schema!`. Generated files are derived artifacts with a named generator and consumer; changes to the authoritative Rust inputs regenerate them. Track both included files and directory membership so additions/removals rebuild the embedded inventory. No startup needs a writable checkout or live introspection to reconstruct source authority. Runtime filesystem sync/watch consumes the same generated inputs on disposable developer targets.

The [tagged Sync API](https://raw.githubusercontent.com/surrealdb/surrealkit/v1.0.0-beta.1/crates/surrealkit/src/sync.rs) supports `Sync::embedded(files).module(name)?.run(&db).await`. Use an explicit builder and independently configured client rather than generated convenience synchronization. Choose stable modules by actual management responsibility/dependencies; renaming a module changes tracking identity. Module/database sequencing is not a cross-target transaction.

The public tester synchronizes its default module rather than the selected Sync module matrix. Generate an explicit default-module test projection from the requested authoritative modules and their full ordered dependency closure; compare its installed inventory with that same native schema. Refuse combinations whose isolation/definition coverage cannot be represented. Do not pass an ignored module selector or describe a partial default-module test as coverage of every responsibility module.

Set pruning and failure policy explicitly. Pruning/sync/watch are allowed on the owned disposable developer boundary. Canonical product installation continues through its existing native maintenance/install authority; beta watch/pruning is not enabled there. Any future adoption into canonical installation requires checked definition transformation and current reader/definition drainage or an equivalent complete retained-epoch inventory. Do not replace functions used beneath pins merely because no table rows changed.

Render lifecycle-sensitive configuration into final authoritative SQL before beta hashing. Beta hashes raw template text independently of variable values; changed vars cannot be assumed to force reapplication. Treat `.env` and seed/type/report outputs as tooling inputs/derived products with actual owners, not another semantic configuration authority. Type generation is JSON/TypeScript introspection, not Rust semantic model generation.

**Required investigation:** beta's custom parser and overwrite transformation must preserve the complete generated definitions. Compare actual installed schema and behavior under beta application against native installation, including functions, permissions, indexes, nested statements, objects whose names track lifecycle and deletion of generated files. Parsing success or equivalent happy-path rows are insufficient. Fresh generated fixtures settle behavior; no historical schema store is needed. If transformation loses a required definition, isolate the exact unsupported asset behind explicit native application on the same owned target, retaining one generated source, and assess whether a narrow tool repair is simpler. Unsupported transformations must be explicit before beta is used for those contracts.

**Completion:** deterministic generator controls, rebuild on file addition/removal, generated-inventory correspondence, permission/function behavior and definition identity checks pass. The development route validates/formats SurrealQL using pinned tools as focused tooling checks, not a new mandatory product gate. Remove replaced duplicated schema/interpreters after all their actual consumers migrate; retain the necessary native installer/maintenance responsibilities.

## 4. LD02 — own the whole remote test target

Use existing executable-generation, managed-process/run and storage adapters to create a campaign-owned remote service with its own datastore and credentials. Reuse the exact qualified server binary without copying lifecycle facts or rebuilding per test. Register target/run/storage ownership before spawning or creating databases. Do not install, restart, borrow for DDL, reset or attach root credentials to the shared/dedicated/operator service. Root test credentials apply only inside this exclusively owned service; configure actual required capabilities explicitly, not broad convenience defaults.

Target records bind process identity, executable provenance, endpoint, whole-datastore boundary, credentials reference, run consumer and cleanup status. Tests may create arbitrary generated suite database names only inside that boundary. This whole-target inventory remains recoverable when beta fails before producing a report. An inventory based solely on report-listed suites is inadequate.

The Rust worker calls public `tester::run_test` with explicit target overrides, template inputs, `keep_db = true` and JSON reporting. Runner internals are not an integration API. A process boundary contains environment/stdout and aborted suite tasks while preserving the Rust-library target. The parent records test exit, report/capture health, child cleanup, database disposal and any actual native effects independently. No invented native attempt is needed for a pure schema suite that did not create one.

After draining the worker and any submitted owners, inspect the exclusively owned target inventory and perform checked disposal. Beta warnings/success are not disposal acknowledgement; [tagged cleanup](https://raw.githubusercontent.com/surrealdb/surrealkit/v1.0.0-beta.1/crates/surrealkit/src/tester/runner.rs) can discard statement errors. Namespace/database removal is a logical operation and may enqueue reclamation. Final whole-target shutdown and datastore disposal require confirmed process/native executor drainage and the actual host storage owner. Never remove a live datastore from under a daemon.

The selected worker sets `keep_db=true`, so logical DROP is not attempted; whole-target shutdown/discard is its retirement route. If a later explicitly selected logical DROP fails, the target remains owned. A fully confirmed whole-target shutdown/discard can settle its disposal without recovering or preserving its old data; report the failed step and successful disposal separately. If drainage is unknown, keep the minimal current obligation/target identity until resolved. No preserved old dataset or evidence archive is required. Only a named current diagnostic consumer may temporarily hold a failed target; once released, dispose it. Generic storage sweeps do not gain native retirement authority.

**Completion:** fresh controlled cases fail during setup, schema statements, report output, parallel fail-fast, cancellation and disposal. A failure before report creation still identifies and drains the whole target. Late remote errors preserve uncertainty. Repeated checked cleanup is idempotent, cannot touch another campaign and reports missing prerequisites honestly. Normal available suite/test parallelism remains. Prove a shared service remains untouched by endpoint/identity controls rather than performing disruptive tests against it.

### Selected worker support and negative boundaries

The current adapter uses `fail_fast=false`, ordinary available suite parallelism and `keep_db=true`. Named-module Sync and dependency-closed default-module test projection are its two database operations. It exposes no watch, seed, rollout, type generation, API request, embedded-engine or fail-fast-selection route. Multi-suite fail-fast interruption and stale-prune deletion are not established by a single fresh full-schema suite; qualify them when their actual consumer is introduced rather than infer support from the upstream command list.

The [small negative input projects](../../tools/lctx-surreal-dev/tests/fixtures/README.md) distinguish input parsing before a worker connection, a failed assertion with a completed JSON report, and an actor authentication refusal during tester setup with no report. Beta writes JSON only after its runner returns; an unsuccessful setup is consequently missing capture, while a completed failed case has healthy capture. Worker outcome, report health, process cleanup and target finality retain independent meanings. A missing report never becomes success, including if the public tester unexpectedly returns success without writing one.

Cancellation uses a fresh fixture table and a bare multi-statement query that creates a marker before `SLEEP`. Observing that committed marker while the worker remains live establishes that the issued query began; it does not establish which later statement reached terminal completion. Authenticated local worker cancellation and confirmed child cleanup still leave the private beta sessions/native executor unknown until the whole exclusively owned target is drained and disposed. A cancellation attempt that misses this observation remains failed evidence; a later successful control does not rewrite it. Actual selected-profile parser, authentication, definition, report and cancellation receipts remain in coordinator §6.
